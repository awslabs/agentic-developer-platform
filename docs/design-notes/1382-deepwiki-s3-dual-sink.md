# Design Note: DeepWiki Output to S3 (Human Browse) + S3 Vectors (Semantic Embeddings)

**Issue:** #1382 (sub of #1345)
**Author:** @agent-architect
**Date:** 2026-06-12
**Status:** Implementation-ready design
**Companion docs:** `docs/knowledge-layer-storage-design.md` (design of record), `docs/design-1348-replace-openviking.md` (S3 Vectors implementation detail)

---

## 1. Executive Summary

DeepWiki generates **natural-language architecture wikis** describing a repository's design, components, and data flow. Today this output is uploaded to OpenViking (`viking://resources/deepwiki/{repo}-wiki.md`). EPIC #1345 removes OpenViking (#1348). This design re-homes the wiki to two sinks:

1. **S3 (human-browsable):** wiki markdown as an S3 object, served via Mountpoint or presigned URL.
2. **S3 Vectors (semantic search):** wiki text chunked by heading, embedded via LiteLLM/Titan, stored as vectors with ACL metadata.

The wiki is the **primary semantic-search content** (not raw code). A query like "where do we handle rate limiting?" matches the wiki sentence "this module implements token-bucket throttling" far better than it matches `class TokenBucket`. This is the key design insight.

## 2. Design Validation Against S3 Vectors Docs

| Design claim | Verified | Notes |
|---|---|---|
| Wiki text can be embedded at 1024 dim | Yes | Titan Embed v2 produces 1024-dim vectors; S3 Vectors supports up to 4,096 |
| Section-aware chunks fit in metadata budget | Yes | Filterable metadata <=2 KB, non-filterable <=40 KB. Wiki chunk text as non-filterable (~2-4 KB) is well within 40 KB |
| `source_type` as filterable metadata | Yes | Allows queries to filter `source_type: "wiki"` vs `source_type: "code"` |
| Cosine distance for wiki similarity | Yes | S3 Vectors supports `cosine` metric (confirmed in design-1348 §2.1) |
| Batch write (500 vectors/call) | Yes | A wiki with 20-40 sections = 20-40 vectors per repo, well within single batch |
| ACL metadata (`allowed_principals`) as non-filterable | **Revised** | Use `repo` (filterable) for shard routing + Door filter for ACL enforcement. Don't embed `allowed_principals` array as filterable metadata (too large, changes on team membership). The Door reads ACL from Postgres `repositories.allowed_principals` at query time. |

### 2.1 Why Wiki Text is Better Embedding Input Than Raw Code

| Input type | Embedding quality for concept queries | Cost | Volume |
|---|---|---|---|
| Raw code chunks (per-symbol) | Low — identifiers are terse, context is implicit | High — 50K+ chunks per large repo | ~5-50 MB/repo |
| Wiki text (per-section) | **High** — complete sentences describe architecture, patterns, intent | Low — 20-40 sections per wiki | ~20-100 KB/repo |
| Both (raw code + wiki) | Marginal gain over wiki-only for concept queries | 2x embedding cost | Both |

**Decision:** Wiki text is the **primary** embedding target. Raw-code embedding (#1348's code-chunking path) is secondary and optional — deferred unless recall testing shows gaps.

**Rationale:** The wiki is generated by Sonnet, which already understood the code. Embedding the wiki embeds the *understanding*, not the *syntax*. For retrieval queries that are inherently natural-language ("how does auth work?", "where is the rate limiter?"), wiki prose provides dramatically better recall than symbol names and raw code.

## 3. Dual-Sink Architecture

```
                    DeepWiki generates wiki markdown
                              │
                              ▼
              ┌───────────────────────────────────────┐
              │         wiki_store.py                   │
              │   (replaces upload_to_openviking)       │
              ├───────────────────────────────────────┤
              │                                        │
              │   1. Write wiki to S3                   │
              │      s3://.../content/wikis/{repo}.md   │
              │                                        │
              │   2. Chunk wiki by headings             │
              │      (section-aware splitter)           │
              │                                        │
              │   3. Embed each chunk via LiteLLM       │
              │      (Titan Embed v2, 1024-dim)         │
              │                                        │
              │   4. Write vectors to S3 Vectors        │
              │      (code-shard-N, metadata tagged)    │
              │                                        │
              │   5. Update catalog (repositories row)  │
              │      wiki_status = 'complete'           │
              │      wiki_s3_key = '...'                │
              └───────────────────────────────────────┘
```

### 3.1 S3 Object Layout

```
s3://{bucket}/content/wikis/{org}-{repo}-wiki.md       # Wiki markdown
s3://{bucket}/content/code-indexes/{org}-{repo}.md     # Code-index markdown summary
```

**Naming:** `{org}-{repo}` with `/` replaced by `-` (matches existing `safe_name` pattern in `ingest-repo.py`).

**Write semantics:** New object per wiki generation (idempotent overwrite via S3 PutObject, NOT Mountpoint which is write-once). Workers use the boto3 S3 API directly, not Mountpoint, for wiki writes — Mountpoint's write-once constraint means you can't update a wiki when the repo changes.

**Read semantics:** Serving pods can read via Mountpoint (read-only mount) or presigned URL. The `browse` verb uses the catalog to look up `wiki_s3_key` then serves the content.

### 3.2 S3 Vectors Embedding

Each wiki section becomes one vector in the shared code-vectors index (same sharding as code embeddings):

| Field | Value | Filterable? |
|---|---|---|
| `key` | `wiki:{org}/{repo}:{section_heading}:{chunk_idx}` | (vector key) |
| `data` | 1024-dim float32 embedding | (vector) |
| `repo` | `org/repo` | Yes |
| `org_id` | org identifier (determines shard) | Yes |
| `source_type` | `"wiki"` | Yes |
| `language` | `"en"` | Yes |
| `section_heading` | heading text | No |
| `chunk_text` | first 500 chars of chunk (for preview) | No |
| `wiki_s3_key` | full S3 key for browse link-back | No |

**Shard assignment:** Same as code vectors — `hashlib.sha256(org_id) % shard_count`. Wiki vectors and code vectors coexist in the same sharded indexes, differentiated by `source_type` metadata.

**Why same index (not separate wiki index):** Agents querying "how does X work?" benefit from BOTH wiki prose and code definitions appearing in one result set. Separate indexes would require scatter-gather across wiki AND code indexes, doubling query cost for minimal benefit. The `source_type` filter allows wiki-only or code-only queries when needed.

### 3.3 Catalog Update

The `repositories` table already has `vectors_status` (for code vectors). Add:

- **`wiki_status`** — `pending` | `complete` | `failed` (status of wiki generation + S3 upload + embedding)
- **`wiki_s3_key`** — S3 object key of the wiki markdown (nullable, set on success)

These are added via a new Alembic migration (`002_add_wiki_columns.py`). The `browse` verb uses `wiki_s3_key` to locate and serve wiki content.

## 4. Wiki Chunking Algorithm (Section-Aware)

### 4.1 Why Section-Aware

DeepWiki outputs structured markdown with headings (`## Architecture`, `## Key Components`, etc.). Each heading introduces a semantically coherent section. Splitting on headings:
- Preserves semantic boundaries (a section about "auth" stays together)
- Produces chunks of reasonable size (200-2000 tokens)
- Aligns with how humans browse (each chunk = one browsable section)

### 4.2 Algorithm

```python
def chunk_wiki_by_sections(wiki_text: str, max_chunk_tokens: int = 1500) -> list[dict]:
    """Split wiki markdown into section-aware chunks.

    Rules:
    1. Split on headings (##, ###, ####). Each heading starts a new chunk.
    2. Include the heading in its chunk (for embedding context).
    3. If a section exceeds max_chunk_tokens, sub-split on paragraph breaks.
    4. Content before the first heading is chunk 0 ("preamble").
    5. Each chunk includes its heading hierarchy (e.g., "## Architecture > ### Components").

    Returns: [{heading, text, chunk_idx, char_start, char_end}]
    """
```

### 4.3 Edge Cases

| Case | Handling |
|---|---|
| No headings (flat markdown) | Single chunk (the whole document). If > max_tokens, split on paragraph breaks. |
| Very long section (>1500 tokens) | Sub-split on `\n\n` (paragraph breaks). Each sub-chunk inherits the parent heading. |
| Very short section (<50 chars) | Merge with the next section (don't embed fragments). |
| Code blocks within sections | Keep code blocks intact within their section. Don't split mid-code-block. |
| Empty sections | Skip (don't embed empty content). |

### 4.4 Token Estimation

Use a simple heuristic: `len(text) / 4` for English prose (Titan tokenizer produces ~1 token per 4 chars for natural language). This avoids importing a full tokenizer. The `max_chunk_tokens=1500` target produces chunks of ~6000 chars — well within the Titan Embed v2 input limit of 8192 tokens.

## 5. Dependency Ordering (No Storage Gap)

**Critical sequencing:** This issue (#1382) must land **with or before** #1348's OpenViking removal.

### 5.1 Migration Strategy

Follow the Phase 1-4 approach from `design-1348-replace-openviking.md`:

1. **Phase 1 (this issue):** Add S3 + S3 Vectors as a NEW wiki sink. OpenViking upload continues (dual-write). Feature flag: `WIKI_SINK=dual` (default during transition).
2. **Phase 2 (#1348 lands):** Switch to `WIKI_SINK=s3` only. Remove OpenViking calls.
3. **Phase 3 (cleanup):** Remove dual-write code, feature flag, OpenViking references.

**Implementation in `ingest-repo.py`:** The new `wiki_store.py` module is called AFTER (or instead of) `upload_to_openviking()`. During dual-write, both are called. The feature flag determines behavior:

```python
# In ingest-repo.py Step 4:
WIKI_SINK = os.environ.get("WIKI_SINK", "dual")  # "dual" | "s3" | "openviking"

if WIKI_SINK in ("dual", "s3"):
    store_wiki_to_s3(wiki, org_repo, allowed_principals)  # New path
if WIKI_SINK in ("dual", "openviking"):
    upload_to_openviking(...)  # Legacy path (removed in Phase 3)
```

### 5.2 What Happens If #1348 Removes OpenViking First

If OpenViking is removed before this lands, the wiki upload simply fails (gracefully — `upload_to_openviking` returns False, `result["deepwiki"] = "upload_failed"`). Wikis are regenerable, so no data is permanently lost. But this is suboptimal — the goal is to have the S3 sink ready first.

**Enforcement:** This PR should be merged BEFORE or simultaneously with the #1348 PR that deletes OpenViking deployment manifests.

## 6. ACL Metadata Design

### 6.1 What Gets Tagged

| Artifact | ACL mechanism | Why |
|---|---|---|
| S3 wiki object | Postgres catalog (`repositories.allowed_principals`) | The object itself doesn't carry ACL — the Door looks up permissions at serve time via repo_name |
| S3 Vectors entries | Filterable `repo` metadata + Door filter at query time | The Door reads `allowed_principals` from Postgres for each result's `repo`, drops unauthorized results |

### 6.2 Why NOT Embed `allowed_principals` in Vector Metadata

- `allowed_principals` is a JSON array (e.g., `["team:backend", "user:alice", "user:bob"]`)
- It changes when team membership changes (without re-indexing)
- S3 Vectors filterable metadata supports equality/range filters, not array-contains
- The Door already implements fail-closed ACL filtering for all query results

**Correct approach:** Tag vectors with `repo` (stable identifier). At query time, the Door:
1. Fetches `allowed_principals` for each result's `repo` from Postgres
2. Checks if the caller's identity intersects with `allowed_principals`
3. Drops unauthorized results (fail-closed: unknown identity = empty results)

This is the same pattern used for code vectors (#1348) and is already designed in `design-1348-replace-openviking.md` §8.3.

## 7. DeepWiki JSON Config — Second Source of Truth Resolution

### 7.1 The Problem

Two config sources control DeepWiki behavior:

| Config | Controls | Location |
|---|---|---|
| `config.py` (centralized) | `model_wiki`, `deepwiki_url`, `deepwiki_enabled` | `images/ingestion/config.py` |
| `generator.json` | DeepWiki container's model selection | `images/deepwiki/config/generator.json` |
| `embedder.json` | DeepWiki container's internal embedder | `images/deepwiki/config/embedder.json` |

Changing `model_wiki` in `config.py` changes what the ingestion script sends to DeepWiki as the `model` parameter. But `generator.json` independently pins `bedrock/global.anthropic.claude-sonnet-4-6` — DeepWiki uses ITS OWN config for model selection, not the caller's parameter.

### 7.2 Resolution: Document as Intentional Container Config

**Decision:** The DeepWiki JSONs are **intentional container-level config**, not a bug.

**Rationale:**
1. DeepWiki is a separate service (its own image, Dockerfile, deployment). It should own its own model config.
2. The `model` parameter in the `/chat/completions/stream` request is a *suggestion* — the server's `generator.json` takes precedence.
3. Changing the DeepWiki model requires rebuilding the DeepWiki image (or mounting a ConfigMap override), which is an intentional operational step.
4. The `embedder.json` uses 256-dim Titan (for DeepWiki's internal RAG retrieval), while the ingestion pipeline uses 1024-dim Titan (for S3 Vectors). These are intentionally different — DeepWiki's internal retrieval needs fast/cheap embeddings, while our semantic search index needs high-quality embeddings.

### 7.3 Action Items

1. **Add a comment in `config.py`** noting that `model_wiki` controls the model parameter sent to DeepWiki but DeepWiki's actual model is governed by its container config (`images/deepwiki/config/generator.json`).
2. **Add a comment in `generator.json`** noting this is the authoritative DeepWiki model config.
3. **Do NOT template these JSONs from config.py** — it couples the ingestion container to the DeepWiki container's internals, creating a brittle dependency.

### 7.4 The `embedder.json` Dimension Mismatch Is Intentional

| Context | Model | Dimensions | Purpose |
|---|---|---|---|
| DeepWiki internal RAG | Titan Embed v2 | **256** | Fast retrieval within DeepWiki's own knowledge base during wiki generation |
| S3 Vectors (our semantic search) | Titan Embed v2 | **1024** | High-quality semantic search across repos for agents |

These serve different purposes. DeepWiki's 256-dim embeddings are internal to its generation process and never leave the container. Our 1024-dim embeddings are what we store in S3 Vectors for agent queries. No conflict.

## 9. Interface Contract

### 9.1 `wiki_store.store_wiki()`

```python
def store_wiki(
    wiki_text: str,
    org_repo: str,
    org_id: str,
    allowed_principals: list[str],
    *,
    s3_client=None,       # Injectable for testing
    vector_store=None,    # Injectable for testing (FakeVectorStore in tests)
    embedding_client=None,  # Injectable for testing
) -> WikiStoreResult:
    """Store wiki to S3 and embed to S3 Vectors.

    Returns a result object with status for each sink.
    """
```

### 9.2 `WikiStoreResult`

```python
@dataclass
class WikiStoreResult:
    s3_key: str | None = None           # S3 object key on success
    s3_success: bool = False
    vectors_written: int = 0            # Number of wiki chunks embedded
    vectors_success: bool = False
    catalog_updated: bool = False
    error: str | None = None            # Error message on failure
```

### 9.3 `chunk_wiki_by_sections()`

```python
def chunk_wiki_by_sections(
    wiki_text: str,
    max_chunk_chars: int = 6000,  # ~1500 tokens
    min_chunk_chars: int = 50,
) -> list[WikiChunk]:
    """Split wiki into section-aware chunks for embedding."""

@dataclass
class WikiChunk:
    heading: str          # e.g., "## Architecture"
    text: str             # Full chunk text including heading
    chunk_idx: int        # Sequential index
    char_start: int       # Start position in original text
    char_end: int         # End position in original text
```

## 11. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| S3 Vectors not available in deploy region | Verified GA (`s3vectors-2025-07-15`); fall back to `us-west-2` if needed |
| Wiki embedding cost spike on bulk re-index | SHA-gated: only re-embed when repo SHA changes. 500 repos x 30 chunks x $0.01/1K tokens = ~$0.15 total |
| Mountpoint write-once blocks wiki update | Use boto3 S3 PutObject directly (not Mountpoint) for writes |
| OpenViking removed before this lands | Graceful degradation (upload_failed is non-fatal); wikis are regenerable |
| Vector metadata changes require re-embed | Metadata schema is stable; `repo` and `org_id` don't change for a given wiki |

---

## 12. Summary

The dual-sink design is sound and well-supported by AWS services. Wiki text is materially better semantic-search input than raw code. The implementation is a self-contained module (`wiki_store.py`) that slots into the existing ingestion pipeline at the point where `upload_to_openviking()` is currently called. The feature flag (`WIKI_SINK`) ensures safe transition during the OpenViking removal. ACL enforcement stays at the Door (not in vector metadata), keeping the permission model simple and updateable without re-indexing.
