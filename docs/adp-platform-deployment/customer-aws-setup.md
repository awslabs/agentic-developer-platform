# Customer AWS Role Setup

ADP supports two gateway-mediated steady-state operations and publishes a
separate bootstrap role contract. Each operation uses its own CloudFormation
role and trust contract. Their permission models differ:
the Bedrock routing role has an ADP-owned, operation-level allowlist, while the
legacy personal inspection role attaches AWS-managed `ReadOnlyAccess`. Neither
role is a platform bootstrap or general infrastructure administration role.

## Supported Operations

| Operation | Access phase | Role template | Effective permissions |
|---|---|---|---|
| Personal account inspection (legacy broad read) | Steady state | `modules/gateway/src/auth/cfn_templates/aws_role_v1.yaml` | AWS-managed `ReadOnlyAccess`; broad metadata and data reads, including S3 object reads, with no Bedrock model invocation or write APIs |
| Shared Bedrock model routing, including the OpenAI-compatible Responses route | Steady state | `modules/gateway/src/auth/cfn_templates/aws_role_v2.yaml` | `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on foundation-model and account-local inference-profile ARNs, plus `bedrock:InvokeModel` on the account-local `project/default` required by Responses |
| Foundation bootstrap contract (hosted execution disabled) | Bootstrap | `modules/gateway/src/auth/cfn_templates/aws_role_deploy_v1.yaml` | Named or tagged networking, ECR, S3, Secrets Manager, SSM, and logging operations plus four default-off capabilities; all IAM mutation is denied |

The Bedrock routing role has no optional sub-capabilities. Native model calls
authorize against model and inference-profile resources; the OpenAI-compatible
Responses route authorizes `bedrock:InvokeModel` against the destination
account's `project/default`. Treat access to both routes as part of enabling a
routing destination. ADP must enforce any
future route-level opt-out before assuming the destination role; do not model it
as a customer IAM toggle unless AWS provides a distinct action, resource, or
condition key.

Only the Bedrock routing template is a least-privilege, operation-level
permission contract. The legacy inspection template is not data-plane-isolated:
AWS `ReadOnlyAccess` permits broad reads of supported service metadata and
customer data, including `s3:GetObject`, and AWS can update that managed policy
without a repository change. Install v1 only when that broad read exposure is
acceptable; do not describe it as least privilege.

Neither template grants IAM mutation, role passing, role assumption, or
destructive infrastructure APIs. The v2 role grants no S3, KMS, Secrets Manager,
Organizations, or billing access. The gateway may call `sts:AssumeRole` and
`sts:TagSession` from its own platform role, but neither customer role receives
permission to assume another role.

## Trust Boundary

Both templates require the per-connection External ID generated by ADP and pin
trust to the exact gateway role through `aws:PrincipalArn`. The account-root
principal alone does not authorize assumption.

The personal inspection role additionally requires the connecting ADP user's
`adp:user_id` request tag. The shared routing role deliberately does not use a
single-user authorization tag because a routing destination can serve a team;
the gateway still sends session tags for customer CloudTrail attribution.

The dashboard currently generates the External ID as a 36-character UUID. Use
the value supplied by the connection flow unchanged. It is stored as part of the
connection credential and is not shared with another customer connection.

## Connect Legacy Personal Read-Only Access

Before continuing, confirm that the target account owner accepts the effective
AWS-managed `ReadOnlyAccess` policy, including customer data reads. For a
metadata-only requirement, do not install v1; the repository does not currently
ship a narrower personal inspection tier.

1. Open **Settings > Credentials > Connect AWS** in ADP.
2. Enter the target 12-digit AWS account ID and a unique connection nickname.
3. Open the returned CloudFormation Quick Create URL while signed into the
   target account.
4. Confirm the account and parameters, acknowledge named-IAM creation, and wait
   for `CREATE_COMPLETE`.
5. Return to ADP and verify the connection.

The stack creates `ADP-Agent-<nickname>`. Do not add policies to that role
outside CloudFormation: an out-of-stack grant survives stack deletion and makes
the role's displayed template differ from its effective access.

An AWS administrator can instead download the setup package from the connection
row. The package contains the same template, External ID, user tag, and expected
role ARN as the Quick Create URL.

## Configure Bedrock Routing

Use the Bedrock account-routing flow in ADP settings. It launches the v2 role
template and verifies both assumption and Bedrock invocation capability before
the account becomes a routing destination. This is a separate authorization
from personal read-only access even when both roles use the same nickname shape.

The installed role authorizes both native Bedrock routing and the
OpenAI-compatible Responses route. Do not install it when the destination
account must exclude either route; the current gateway has no separately
enforceable destination capability for Responses traffic.

## Platform Bootstrap Is Separate

Provisioning ADP itself creates networking, EKS, IAM service roles, CodeBuild,
storage, logging, and other infrastructure. Those bootstrap operations are not
part of either supported customer role above. They also cannot be made safe by
attaching `AdministratorAccess` to the read-only role: that would expose all
customer data and destructive APIs, permit role-grant escalation, and leave an
out-of-stack grant behind after revocation.

The repository publishes `aws_role_deploy_v1.yaml` so customers and reviewers can
inspect the proposed bootstrap ceiling. It is not registered by the dashboard
and does not enable hosted execution. Do not use `customer_account` in
`config/deployment.yml`; the shared deployment loader rejects that block and all
`ADP_CUSTOMER_*` overrides before plan, apply, or destroy.

The bootstrap contract requires a tenant External ID and exact gateway principal.
It contains an explicit control-plane action inventory, scopes writes by the
`adp-<DeploymentId>-*` name or `adp:deployment-id` ownership tag, and denies all
IAM mutation and outbound role assumption. It therefore cannot create a role
with attacker-controlled trust, but it also cannot complete an ADP installation,
which needs service roles. Its optional capabilities all default off:

- tagged RDS, DynamoDB, and ElastiCache control-plane operations;
- tagged CloudFront, ACM, and WAF control-plane operations (DNS is excluded);
- Bedrock invocation-logging and AWS Marketplace subscription operations; and
- destructive teardown of deployment-named or deployment-tagged resources.

Create APIs require the deployment request tag where the service supports it.
Update and delete APIs use the resource tag instead, because those APIs do not
accept request tags. S3, ECR, Secrets Manager, and SSM use deployment-specific
ARNs. The role cannot write S3 bucket policies or ECR repository policies, so it
cannot leave direct cross-account resource grants behind. Deleting the bootstrap
stack removes the role and its inline policy, preventing new role sessions; an
already-issued session can continue until its maximum one-hour expiry. No
resource-policy grant or retained boundary survives. Steady-state access remains
in the separate inspection and Bedrock-routing stacks.

Until hosted execution has all of the following, run the
[self-managed deployment](./self-managed-deploy.md) with temporary,
customer-controlled operator credentials instead:

- tenant-bound registration and explicit deploy-tier selection;
- gateway permission scoped to the registered deploy role ARN;
- an allowlisted role-provisioning mechanism that validates every initial trust policy;
- a verified action inventory for all deployment phases beyond the foundation subset;
- deploy-request authorization against the registered capability set;
- integration tests proving the full selected phase set succeeds; and
- negative runtime tests for unrelated customer data, roles, and regions.

Bootstrap credentials should be removed by the customer after deployment.
Steady-state inspection and Bedrock routing continue to use their scoped roles.

## Revocation and Audit

- Delete the relevant CloudFormation stack to revoke that connection role.
- If the role was modified outside the stack, inspect and remove those grants
  separately; stack deletion cannot manage resources it did not create.
- Filter customer CloudTrail by the `adp:*` session tags to attribute calls to
  the ADP user, agent, task, or run that initiated them.
- Rotate a compromised connection by creating a new connection/External ID and
  updating the stack before deleting the old credential.

No customer IAM changes occur merely by linking an account or editing these
templates. The customer owns stack creation, updates, and deletion.

## Troubleshooting

| Symptom | Likely cause | Repair |
|---|---|---|
| CloudFormation rejects the External ID | Value is not the UUID issued for this connection | Reopen the saved connection setup; do not generate or substitute another value |
| Verification returns `AccessDenied` | External ID, gateway principal, user tag, or role ARN differs from the saved credential | Compare the saved setup package with the installed stack parameters |
| Bedrock routing verification fails | A v1 read-only role was installed, model access is unavailable, or the v2 policy was altered | Launch the routing setup and verify the v2 stack without widening it |
| Terraform returns `iam:CreateRole` denied | A steady-state customer role was used for bootstrap | Stop the run and use the self-managed deployment path; do not attach an administrator policy |
