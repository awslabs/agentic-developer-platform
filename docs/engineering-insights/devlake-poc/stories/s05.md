## Owned change and decisions

Proposed narrow native requirement/test capture mappers and a bounded evidence-chain report under modules/insights/poc/devlake. Reuse #7302 schemas and S04 admission. This is not #7300 delivery-record distillation, a general acceptance engine or production shipment proof. No inference of per-test results from DevLake workflow summaries.

## Interfaces, data and authorization

Inputs pin exact Story/criterion/scenario/test/selection revisions, planned instances, attempts, code and artifact digest, permitted dev receipt and independently identified assessor. Capture revisions before editing; absent source history/selection/actor remains unknown. Every report/artifact/cost edge inherits source and execution-evidence restrictions. The report output separates facts, reviewed links, heuristic links and assessment authority.

### Retained implementation requirements

- **Deliverables and entry points:** Proposed narrow source/test mappers under `modules/insights/poc/devlake/` and a read-only evidence-chain report; no new general query service. Directly capture requirement revisions and detailed test evidence where DevLake lacks that grain.
- **Inputs and configuration:** S04 qualified refs/policy dependencies; AC/scenario revision, code/artifact digest, CI selection/attempts, dev receipt and authenticated execution where available. Source/run/artifact classification is authority-resolved before persistence.
- **Outputs and behavior:** Report requirement -> criterion -> selected test -> attempts -> code/artifact -> environment receipt with evidence for each edge. Explicit manual/policy assessment names its actor and criterion revision. Missing actor or environment remains unknown; bot authorship alone is not execution attribution.
- **Compatibility and data:** Private evidence stays restricted through joins; producer shared labels grant nothing. Reruns differ from retries; run-level summaries cannot invent tests. Edited criteria retain history; dev is not production; manual assessment is not a general evaluator.

The canonical architecture resolves placement, policy, publication and lifecycle details when the older implementation-contract summary is less specific. It does not relax any acceptance predicate. Common six-field identities, native provenance and current authorization remain mandatory.

## Fixtures, independent oracles and completion

One controlled Story has two criterion revisions, a fail-then-pass instance and one planned instance with no result. Source/CI/artifact/deployment systems provide independent readback. Wrong artifact digest and private-to-shared join fail. An assessment referencing revision one cannot accept revision two; both attempts remain and coverage cannot be 100 percent. Fixed selection/correction ordering prevents rerun-dependent results.

Use the [shared verification controls](../verification.md#fixture-and-determinism-contract). Pin code, requirements, source revisions, clocks, routing/policy epochs and cleanup ownership. Authenticate through the real entry point; mocks may support pre-review tests but cannot substitute for required live proof. A plausible wrong result must fail the independent oracle, not merely match an implementation-generated fixture.

The delivery owner reports every acceptance ID as pass/fail/blocked/not-run with attempt, tested revision, expected/actual result and private evidence reference; the acceptance owner separately records the decision. Failed cleanup or missing required evidence is incomplete. [Architecture questions](../audit.md#unresolved-facts-and-coverage-limits) identify remaining readiness/fixture/ownership facts.
