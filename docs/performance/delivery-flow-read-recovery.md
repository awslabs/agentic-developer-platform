# Delivery-flow read: release recovery and abort procedure (#7777)

**Status: PROCEDURE ONLY — deployment and live acceptance are not established by this document.** Use this with [the rollout and validation runbook](delivery-flow-read-validation.md). Keep the private operations receipt outside the repository; never commit credentials, environment addresses, account or workspace identifiers, fixture manifests, benchmark output or live evidence. A successful workflow or checked merge alone does not prove the backend, served frontend or engine delivery. Do not claim engine acceptance.

## Before recovery: identify the release and authority

1. Preserve the failed or interrupted run URL, attempt, job and step conclusions, log excerpts, selected source and workflow-definition revisions, environment, authentic invocation correlation, observed backend image/digest and frontend build/asset evidence, and the last verified compatible release in the controlled operations record. Keep observer failure distinct from deployment failure. Compare with the accepted operations-task pins; if the checked repair merges, the coordinator must advance **both** pins together to its verified merge revision before its authorized combined dispatch. Never invent a correlation, relabel an older run, independently advance a pin or relax revision guards.
2. Inspect the current `gateway-deploy.yml` run and any automatic push deployments before asking for another release. A push-triggered Gateway Deploy can update the backend but does not execute the combined frontend job; documentation-only changes start neither job. The authorized coordinator, not this worker, dispatches the combined workflow using the task's invocation and conducts live certification. Do not rerun a deterministic failed attempt unchanged or supply human-approval inputs. If dispatch, private config or runtime access is denied, record the exact block and leave verification open.
3. Classify the fault before choosing an action: source/configuration error, migration or index error, backend rollout, frontend build/sync/invalidation/served-content mismatch, smoke test, auth/runtime-access failure, benchmark/content regression, cleanup failure, or observer interruption. A failed observer on a green deploy leaves the release **unverified**; resume observation only for the current attempt's genuine correlation and matching selected revisions. Fix an observer defect through a scoped checked repair rather than treating workflow success as a runtime evidence ID.

## Restore service if the release is unsafe

Stop new benchmark clients and preserve their partial counts and logs. Through the accepted deployment authority, restore the **last verified compatible frontend first**, then the matching backend release; verify that this order and pair are compatible with the installed schema. Do not swap an old frontend onto an incompatible backend, bypass an approval, or reset a live schema to force a rollback. Additive decision indexes may remain installed; for an interrupted concurrent index build inspect database state and follow the accepted resumable migration path before promoting a reader. If a safe compatible pair or authority is unavailable, hold the release and escalate that exact prerequisite instead of guessing a revision or destructive database action.

After each rollback stage record the selected/restored revisions, action run/attempt and outcome. Using the verified runtime connection and private configuration, confirm the served HTML shell and its hashed JS/CSS assets are the restored build (successful responses, correct content type, no HTML fallback), `/api/health` returns healthy JSON, and the permitted read and cross-workspace-denial checks still hold. Observe automatic deployments to terminal state so a later push cannot silently overwrite the restored pair. A rollback is not complete merely because the rollback workflow exited successfully. If the frontend cannot be verified after restoring it, do not mark service recovered while proceeding with a backend action; record the degraded state and assess compatibility under the accepted authority.

## Abort and fixture cleanup, including interrupted testing

On a timeout, five consecutive failures, out-of-memory, process restart, drift of source or runtime, auth failure or budget limit, abort promptly. The shared certification budget is at most 3,000 API plus intercepted browser API attempts, 20 active minutes, five concurrent readers, a 15-second request deadline and a 30-second client drain. Do not restart a new output directory to reset the budget or omit failed attempts. Stop owned clients and drain for 30 seconds; preserve planned/observed/success/failure counts and classifications for every incomplete cell.

Restore the synthetic workspace and any read-only real-workspace selection to their prior states. Use only the private ownership manifest to identify synthetic fixtures; never delete or modify real-user data. Retain `ownership.json`, `cleanup.json` and `cleanup-receipts.jsonl` in private storage. If the harness was interrupted, use its `--cleanup --manifest PRIVATE_OWNERSHIP_JSON` path only for manifest-owned local cleanup. That path does **not** prove server-side fixture deletion: any manifest-owned remnants require separately authorized deletion and a verified readback. Record each deletion receipt, remaining owner/fixture state and any hold; do not call cleanup complete while a remnant remains. Recheck health, served assets, permitted reads and foreign-workspace denials after cleanup.

## Verify the repaired release before closing the hold

Publish the smallest scoped fix in a ready PR, inspect its exact head and required CI, merge through the gateway only when ready, and record the actual merge revision. Observe automatic deployments before the coordinator's next combined dispatch. For that dispatch, match the selected source and definition revisions to the **jointly advanced** pins and the authentic correlation. Observe `changes`, `deploy-backend`, `deploy-frontend`, `run-migrations`, `finalize-pricing` and `smoke-test` to terminal state; frontend must succeed, not skip. Capture backend release digest, frontend build/sync and invalidation receipts and smoke-test assertions (a missing-token smoke success may skip real-token checks). Compare the post-invalidation served index and hashed assets against the selected frontend build, and independently check healthy backend JSON via the verified runtime connection. Confirm migration and new-reader compatibility when relevant. A green build, upload or run is not served-content verification.

After rollout or a rolling restart settles, the authorized operator must discover the **current execution identity and ready pod names** before running the unchanged read-only schema probe. Rebind temporary schema-probe access to that exact Kubernetes User and only those named pods; stale pod names or an identity from an earlier attempt cannot authorize this attempt. For Kubernetes 1.35 WebSocket exec connect authorization, allow both `get` and `create` on `pods/exec` for those exact pods: an initial allowed GET may still be followed by a 403 when the matching create permission is absent. Verify the current connection and probe receipt before treating the schema as checked. Never grant access group-wide or to all pods. Kubernetes RBAC cannot constrain the text of a command executed through `pods/exec`, so the narrow User/pod binding and unchanged read-only probe are both necessary; revoke the temporary binding immediately after its receipt or any failure, and record the revocation and any hold privately. Do not put execution identities or pod names in this document.

Only after the selected release is actually served may the authorized operator run the live 1-reader and 5-reader certification in [the validation runbook](delivery-flow-read-validation.md) using private fixture/auth configuration. Keep core graph timing separate from activity enrichment; capture content correctness, browser agreement, cross-workspace denials, all sample denominators and failure-inclusive gate p95, plus manifest-owned cleanup readback. A missing token, incomplete cell, cleanup remnant or failed runtime observer is an explicit incomplete result, not a pass. Record the run, exact attempt, selected revisions, runtime evidence ID when genuine, per-gate results and remaining limits in the private operations receipt. Mark backend/runtime verified only with its own live evidence; frontend and latency have separate gates. Keep engine acceptance open unless the authorized coordinator supplies its independent evidence. If verification fails, diagnose the new failure and repeat a checked repair cycle within the accepted limits, or record the actual external hold.
