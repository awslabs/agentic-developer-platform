# Shared verification contract

All scenarios are planned, not reported passing. Each story's AC-01/02/03 maps to an equally numbered issue-local scenario. Implement tests beside the maintained component or under the proposed modules/domain-apps/superplane/tests/factory_architecture/test_<alias>.py; UI stories use the existing browser harness with equivalent proposed scenario names. The suggested path is a deliverable, not an existing command.

For source/contract tests use two isolated organizations/workspaces, versioned backend-derived API fixtures, fixed UTC clock where expiry matters, stable IDs/order, recording provider adapters and a disposable PostgreSQL database for transaction/lease/migration behavior. Expected IDs, counts, permission outcomes, digests, lifecycle transitions and survivor inventories come from the accepted contract/fixture; do not calculate the expected answer by calling the implementation under test. Synchronize failure injection at durable intent/provider-call/observation boundaries with explicit barriers. Await an observable terminal condition within a configured deadline; arbitrary sleeps are not the correctness oracle.

Each acceptance case states the action and decisive result in the issue. SCN-01 exercises the public/production entry point for success; SCN-02 exercises the stated refusal/failure boundary; SCN-03 exercises retry, restart, compatibility or cleanup. Include wrong-tenant authorization through the real producer/consumer path where it applies, not only a direct helper. If behavior spans API/worker/browser, fixtures must derive from the backend schema or a captured authorized response. An HTTP fixture browser pass does not establish provider acceptance.

Live operations use named, authorized run-owned fixtures, pinned artifacts, allowed profiles/regions, recorded cost/runtime limits, original provider request/resource IDs and independent provider/Kubernetes observations. Record every attempt and the exact requirements/source/release/target revisions. Unknown billing or resource exposure stays unknown; a missing/denied read never proves deletion. A seed cannot make provider availability or training results deterministic.

Cleanup belongs to each run, survives interruption and compares before/after inventories. Never close shared accounts, remove supplied networks/clusters or erase operation/evidence history. A failed cleanup or required blocked/not-run row leaves acceptance incomplete. No tests are required for prose-only edits beyond document/link/structure checks.

Gateway compatibility checks use actual serving replicas and scheduler and repeat if a concurrent rollout changes them. Preserve unrelated changes. Implementation tests use source fixtures; release tests use the exact built artifacts without source overlays. Three batches share this verification contract; they do not reuse historical pass claims for changed code.
