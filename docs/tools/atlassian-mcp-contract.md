## 1. Baseline and architectural choice

Today the private Jira mediator advertises only `get_issue`, uses the Jira REST adapter and binds one observed vendor user/site set to one ADP owner. The built-in Atlassian OAuth setup requires an app's client ID and secret and requests legacy `read:jira-work`, `read:me`, `offline_access`. This is not the v2 MCP scope model. Existing consent completion checks a stored attempt and connection snapshot; disconnect reports that remote revocation was not attempted. Preserve these paths while adding v2, not by relabeling their tokens. Sources: [Jira mediator][jira], [scope registry][scopes], [setup][setup], [consent completion][connections], [bindings][binding].

The CLI already writes `adp-tools` entries during both client setup commands. Main's setup replaces a same-named entry without a provenance check. [PR #8392](https://github.com/aws-e/adp/pull/8392), inspected at `21a0a2fdb06035eb8d5728e3014a1b2137eb8b72`, is **open/draft with no reviews** at inspection: its Claude session-scoped wiring and AWS-free login are reuse candidates, not merged/deployed dependencies. Codex still needs equivalent launch-time assurance and separate measurements. Sources: [CLI setup][cli], [MCP bridge][bridge].

```text
Claude or Codex
  -> installed ADP CLI stdio MCP bridge (ADP identity only)
  -> existing tools facade (operation IDs, receipts, recovery)
  -> ADP authorization + AgentCore Gateway + interceptor
  -> private shared tool-adapter service in EKS (separate image; core authorizes)
  -> Atlassian hosted MCP v2 (user access token retrieved from AgentCore Identity)
```

Use a separate `atlassian` target/namespace directed to the new shared adapter service. Reuse the existing [GitHub/Jira target pattern][targets] and [private transport/claims][transport], extending the edge to the adapter Service rather than the core gateway. The adapter retrieves the resolved user's token from AgentCore Identity only after a current core authorization decision. Preserve `jira___get_issue` and all existing connector names/bindings while migrating all four paths in one coordinated release. The [adapter contract](atlassian-mcp/adapter-service.md#core-to-adapter-contract) specifies IAM, observation/admission/dispatch, duplicate fencing and token handling; the existing facade remains the operation journal owner.

**Required OAuth architecture:** reuse AgentCore Identity's user federation and token vault. Start consent with `get_resource_oauth2_token`, bind completion through `complete_resource_token_auth`, and retrieve usable access tokens through Identity as the current implementation does. Identity owns the provider OAuth callback, code exchange, refresh-token storage and refresh/rotation. ADP owns its browser return/completion routes, session/tenant/user binding, selected site, permissions and connection status. The adapter may hold the returned access token transiently for a provider call; it must not persist user access/refresh tokens or implement direct provider code/refresh exchanges. The user still approves access on Atlassian's consent screen.

Inspect the built-in `AtlassianOauth2` provider and the existing `CustomOauth2` setup pattern in [oauth_setup.py][setup]. Select a separate MCP credential provider inside AgentCore Identity, pinning its configuration without changing the legacy provider. `CustomOauth2` means configuration of AWS-managed OAuth, not an ADP OAuth engine. #8446 must prove issuer/resource, PKCE, scope, callback/session, refresh and revocation behavior for the selected mode. Existing source proves the reuse path, not MCP v2 compatibility. If neither Identity configuration satisfies a required behavior, publish the exact incompatibility and block the affected implementation; do not silently switch to ADP-managed OAuth.

Maximize deployment-client automation within that Identity contract. Prefer server-hosted OAuth client metadata (CIMD) only if it works with Identity's provider configuration and issued OAuth callback. Evaluate dynamic client registration or a retained deployment app when needed, with exact automation/admin steps evidenced by #8446. An ADP return URL is not the provider OAuth callback. Registration modes are versioned deployment choices, not per-request fallbacks. Required manual app setup beyond the agreed policy-only admin journey is a product acceptance gap to resolve explicitly, never a reason to bypass Identity.

| API | Inputs / authority | Output and retry semantics |
|---|---|---|
| `GET /api/auth/connections/atlassian-mcp/status` | Current ADP human/tenant | Deployment readiness, own connection state, capability names, selected site display, stable reason/action; no secrets. |
| `POST /api/admin/connections/atlassian-mcp/prepare` | Platform admin; reviewed config revision only | Idempotent setup attempt/status; same config reuses the client; conflicts require deliberate replacement. |

| `POST /api/auth/connections/atlassian-mcp/start` | Current human; `capability_set: reads\|jira-writes`, optional reconnect revision | Opaque attempt ID and Identity-provided authorization URL; persist Identity session reference, state digest and owner. | `GET /api/auth/connections/atlassian-mcp/return` | Identity browser return | Redirect to fixed Connections result route; no code exchange or binding publication. Identity owns the separate provider OAuth callback. |
| `POST /api/auth/connections/atlassian-mcp/complete` | Current human and bound attempt | Validate owner/state/reconnect snapshot, complete the Identity session, request an owner-bound observation from the adapter, then publish metadata binding once. No token or session secret returned. |
| `POST /api/auth/connections/atlassian-mcp/select-site` | Current human; attempt/connection revision and observed site ID | Atomically select an accessible site, increment binding revision; unknown site rejected. |
| `DELETE /api/auth/connections/atlassian-mcp` | Current human; expected connection revision | Deny new calls first, return disconnected locally plus `revocation_pending` until provider proof. Repeating returns the same pending/terminal state. |

These are a versioned interface proposal; handlers belong alongside [existing connection routes][connections] and [admin setup routes][admin]. Mount them through [application router registration][app] and include new private routes in the [authority manifest][routes]. Keep existing `/atlassian` requests and response shapes intact. Before completing an Identity session, require the current ADP browser session to match the attempt's initiating human/tenant; otherwise require reauthentication as that owner and do not publish a binding. State possession alone cannot switch ADP owners. Normal users cannot call prepare or alter deployment config. Readiness separates `setup_required`, `ready`, `policy_blocked`, `unavailable`; metadata availability alone cannot assert that a particular organization allows consent.

#### Authentication, storage and cleanup procedure — AC-01

1. Pin source/config, run/owner, isolated Identity workload/credential-provider and ADP return identity in the private ledger. Fetch v2 resource/issuer metadata; verify TLS, issuer and S256. Test built-in/custom Identity configuration and select a mode only with actual support for required fields. Pin the Identity-issued OAuth callback separately from the ADP return URL and prove the registration mode, including retained identity and lost-acknowledgement recovery.
2. Establish the initiating ADP browser identity. Start consent via Identity user federation; complete its session through the probe's owner-bound completion listener. Reject changed owner, wrong state and replay. Record redacted SDK/config/session evidence for issuer, resource, PKCE and client authentication without reading refresh tokens. Any field not observable through supported evidence stays unproven. No later production route is required.
3. Retrieve access tokens only through Identity; use them transiently to initialize MCP and observe provider identity/sites, independently compared with fixture records. Prove token retrieval after probe restart and metadata-write/report failure. Assert no user access/refresh token was persisted in ADP SQL, Secrets Manager, run ledger or logs. Verify owner isolation and Identity vault/resource permissions; ADP metadata persistence is distinct from Identity's token store.
4. Exercise expiry, concurrent retrieval during Identity-managed refresh/rotation and lost SDK/completion replies. A later token retrieved from Identity must work without reconsent when the grant remains valid; invalid or unrecoverable sessions require reconnect, never a direct token-endpoint fallback. Deny locally before requesting a supported Identity-managed revocation/credential-removal operation. Pin the actual supported API and independently prove its provider effect, including refresh invalidation and access-token expiry/lag; do not invent an API or claim local/provider-configuration deletion revokes a user grant. Missing required revocation behavior blocks acceptance. Do not retrieve refresh tokens to perform that proof.
5. Revoke/remove only probe-owned grants, provider/workload configuration and setup secrets, using the proven lifecycle. Verify provider revocation or known expiry and owned-resource cleanup without deleting shared deployment resources. Retain incomplete cleanup in the ledger. Publish sanitized Identity/provider/fault evidence; no token values. Apply the section 4 request/retry bounds and record clock/fault order throughout.

## 3. Owner-bound state and storage — EC-02

Use existing relational vault records for owner/consent/binding metadata, AgentCore Identity's token vault for user credentials, and the existing tools DynamoDB journal for tool operations. Secrets Manager may retain deployment app secrets through [existing setup controls][setup]; it is not a second store for v2 user tokens. Do not persist tokens in ADP SQL, user secrets, evidence, CLI, browser storage, tool output, audit messages or Terraform state. Retain canonical ADP `tenant_id` in new interfaces/tables; existing SQL `org_id` remains the compatibility column. Resolve the current human from authenticated ADP identity; vendor account/site IDs never become ADP login identity.

The [135-migration ordered audit](atlassian-mcp/migrations.tsv) resolves the source head to `122_product_handoff_callbacks`. Relevant existing state is the merge of `004` vault creation, `007` ownership relaxation, `097` OAuth attempts, `109` requested scopes, `110` observed binding/one-use receipt and `111` reconnect snapshot/resources, plus later migrations in the ledger. [Models][models] and [secret helper][secrets] are the source of truth. Do not allocate migration numbers until rebasing on the then-current head.

**Implementation ownership:** #8447 delivers `oauth_setup_states` and `oauth_recovery_jobs`: additive migrations/models, transactional enqueue and leased claim/retry/retirement, the executable SQL consumer, and Identity provider/setup reconciliation and owned setup-cleanup handlers. Its AC-03 exercises that consumer against a migrated database with only Identity/provider transport substituted. Its new AC-04 supplies the separate adapter package/image/service foundation and shared wire contracts; it needs no successor user routes or protected deployment. #8448 consumes this foundation and adds core credential/binding/attempt metadata, authorization/dispatch routes and metadata/revocation recovery, plus adapter-side provider observations. Core SQL remains inaccessible to the adapter. Neither story builds a token store, OAuth code exchange or refresh worker. #8453 owns schedule/IAM/config rollout and live readiness, separate from each story's pre-review worker integration tests.

Proposed outbox fields: UUID job ID, `tenant_id`, owner/credential/setup reference, job kind/state, expected binding/grant generation, nonsecret evidence reference, attempt count, `due_at`, lease owner/expiry, last error category and terminal timestamp. Unique `(kind, owner reference, expected revision)` prevents duplicate scheduled effects. Claim due rows with transactional skip-locked leases; use a 45-second lease/tick, one-minute schedule, capped exponential backoff to 15 minutes, and an alert after 10 minutes overdue or five failed attempts. Alerts do not retire work. Unresolved work cannot expire away. Setup rows contain a unique deployment/provider-mode key, config digest, Identity provider/client reference, optional app-secret reference and phase. V2 attempts keep genuine Identity session references; never fabricate an AgentCore session. Readiness and retry behavior must follow the API semantics proven by #8446.

Retain deployment app-secret naming through [existing setup][setup] and [secret controls][secrets], using a distinct approved reference for any new MCP app configuration. Never overwrite legacy app secrets. User OAuth credentials remain in Identity's token vault; ADP stores only the owner-bound pointer and observed authorization metadata. Persist intent before Identity/setup effects and reconcile lost replies through supported reads; compare the initiating binding revision before publishing completion. A disconnect/reconnect racing adapter token retrieval invalidates the old authority: the adapter must obtain core dispatch authorization against the current owner/grant generation before provider dispatch. No ADP token-version compare-and-swap or secret staging is introduced.

Revalidate user membership, current consent/policy, binding revision, granted scopes and selected site **on every execution**, not just discovery. Observe identity/resources with tokens retrieved from Identity; cache only for the bounded discovery window. Serialize ADP's concurrent token requests per connection where needed; Identity owns refresh and rotation. A 401 permits at most one further Identity token retrieval before a safe read, only with #8446-proven semantics and within the operation deadline. It never permits a direct refresh call or blind write replay. Identity unavailability fails closed; a proven invalid/unrecoverable grant requires reconnect. Never use an admin or another user's token as fallback. On disconnect commit local denial/revision invalidation and a revoke job before acknowledging; already dispatched writes may finish and remain recoverable, but cannot authorize further work. Remote revocation remains pending until the supported Identity/provider effect or known expiry is verified; unsupported required semantics remain a release blocker.

Gateway runs the SQL consumer foundation from #8447, with user-lifecycle handlers from #8448, as a bounded scheduled job in its existing image/IRSA deployment. #8453 installs/verifies its schedule, IAM and alarms. Keep the facade reconciler for DynamoDB operation/report work; it has **no** Identity token-retrieval or vault-read permission. Core internal reconciliation endpoints accept the exact reconciler identity and operation ID, re-resolve stored owner, and authorize adapter-side observation/settlement only. The adapter owns vendor transport; the core owns metadata/revocation recovery and has no new vendor execution code. Both consumers use leased work, bounded retries and due-work age/failure alarms; acknowledgement/report loss cannot remove pending work. Current [facade cron][cron] runs every minute but [its consumer][reconciler] only knows existing cleanup families: this extension is real implementation work, not already available behavior.

`atlassianUserInfo`, `getAccessibleAtlassianResources`, and `listJiraIssueTransitions` are internal supporting reads, not generic execution or extra user-facing capabilities. Pin any additional project/type metadata reads that the four writes actually require. The initial read grant requests only the four product read/search groups plus provider-proven identity/offline scopes. Write opt-in adds only `write:jira:agent-interface`, and any necessary read scope must be explicit. Advertised scope availability is not observed granted consent. Exclude `discover`, `executeRead`, `executeWrite`, `executeDestructive`, delete/admin tools, non-page Confluence content expansion and Confluence writes from the ADP catalogue.

Initialize MCP with a contract-pinned mutually supported protocol version, then use Streamable HTTP; refuse an unsupported negotiation. Paginate every upstream `tools/list` page before declaring a catalogue usable. Stage and validate a complete set, detect cursor loops and duplicate/conflicting names, validate JSON Schemas, then atomically publish its digest. Unknown upstream tools remain unadvertised until classified in a reviewed allowlist. A changed input contract invalidates the pinned mapping. Reads may tolerate changes to string `description` annotations at recognized JSON Schema locations only after verifying the stored schema against its reviewed digest; clients continue receiving that reviewed schema. Types, required fields, constraints, defaults, literal values, extensions and properties named `description` remain exact. Shared service-account reads apply the same comparison to their signed connection schemas. Write and identity-observation schema pins remain exact. No silent best-effort truncation or invented schema is allowed. Page result pagination remains separate from catalogue pagination.

Proposed admission bounds, owned by #8446 and tested by #8449: 20-second aggregate upstream work budget within the bridge's current 30-second HTTP timeout, 2-second connect, at most 5 seconds per read, 32 catalogue pages, 1,024 tool definitions, 256 KiB per definition and 4 MiB total catalogue. Respect the earliest signed assertion/operation deadline. If a complete catalogue cannot fit, return `catalogue_incomplete` and require an explicitly reviewed bound change; do not present a partial list as complete. Cache full discovery for at most 60 seconds under `(deployment, tenant, human, provider subject, selected site, connection revision, granted scopes digest, schema revision)`. Authorization always rechecks fresh state. Never extend a deadline on retry. Normal [facade discovery][facade] currently stops after five pages and checks duplicates; update that bound/receipt flow end to end, not only in the new mediator.

Reads permit at most one retry for 429/temporary unavailability if `Retry-After` fits the remaining deadline; one Identity token retrieval for managed refresh is separately coordinated and still fits the same aggregate budget. Writes permit **zero automatic retries after dispatch**, including HTTP 401, 429 and timeout, unless absence of an effect is conclusively established and a new explicit operation is admitted. Oversized responses fail safely; no tokens/secret sentinels may appear in returned diagnostics.

| Condition | Stable ADP outcome | Effect / next action |
|---|---|---|
| Missing or expired ADP login | `login_required` | No provider request; run ADP login, not AWS refresh. |
| Missing/stale v2 binding or invalid refresh grant | `reconnect_required` / `connection_changed` | No credential substitution; user reconnects. |
| Consent/policy/site denial | `scope_not_granted` / `site_denied` / `approval_required` | Zero unauthorized effect; filter corresponding schemas during discovery. |
| Provider 401 / 403 / 404 | `provider_unauthorized` / `provider_forbidden` / `not_found` | Preserve distinction without revealing another owner's resource existence. |
| 429 / timeout / MCP `isError` | `rate_limited` / `provider_unavailable` / structured provider failure | Empty search is successful only on a valid empty result. Uncertain write is `outcome_unknown`. |
| Repeated operation ID with changed arguments | `operation_conflict` | Never dispatch changed payload. |

Update [authorization][authorize], [effective policy][policy], [dynamic catalogue validation][catalogue], [interceptor allowlists][interceptor], [route registration][app], [private authority manifest][routes], private target/edge route and configuration renderers together. The current allowlists explicitly name `knowledge`, `github`, `jira`, `slack`; a new file alone is unreachable. Carry tenant/human, team where applicable, Task/run, connection revision, provider subject, selected site, required scope set, operation ID, payload digest, target/schema revision and expiry in trusted claims. The adapter submits the signed context to core authorization, which compares it with current records before allowing Identity retrieval and rechecks before dispatch. Workload callers must resolve the original human through existing Task authority; this epic does not introduce machine Atlassian grants or require worker/scaledjob direct secret access.

## 5. Approved writes and durable outcomes — EC-04

Existing [execution storage][execution] provides operation keys, conditional admission and recovery helpers; it does not already qualify these eight new tools. Extend it rather than add a competing write log. Before provider dispatch, persist the exact tool/input digest, owner/site/binding and approval decision/version with an operation ID. The approval is bound to exact normalized arguments and operation, not merely a tool name. Execute only the intersection of enabled product capability, current entitlement, Task grant if present, user consent, site authority and existing approval policy. No new dollar ceiling or blanket write grant is introduced.

State machine: `prepared -> dispatched -> confirmed | failed_no_effect | outcome_unknown`. Reporting and cleanup have independent pending/terminal fields. An idempotent same-ID repeat returns the persisted result/status; changed arguments or owner fail. A crash after dispatch but before reporting leaves `outcome_unknown`; it is not equivalent to `failed_no_effect`. Mark dispatch durably before sending. If the process dies in that narrow window before actually sending, conservative unknown is acceptable; a second automatic write is not.

Use upstream idempotency only where #8446 demonstrates its exact semantics. Do not assume Jira MCP accepts an idempotency key. Reconcile via returned provider IDs, exact field/version/history/comment evidence or an agreed fixture marker. A matching issue title or an eventually consistent empty search is not proof of uniqueness/absence. If no conclusive oracle exists, retain unknown with owner and next action. The `operation_retry` helper must refuse uncertain Atlassian mutations; a new user-approved operation is a separate choice, not disguised replay. Disconnect blocks new work but original owners retain narrowly scoped status/receipt access and authorized settlement.

The facade persists provider outcome before returning success, and persists pending gateway usage/audit reporting independently. Its scheduled consumer repairs reporting using the same receipt, including success acknowledgement followed by report failure and a failed first repair after restart. The core authorizes provider readback using recorded ownership and the adapter executes it; lack of permission after revoke yields unresolved settlement, not broader credentials. Fixture cleanup is acceptance-harness work using a separate consenting fixture-owner identity, never an advertised delete tool. Live unknowns/orphans keep EC-04 incomplete.

## 7. Release ordering, verification and rollback — EC-06

#8453 extends existing [release-scope][release-scope], [orchestrator][orchestrator], platform guard and receipt mechanisms with an independently selectable `tool-adapters` image/build/deploy stage. **No new standalone workflow is proposed.** Adapter-only changes must not rebuild or roll out the core gateway or facade. Shared-contract changes still select their actual consumers. The [adapter release/migration contract](atlassian-mcp/adapter-service.md#independent-release-and-migration) and [entry-point audit](atlassian-mcp/audit.md#deployment-and-build-entry-points) cover ECR/build roles, IRSA, private edge/ALB routing, service health, route generation and image/SBOM evidence. Extend orchestration with explicit readiness ordering; a core deployment alone cannot deploy the adapter.

1. **Prepare the release manifest.** Pin design/proof/schema, wire contract, workflow, core/facade/interceptor and adapter image digests, migration head, UI/CLI assets, Identity mode/config, private edge destinations, group activation generation, per-connector backend generation and previous rollback artifacts. Keep target identities private; the canonical [deployment guide](../adp-platform-deployment/deploy-with-agent.md) governs actual deployment authority.
2. **Publish control-plane prerequisites.** Apply additive core metadata migrations, scoped IAM/config and tested setup/revocation recovery. Core-deploy publishes core APIs and served CLI only. Keep new routes/capabilities disabled until the adapter contract is compatible.
3. **Deploy the separate adapter service.** Extend existing tools-platform stages to build/publish the adapter image and reconcile its separate EKS Service/Deployment, service account, network policy, resources, probes and drain settings. Reuse the tools launcher for fresh installs. Verify the running digest/SBOM and effective authority. Publish compatible facade/interceptor changes where selected; do not couple an adapter-only release to a core rebuild.
4. **Prepare private routing and targets.** Add the adapter backend to the existing private edge/ALB with exact per-route callers and service-specific provenance. Prepare all four mappings without switching active legacy routes; the new `atlassian` target is adapter-only. Preserve Door's route. Qualify actual candidate destinations, schemas and wire revisions with owned fixtures before handoff; changing an endpoint string without changing its backend is insufficient.
5. **Hand off all four connectors together.** Publish compatible UI/CLI and pass Atlassian and existing-verb parity checks before the coordinated release. No scheduled maintenance window is required. Under a durable release lease, fence new group admission, drain or retain attributable in-flight work, apply mappings and read back every destination/readiness before reopening on the new generation. AWS updates are not atomic: record partial progress and restore the previous group manifest on failure. Fresh calls can receive bounded retryable unavailability during the handoff; no duplicate shadow writes or automatic backend fallback. The [migration procedure](atlassian-mcp/adapter-service.md#independent-release-and-migration) defines interrupted-release recovery, original operation generations and rollback retention.
6. **Verify release and failure isolation.** Extend the existing live evaluator with independent adapter route/digest evidence, both client matrices, all four connectors, pod failures, partial route apply, controller restart and group rollback. Record core/adapter image bytes, dependency inventories and memory/startup measurements. A required blocked/not-run row remains incomplete; a successful workflow is not live acceptance.

The tools-platform **release** job only runs on `workflow_dispatch`, `refs/heads/main`, first run attempt, non-drift mode; use `mode=release`. Push may run guards; schedule/drift success is not deployment. The engine uses `adp_correlation`, `adp_source_revision`, `adp_definition_revision`; the workflow guard checks source ancestry and workflow content. Manual dispatch instead supplies `manual_source_revision` and **must not mix engine fields**. Source: [workflow][platform-workflow] and [dispatch guard][dispatch-guard].

For an already authorized operator, the existing manual surface is the following. `REVIEWED_MAIN_SHA` is an environment variable containing an approved 40-character main-history commit; it is not a literal value. **Rollback:** fence the four-connector group, preserve original operation/backend generations and drain or retain accountable in-flight work. Initial rollback disables new Atlassian MCP and restores legacy routes; never substitute legacy Jira tokens for MCP. Keep generation-specific reconciliation, core metadata/revocation and facade reporting consumers; keep unrelated runtimes and core login/model APIs available. Record rollback retention; inactive core compatibility handlers receive no new features and their later removal is separate cleanup. Partial restoration stays fenced with durable recovery progress. Verify all destinations, existing behavior and pending operations/revokes.
