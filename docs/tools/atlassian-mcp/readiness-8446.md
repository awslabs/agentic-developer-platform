# Atlassian MCP standalone proof handoff

This is a controlled-development handoff, not provider activation or deployed acceptance. The standalone AgentCore Identity probe runs without later production connection routes. Its generated cases can qualify the probe and provisional contract for downstream development; they cannot show that an actual account completed consent, that Identity refreshed or revoked a grant, or that Atlassian exposed the required schemas. Do not relabel legacy Jira OAuth or a direct OAuth prototype as this proof.

The machine-readable [readiness matrix](readiness-8446.json) pins each of AC-01–03 to its separate SCN-01–03 procedure and names the producer, consumer, fixture owner and pending activation evidence. It follows the proposed design at `3454ce6b73d7a263e4e90979d6eaa49f5896d098`; the design review merged in PR #8464 at `5e0d7e5551faaac1427fba1903d7c63492f9c76c`. [Provisional operation names and policy](required-operations.json) are not observed input schemas. Each generated report must carry the actual evaluated source revision, design revision and phase; a generated pass never changes a live status to pass.

- The proof owner generates local Identity/provider fault cases and runs an isolated core/adapter-role probe; no successor service or human-prepared dataset is a prerequisite for those controlled cases.
- The integration lead and authorized target operator supply private isolated roles, a return host and release configuration; the account owner gives actual consent, and a provider policy admin participates only if needed. None of that access or consent has been verified by these generated tests.
- Story #8447 must deliver provider setup **and its working recovery consumer** before #8448 implements user lifecycle against it. Story #8449 consumes the owner-bound authorization contract and must pin authenticated read schemas; #8450 adds independently approved writes. Their production integration tests are not accepted by this probe.
- Story #8452 qualifies actual installed clients; #8453 owns the fenced coordinated release; #8454 and the epic integration lead verify live end-to-end provider effects and cleanup. Real consent, Identity-managed refresh, revocation and catalogue schemas remain activation blockers until independent evidence is attached.

Before forwarding a controlled report, compare its immutable source and design revisions with the reviewed implementation, check the exact case statuses and missing evidence, and keep the live rows unproven. The protected phase producer and reader are implemented on the branch; the existing accepted graph has not selected them, and no live target run has been observed.

The Gateway release's controlled `stage.identity-proof` job runs the three generated proof procedures and regression fixtures on the reviewed source bytes. It records the selected source, workflow definition and gateway revision, plus the operation contract and readiness digests, in a private versioned phase report. Its independent reader downloads and checks the private artifact against the selected revisions, run and passing JUnit cases. A successful controlled report is only a **candidate**: it always retains `live_status: unproven` and cannot satisfy live provider acceptance. This phase neither imports a user session nor deploys a successor service. The required authenticated consent, refresh, revocation, cleanup and tool catalogue checks remain with the authorized target owners.
The isolated probe also exposes an authenticated ADP return listener at its configured HTTPS return path. It uses the existing JWT validation and a fresh workspace-membership lookup, records only the initiating user and tenant in the private attempt ledger, and passes the stored Identity session to the SDK only after matching the bound state. Unauthenticated browser redirects do not complete consent: an authorized caller must present an ADP bearer session to the return endpoint (or submit the returned state by authenticated POST). No OAuth code, caller-supplied session reference or token is exchanged by ADP. The probe now names the exact MCP v2 resource in both SDK token requests; the installed botocore request model accepts that field, but actual resource issuance, PKCE and browser/Identity behavior still require live validation.


### Protected release and proof ordering

The currently accepted gateway-backend operation has one workflow, `gateway-deploy.yml`, **without** `proof_phase`. It can release the support code, but it does **not** select or run this controlled proof. The earlier standalone tools-evaluation binding is not a compatible substitution: the packaged Gateway target authorizes `gateway-deploy.yml`, and adding `tools-live-evaluation.yml` to the same operations grant would exceed the single-workflow release contract.

After the support code and reviewed workflow definition are merged and installed, the supervisor must arrange an authorized, accepted plan version and a new eligible deployment attempt whose existing gateway-backend `operational_release_binding` retains the already reviewed `target` field (do not replace its private value), `component: gateway-backend`, `repository: aws-e/adp`, `default_branch: main`, and **`workflows: [gateway-deploy.yml]`**, and adds **`proof_phase: stage.identity-proof`**. Keep the existing verified-merge predecessors, build prerequisites, connection policy, `deployment_workflow:gateway-deploy.yml` required input and `runtime_verified:gateway-backend` expectation. Review/pin the changed `gateway-deploy.yml` definition through the supported definition-predecessor/manifest mechanism; the source must include the probe, fixtures, provisional contract and phase reporter, and be an ancestor with identical proof bytes. Do not rewrite an active attempt or change an already accepted binding in place. Existing deployment authority and target approvals still apply.

Only that amended release grant causes the Gateway dispatch to supply the proof selector. The workflow first releases the backend, then runs the generated phase job **only when the backend succeeds**; it publishes a private report and independently reads it back using the runner's scoped identity. The Gateway's selected source SHA is also the phase's gateway revision; the reviewed workflow SHA is checked separately. A report without the amended accepted operation is not evidence that the accepted graph ran the proof. No external Identity/provider lifecycle or authenticated catalogue result is asserted by this controlled artifact.

### Native evaluator handoff (candidate only)

The generated cleanup case records the final ledger phase, remaining fixture resources and uncertainty flag in its private JUnit properties. The phase reader requires verified resource absence and no uncertainty before emitting an empty unresolved-operations list. The summary identifies generated fixtures and matches their source to the selected release; the native deployment receipt remains the authority for installed runtime verification.

The native repository evaluator no longer depends on GitHub Actions artifact storage for this phase. The reviewed, maintainer-owned signed transport `ADP_IDENTITY_PROOF_EVIDENCE_STORE: s3-oidc-v1` carries the bounded summary, and the native reader (`EvidenceStore.read_archive`) authenticates the signed descriptor before fetching that exact archive object version. The *same* Gateway release workflow runs its backend first, then the controlled `identity-proof` job (`contents: read`, `id-token: write`, protected environment `adp-gateway-deploy-dev`), and only when `deploy-backend` succeeded on `main` with `proof_phase: stage.identity-proof`, `environment: dev` and `product_cases: none`. That job retains the complete private evidence as `atlassian-identity-proof-<run>-<attempt>` in the private CI evidence bucket with 14-day retention, then independently reads it back under the preserved scoped runner identity, checking the manifest version, content checksum, archive digest, declared file set and that the stored `evidence.json` equals the phase report recomputed from the retained `junit.xml`. Only after that private readback succeeds is the narrowly selected, sanitized `atlassian-stage-summary.json` staged and published through the signed path: `publish-deployment-evidence.py repository-artifact identity-proof` packs it write-once (`--if-none-match "*"`, SSE-AES256, versioned) and signs a bounded descriptor (bucket, key, version id, sha256, size, component, workflow path, workflow and source revisions) with a GitHub OIDC token whose audience is the exact descriptor digest and whose claims bind repository, repository id, run id, run attempt and workflow revision, at `deployment-evidence/v1/<repository_id>/<run>/<attempt>/repository-artifact/identity-proof.json`. The publisher refuses to sign unless the workflow ref is the maintained `main` `gateway-deploy.yml`, the event is `workflow_dispatch`, `PROOF_PHASE` is `stage.identity-proof`, `ENVIRONMENT` is `dev`, `GATEWAY_REVISION` equals the 40-hex `EXPECTED_SOURCE_REVISION`, the checkout equals `ADP_WORKFLOW_REVISION`, the selected source is an ancestor of that definition, and the payload file is exactly `atlassian-stage-summary.json`. The logical artifact name `atlassian-stage-<run>-<attempt>`, its `atlassian-stage-summary.json` path and every summary predicate are unchanged; only the transport moved, so GitHub artifact storage quota can no longer fail the publication step as it did on the earlier attempt. The raw JUnit, provider data, account, role, token and S3 coordinates remain private. The private reader requires the generated owned-resource cleanup testcase as well as the three scenario cases; the public summary labels only that generated cleanup verified, keeps remote grant revocation unproven, and pins the issue and scenario associated with each criterion. Runtime release verification comes from the native deployment predecessor, not a claim in the summary. A failed or missing readback produces no public summary.

The proof's selected revisions advance only through a native checked repair merge. The gateway supplies the correlation, `adp_source_revision` (also the gateway revision) and `adp_definition_revision` from the accepted operation; the job then requires `SOURCE_REVISION == GATEWAY_REVISION`, `GITHUB_SHA == github.workflow_sha == DEFINITION_REVISION ==` the checked-out `HEAD`, the source to be an ancestor of that definition, and byte-identical proof sources across `tests/e2e/tools/atlassian_*`, `tests/e2e/tools/test_atlassian_*`, `docs/tools/atlassian-mcp/` and `.github/workflows/gateway-deploy.yml`. A repair therefore keeps the reviewed pins untouched and lets a merged `main` head advance them; no worker may edit a pin, supply a dispatch input reserved to the accepted binding, or change workflow authority to make a stale source look current. Cleanup remains `generated_only`: the generated owned-resource case is verified, while remote grant revocation, real account consent, Identity-managed refresh and authenticated catalogue schemas stay unproven and remain activation blockers until independent live evidence is attached.

[The candidate operation amendment](operation-amendment-8446.json) selects this phase within the existing `gateway-deploy.yml` allowlist; it does not change an accepted attempt or authorize a new target.
