# Product service workspace

All five L5 services use the same navigation: **Setup → Capabilities → Runs & schedules → Results**.
The sections stay mounted while the user navigates so draft edits and pending operation receipts survive.
The shared components live in `modules/gateway/frontend/src/pages/products/services/L5ServiceJourney.tsx`.

The Product overview shows five service choices: **Security, DevOps, FinOps, Transform and Well-Architected**.
The **Services** tab opens the same chooser. Each choice has a direct URL within the current Product and delivery scope;
changing scope retains the selected service and reads that scope's configuration. Profile completeness does not hide the choices.
Opening the chooser does not load service configurations or start work. Opening a service keeps its own access, setup,
capability availability and execution checks. Profile-sharing status appears separately under **Profile setup → Product profile sharing**
and does not describe the availability of every service.

## What each section means

- **Setup:** the saved Product-profile revision, actual inherited values and source revisions, explicit service overrides, required connections, and provider setup/readback. A saved draft does not establish native readiness.
- **Capabilities:** understandable descriptions and service-specific prerequisites. Product configuration options express eligibility, not installed execution or permission to run. Unsupported execution paths say **Not available yet** and have no enabled launch control.
- **Runs & schedules:** explicit execution against saved configuration, retained operation receipts and run history. A navigation click never launches work. Schedule editing availability is separate from backend schedule support.
- **Results:** observed outputs, coverage, findings and retained evidence. Accepted work and completed work remain distinct; unavailable or partial evidence is not presented as success.

## Verified backend contracts

| Service | Capabilities and setup | Availability boundaries |
| --- | --- | --- |
| Security | Threat modeling uses pinned documents and a selected native model; code scanning uses pinned repository commits. Both need registered source bucket/role, AWS connection/region, limits, triggers and current owner authorization. | Pen testing has no admitted capability. Daily UTC schedules exist for threat modeling and code scanning, use pinned revisions and require current consent. Initial source registration has no public L5 mutation API and still requires an authorized operator. Existing model selection and owner consent are exposed in Setup. |
| DevOps | Bounded manual investigation uses a verified native space, selected environment/resources and current authorization. Creation or adoption starts with a disabled Investigation draft and explicit setup-only consent for that saved selection. Adoption reads and links the exact existing space and preserves customer ownership. Setup also exposes separate resource consent, verification of one Lambda/log group, verified-reference readback and bounded manual activation; execution consent follows for the new revision. | Release-readiness execution and prevention controls exist, but current configuration activation only supports Investigation. New release-readiness runs and prevention enable/resume remain unavailable. Release verification also lacks an installed executor and test-profile reader. Keep historical outputs and authorized pause controls. |
| FinOps | Cost inquiry uses an existing qualified agent, explicit account IDs, billing view/data role, connection, region, limits and current authorization. | The installed runtime contract only adopts existing agents; creation and scheduled inquiries are unavailable. Cost inquiries also remain **Not available yet** while backend admission is disabled or its availability has not been confirmed; an existing ready binding cannot override this deployment gate. Monthly-template helpers do not establish an installed scheduler: periodic dispatch excludes FinOps and admission requires a human/manual trigger. Neither a cost inquiry capability selection nor an enabled admission flag establishes an installed worker, qualified provider or billing scope. Setup adoption remains separate so an operator can qualify an existing agent before enabling inquiries. |
| Transform | Refactor and dependency upgrade use an immutable repository commit, scoped paths, typed goal, existing linked binding, qualified executor and test policy. Dependency upgrades require a target type (dependency or runtime), name and requested version; switching to refactor removes that target. | Scheduled runs are not available yet: configuration writes persist `needs_input`, while schedule freeze/admission require stored `ready`; no public transition resolves that mismatch. A schedule editor alone would not unlock execution. New binding setup is also unavailable: the installed Transform worker does not wire a setup authority. Manual runs require an already linked and qualified binding; saving executor/test-policy references does not create or qualify it. |
| Well-Architected | Source-only architecture review uses pinned documents/code, selected pillars, connection/region, execution role, source store and qualified provider. Setup validates the explicit role and bucket, displays their pinned references and saves enablement only on an explicit save. | Resource inspection is unsupported. Daily UTC schedules can be created paused, edited or explicitly enabled. Advanced saved schedules can be paused without rewriting their expressions. Existing triggers and settings are preserved during setup edits. |

Source references: `configuration_population.py`, `configuration_readiness.py`, `run_input.py`, the service `runtime_*.py` modules, `devops/test_profiles.py`, `devops/prevention.py`, and Gateway `l5_*_schedule.py` / `l5_integration.py`.

The capability catalog must change together with executable backend contracts. Do not enable an action just because its name exists in a schema, Product selection or retained binding. Do not hide a missing frontend editor by claiming that the backend feature is absent.

Security configuration checks are local and do not contact the provider. Binding `check`, `update` and `resume` are provider operations: they can initialize the first threat model in an ADP-created space under current authorization. The existing-model selector takes an explicit model ID and creation-time revision, derives scope from the current binding and submits `native_model_ref` with the binding ETag and retained request key. It only accepts an existing scoped model. The UI discloses this difference before those controls.

The shared Owner consent panel reads the saved scope and current grants only on an explicit user action. It shows the owner, binding generation, capabilities, operations, source revisions and expiry before an explicit grant. Every new grant needs a matching saved owner identity, configuration ETag, scope digest, retained idempotency key and owner-reviewed expiry of more than one minute and at most 24 hours. It never renews consent automatically. Unconfirmed requests remain in owner-scoped session storage and must be reconciled through current grant readback or an explicitly reviewed replay of the original request. Revocation is separate from starting setup or a run.

Well-Architected provider validation contacts AWS to read only the explicitly entered role and source bucket. It does not provision resources or establish native qualification. Changing the connection, region, resources, sources or pillars invalidates the validation. Failed configuration refreshes and uncertain saves preserve drafts and retained results but block further writes and setup/run actions until a fresh configuration read succeeds.

Existing Well-Architected bindings, including blocked bindings, expose a separate **Read current binding → Check binding** recovery path. The read validates configuration, connection and relationship scope and obtains the current binding ETag. Check uses the saved configuration revision and retains its original request key, body and ETag in the current owner's session before dispatch. Original operation action, state and gaps remain visible; status readback refreshes binding/run state and invalidates prior run readiness. An uncertain dispatch cannot start a replacement check: an explicitly reviewed replay uses the original request unchanged, and a changed configuration revision requires operator reconciliation of that original key. Check does not grant consent or automatically resume, update or start a review. Binding update/resume are backend-supported operations without a current UI editor; initial source-only setup is also supported by the backend.

Security Setup exposes the documented per-assessment limits and an existing scoped budget-policy reference. Editing these limits does not create or increase the underlying budget. Product refresh is separate from reloading saved settings: read the current Product, review its revision and inherited values, then explicitly apply that revision using the saved configuration ETag. Explicit overrides remain intact and newly added sources require separate selection. Unsaved edits prevent Profile application; an uncertain refresh or save blocks further writes until current configuration readback.

Well-Architected schedules use every saved source reference in its saved order, a current ready binding and an explicit review of the scope. Schedule writes do not submit unsaved Setup edits. Editing or pausing retains trigger identity and history; an uncertain creation is reconciled against the refreshed trigger identity before another edit. Current provider validation still applies to configuration writes, including pause requests, so stale or inaccessible provider resources can prevent a schedule save.

DevOps adoption uses the saved existing-space ID and hosting-connection revision in both reviewed consent and the subsequent link request. Its grant permits only `binding:link` and `credential:session`, without execution or native UI authority. Creation retains its separate `binding:create` scope. Setup dispatch does not use unsaved form edits. Before either operation is sent, its exact request, receipt and saved configuration identity are retained in session storage scoped to the owner, tenant, Product, project and configuration. Reload restores the original request without submitting it. An uncertain outcome permits only explicit continuation with the same receipt after current readback succeeds; a changed configuration or target blocks replay. A confirmed operation remains available for status inspection and cannot start duplicate setup. Missing owner identity, unreadable or malformed retained data, and failed retention block new setup. A later authorization rejection during replay cannot clear uncertainty about the first request. Consent requests remain in owner-scoped session storage. Setup never silently switches adoption to creation.

DevOps resource verification discloses its native association operation before explicit consent. It accepts a created binding or the exact customer-linked binding selected by the saved adoption draft. It retains original request keys, expiry and ETags in the owner's session and keeps verification separate from activation. Activation uses the verified resource references, a current access policy, one environment and an existing hard organization budget policy. A revisioned budget-policy picker is not available, so its reference is entered explicitly. Local setup drafts remain visible after activation and require reviewed refresh before further edits.

DevOps native inspection has separate **Native UI owner consent** in Setup after binding readback. The Product owner reviews the exact hosting account, native space, current configuration/binding, distinct launcher and operator roles, and an explicit expiry. This grant can coexist with Investigation or setup consent and cannot authorize agent execution. In Runs, **Check native UI access** reads current ADP authority and the provider's exact IAM operator-app configuration without opening a browser. Its result expires within one minute; **Open native DevOps UI** rechecks authority before and after the provider handoff. Neither action records a native arrival automatically.

Launcher authority is restricted to the selected space and ends at the earliest of the ADP session expiry, consent expiry or 15 minutes. Shorter ADP sessions remain supported. This bound does not define the duration of a native operator-app session; existing operator-role permissions determine actions inside that app. Revocation blocks new ADP handoffs under the revoked grant, while already-issued handoffs and native sessions may remain usable until provider expiry. The scoped native deep link still requires human qualification; offline tests do not establish arrival or live acceptance.

DevOps Investigation has an explicit readiness check against the current saved configuration, binding and owner consent. Its snapshot expires within one minute; submission checks authority and budget again. Native resource observations do not establish execution readiness. Prevention status is read only for a configuration that includes Prevention, and failure of that optional read does not remove valid Investigation access.

DevOps Investigation accepts a normal question field with explicit reuse of the exact saved resource and telemetry scope; advanced JSON remains available. Known admission gaps for consent, connection, budget or runtime availability preserve the draft and explain the next action. Security likewise requires an explicit current configuration-readiness check and an exact identity reread; its snapshot expires within 60 seconds. Binding/provider observations alone do not establish current execution authorization.

Security full-repository preparation appears as progress before run admission. A `source_capture_preparing` response keeps the exact original submission and receipt, with automatic checks for code review bounded to ten minutes. Changing sources, configuration or scope stops those checks; leaving the page does not cancel server preparation. The original request remains available for explicit continuation and prevents a replacement submission. Receipts survive reload in the current owner's scoped session storage when the saved configuration includes its owner identity; otherwise they remain in memory. Checked retry requests also retain their original run, reason and receipt. Terminal capture errors give fixed recovery guidance and keep the receipt because a run may already have been admitted despite a lost response. Refresh run history before any further recovery.

Ordinary schedule occurrences rejected before run creation still need a scoped backend status API; run history alone cannot explain those rejected ticks. Advanced Well-Architected cron expressions can be preserved and paused, but editing them remains outside the daily editor.

## Verification and remaining acceptance

Component tests cover current FinOps/Well-Architected readiness, canonical Security source matching, preserved DevOps activation and setup consent guidance, all four sections, draft persistence, scope revocation, receipts/ETags, unsupported capabilities, and Security's real registration/model readiness format. Production compilation is required. These checks do not replace human review of the served UI or real service acceptance.

Provider qualification, genuine assessment/inquiry outputs, consent renewal, source refresh, scheduling observations and final delivery-flow evaluations remain separate work. This UI change does not complete those tasks or change existing grants, budgets, flow attempts, schedules or task-board statuses.
