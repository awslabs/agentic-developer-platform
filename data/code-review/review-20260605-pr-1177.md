## Findings (by confidence)

### HIGH — merge blockers

None.

### MEDIUM — discuss before merge

- **DynamoDB gateway endpoint uses only private route tables**: The S3 endpoint (line 291) uses `concat([aws_route_table.public.id], aws_route_table.private[*].id)` but the DynamoDB endpoint (line 432) uses only `aws_route_table.private[*].id`. This is likely correct (agent pods run only in private subnets), but means any future public-subnet resource needing DynamoDB won't route through the endpoint. Acceptable for the stated use case.

- **VPC endpoint SG has no explicit egress rule**: AWS creates a default allow-all egress rule on the SG. For VPC endpoint ENIs (which only receive traffic from clients), this is standard practice and not a security concern — documenting for completeness.

### LOW — follow-up candidates

- **Existing ECR endpoints use `aws_security_group.eks.id` directly** (lines 303, 316) while new endpoints use the dedicated `aws_security_group.vpc_endpoints.id`. This is a deliberate improvement (least privilege via dedicated SG), but creates an inconsistency. Consider migrating ECR endpoints to the new SG in a follow-up.

- **New outputs for S3 endpoint** (`vpc_endpoint_s3_id` at outputs.tf line 94-97) was added even though S3 was pre-existing and not part of this PR's scope. Harmless but unnecessary — not a blocker.
