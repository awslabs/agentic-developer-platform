## Findings (by confidence)

### HIGH - merge blockers
None.

### MEDIUM - discuss before merge

1. **Gremlin injection via single-quote escape only** (`graph.py:158-159,205-206`): The `esc()` function only replaces single quotes with `\'`. While `owner_sub` is validated as a strict UUID regex (identity.py:24-27) and `entry_id` is a ULID (no special chars), the `tenant_id` field has minimal validation ("non-empty", identity.py:84-85) — if a tenant_id ever contains backslashes followed by single-quotes, the escaping could be bypassed. However, this is the **same pattern used by `ingest-repo.py`** (line 840: `str(v).replace(chr(39), chr(92)+chr(39))`), so it's consistent with codebase conventions. The practical risk is LOW because:
   - `owner_sub` is strictly UUID-validated (hex + dashes only)
   - `entry_id` is a ULID (alphanumeric only)
   - `tenant_id` is set by the trusted dispatch layer, not by end-user input
   - The safer `ingest-doc.py` parameterized-binding pattern exists but requires the `gremlinpython` WebSocket client (different transport)
   - **Recommendation**: File a follow-up issue to migrate Neptune HTTP clients to parameterized queries long-term. Not a blocker for this PR.

2. **`verify=False` on HTTPS requests** (`graph.py:95`): TLS certificate verification is disabled. This matches the established pattern in `ingest-repo.py` (lines 818, 856, 886) — Neptune Serverless uses AWS-managed certs that may not chain to the system CA store in some container runtimes. Consistent with codebase convention.

### LOW - follow-up candidates

1. **`max_hops` parameter unused** (`graph.py:255`): The `max_hops` parameter is capped at 2 but the query always does a 1-hop traversal (`bothE().otherV()`). The multi-hop logic isn't implemented. This is fine for the current spec ("1-hop graph neighborhood") but the parameter suggests future multi-hop support — consider removing the unused parameter or documenting it as reserved.

2. **Edge property values not type-validated** (`graph.py:210-212`): The `properties` dict in `add_edge()` converts values to string via `str(v)` but doesn't validate key names (e.g., keys with single-quotes could theoretically inject). Low risk since this is only called internally with hardcoded keys like "transfer_context".

## Recommendation
**APPROVE** - All acceptance criteria are satisfied. The 2 MEDIUM findings are pre-existing patterns in the codebase (not introduced by this PR) and don't constitute merge blockers. Tests are comprehensive (30 new tests covering all validation criteria), lint is clean, and no regressions.
