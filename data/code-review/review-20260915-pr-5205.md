## Summary in plain terms

The pause machinery in this branch is genuinely good work. The barrier is
harness-neutral, it never interrupts the model, resume really is the same
execution, and the unit suite around it is unusually thorough. Two things stop it
from being mergeable as the S2 story:

1. **The story's own deliverables are not all here.** Pause is still switched off
   on all four surfaces the story owns, the mandatory real-SDK experiment file was
   never written, and the wave-2 evaluation checks the story owns are untouched.
   The author documented *why* pause stays off, and that reasoning is sound and
   valuable — but the story cannot be accepted as done while its acceptance
   evidence does not exist.
2. **Two state-reporting defects survive inside the barrier itself** — the exact
   class of bug this story exists to prevent (an operator being told a run is
   paused, or pausing, when it is not). Both are reproducible today. Because the
   verbs are disabled they are latent rather than live, but they are latent *in the
   code this story is asking to have accepted as proven*.

## Merge blockers

### B1 — Pause/resume are still disabled on all four surfaces S2 owns
**Impact: high · Confidence: high · Approval impact: blocking**

| Surface | Line | State |
|---|---|---|
| Gateway allowlist | `modules/gateway/src/activity/control_service.py:112` | `SUPPORTED_ACTIONS = frozenset()` |
| Worker verb set | `modules/agent-factory/agent/src/control-runtime.ts:101` | `IMPLEMENTED_CONTROL_VERBS = new Set<ControlAction>()` |
| CI gate (Python) | `.github/workflows/agent-control-ci.yml:322` | `EXPECTED_SUPPORTED: set[str] = set()` |
| CI gate (TS) | `.github/workflows/agent-control-ci.yml:480` | `EXPECTED_SUPPORTED = new Set<string>()` |

All four changes in this diff to those files are **comment-only**. The observable
behaviour is unchanged from `main`: `capabilities.pause` is false, and a pause
request is answered 501 before it reaches any of the new code. No operator can
pause a run on this branch.

The author's justification is in `docs/design-notes/3961-control-authorization-intersection.md`
and it is *correct on the merits* — enabling a verb trips #5028's
`requiresEnvelope` coupling (`control-listener.ts`), the human dashboard path mints
no envelope, `SUPPORTED_AGENT_ACTIONS = {MONITOR}` refuses pause at revalidation,
and envelope keys are unprovisioned while `agent_authority_enabled` defaults false.
I verified each of those four claims independently and all four hold.

**Why that does not clear the blocker.** The story's stop condition permits
stopping when *the barrier* cannot meet its contract. Here the barrier does meet
its contract and an *authorization* gap outside S2's stated scope blocks it. That
is a different situation, and the honest outcome is not "S2 is done with the verb
off" but "S2 is blocked on a dependency and needs a scope decision from the EPIC
owner." The design note is a strong ADR-1 change proposal and should be filed as
its own story (the note itself says so). What must not happen is this PR merging
with S2's acceptance recorded as satisfied.

**Fix:** either (a) land the `human_session` authority story first and then enable
the four surfaces in this PR, or (b) re-scope #3961 with the EPIC owner so the
barrier lands as explicitly-partial infrastructure and the AC set moves to a
follow-up story. Do not enable only some of the four surfaces — the CI gate exists
precisely to catch that, and a one-sided widening ships a button whose handler 501s.

### B4 — A pause stuck in `pause_requested` never confirms, even once the run goes quiet
**Impact: high · Confidence: high (reproduced) · Approval impact: blocking**

`pause-gate.ts:409–420`. `requestPause` waits for quiescence with a bounded timer
(`awaitQuiescence`, line 527, default `DEFAULT_SETTLE_TIMEOUT_MS` = 60s). On
timeout, `finishPause` returns `{outcome:'requested'}` — and **nothing ever
re-drives confirmation.** `settle()` (line 330) wakes `quiescenceWaiters`, but the
waiter for that request was already removed when the timer fired. There is no
"re-check on settle" path, no timer re-arm, and `applyControlCommand`
(`agent-worker.ts:2027–2031`) deliberately leaves the command `pending`.

Result: a tool that takes longer than 60s leaves the gate in `pause_requested`
until the pause budget expires. Admission *is* closed, so the pause is real — but
the run reports "pausing…" for the whole budget, and the operator's command sits
`pending` with no terminal outcome. Only a brand-new pause command confirms it.

I reproduced this with a throwaway probe suite (since deleted; tree is clean):
after the settle wait elapsed and the tool then settled, `activeToolCount()`
reached 0 while `currentPhase()` stayed `pause_requested` and the request's outcome
stayed `requested`; no `pause_confirmed` event was ever emitted.

**Refinement from a second probe (this corrects an earlier draft of this
paragraph):** the stuck state is *not* unbounded — `armExpiry` is set in
`beginPause` before the wait, so the expiry timer still fires. But what it does is
worse than a timeout: at expiry the gate calls `releasePause(true)`, reopens
admission and emits `pause_released` **having never emitted `pause_confirmed`**. So
the sequence an operator actually gets is: press Pause → "pausing…" for the full
budget (default 30 min) → the run silently resumes → and because of B5 the store is
never updated, so the dashboard keeps saying `pause_requested` and the journal
command keeps saying `pending` indefinitely. The bound exists in the gate and does
not reach the operator.

**Amplification worth noting:** each stuck request holds a `pending` journal slot,
and `prune()` (`control-state.ts`) only evicts *settled* entries. Ten such requests
exhaust `DEFAULT_MAX_PENDING` (10) and every subsequent control command — including
`resume`, the one thing that recovers the state — is refused 429. The run becomes
uncontrollable through the control plane.

**Fix:** re-evaluate confirmation when the in-flight count reaches zero while a
pause is active — e.g. have `settle()` publish a quiescence edge that a
still-pending pause request observes, and have that transition emit
`pause_confirmed` and settle the journal command `applied`. Add a test asserting
that a pause which times out its settle wait and *then* goes quiet reaches
`paused`, and that no pause can reach `pause_released` without having passed
through either `pause_confirmed` or `pause_unavailable`.

### B5 — `pause_unavailable` and expiry auto-resume never reach the state store
**Impact: high · Confidence: high (reproduced) · Approval impact: blocking**

`setPhase` has exactly four call sites in non-test code, all inside
`applyControlCommand` (`agent-worker.ts:2004, 2022, 2029, 2036`) — i.e. it is only
ever driven by an inbound command. But two transitions happen **without** a
command:

- `markBreached` (`pause-gate.ts:561–588`) sets `phase = 'running'`, reopens
  admission, denies parked work, and emits only `pause_unavailable`;
- `releasePause(true)` (line 491, armed by `armExpiry`, line 507) auto-resumes on
  expiry and emits only `pause_released`.

The only gate subscriber in the worker is `agent-worker.ts:2233–2235`, which
handles `active_work` and nothing else. The adapter's subscriber
(`claude-control.ts:523–526`) handles `pause_released` and only turns it into a
registry event plus the expiry annotation. **No subscriber maps either event to
`store.setPhase`.**

So after a barrier breach, or after an expiry auto-resume, the store the gateway
polls keeps reporting `paused` while tools are running again. That is precisely the
false-`paused` claim the story is written to make impossible — the AC wording is
that anything unprovable degrades to `requested`/`unavailable`, and here the
unprovable case degrades to a *stale confirmed pause*. Reproduced with the same
probe: after `markBreached`, the gate reported `running` while the store still
reported `paused`.

**Fix:** subscribe the worker to `pause_unavailable` → `setPhase('running')` (and
settle any live pause command `rejected` with the reason), and to
`pause_released` with `expired: true` → `setPhase('running')` plus settling the
pause command. Add a test that asserts store phase and gate phase agree after each
gate-initiated transition.

### B6 — The `PreToolUse` matcher is registered with no `timeout`
**Impact: high · Confidence: medium-high · Approval impact: blocking**

`developer-checkpoints.ts:98`:

```ts
PreToolUse: [{ hooks: [pause.preToolUse] }],
```

`HookCallbackMatcher` in SDK 0.3.220 accepts `timeout` (seconds), and no `timeout`
appears anywhere in `developer-checkpoints.ts`. The pause design *depends* on this
hook parking for up to `DEFAULT_PAUSE_TIMEOUT_MS` (30 minutes,
`pause-gate.ts`). If the CLI applies any default hook timeout shorter than the
pause budget, the parked admission is aborted, `admit()`'s abort handler calls
`markBreached` (`pause-gate.ts:286`/`312`), and **every pause collapses to
`unavailable`** — with B5 leaving the store still saying `paused`.

Confidence is medium-high rather than high only because I could not extract the
CLI's default hook timeout from the minified SDK bundle. That uncertainty is itself
the argument: the safe value is cheap to set explicitly and the failure mode of
guessing wrong is total loss of the feature. This is also a case B2's missing
real-SDK experiment would have settled empirically.

**Fix:** set an explicit `timeout` on the `PreToolUse` matcher that exceeds the
clamped pause budget, and assert it in `developer-checkpoints.test.ts`.

## What I verified as correct

These are real and worth keeping — they are the reason this is a
"request changes", not a "start over".

- **Provider neutrality holds.** `pause-gate.ts` (602 lines) contains no match for
  `Query`, `SDKUserMessage`, `claude`, `anthropic` or `Claude`. All Claude-specific
  translation is in `harnesses/claude-control.ts`.
- **No interrupt, no session restart, no replay.** `interrupt` appears only in
  comments in `claude-control.ts` (lines 49, 286, 347, 425) — never as a call.
  Resume is `pauseGate.resume()` and nothing else (line 637).
- **Pause is an admission barrier, not output suppression.** `admit()` parks and
  later admits the *same* tool the model chose (`pause-gate.ts:267–320`).
- **Serialized transitions with an epoch guard.** `serialize()` (line 596) plus the
  `pauseEpoch` re-check in `finishPause` (line 412) and `armExpiry` (line 511)
  correctly make a superseded pause and a late timer inert.
- **Deadline clamp is right.** `safeBudget` (line 481) clamps to
  `deadline − now − finalizationMargin` and returns `null` when nonpositive, which
  `beginPause` turns into `unavailable('no_safe_budget', …)` (line 390).
- **Cancel denies rather than flushes held work** (`markBreached` and `cancel`),
  with the reasoning documented — an aborting run does not run the side effects the
  operator aborted.
- **Idempotent settle.** `settle()` early-returns on an unknown/repeated ticket
  (line 327), so a double completion/failure edge cannot fake quiescence; the
  adapter's `onStop` sweep (line 351) closes missing edges without claiming
  anything about background work.
- **Background work degrades honestly.** `ClaudeBackgroundWorkObserver.count()`
  returning `null` yields `requested` with "not observable" (line 423–428), never
  `paused`.
- **Watchdogs are pause-aware.** Post-completion force-exit and the idle retry both
  consult the live gate (`agent-worker.ts:1456`, `1582`), and the heartbeat keeps
  logging *and says it is paused* rather than going silent — the right call:
  "paused" must be distinguishable from "stalled".
- **The shared contract suite covers a non-Claude adapter.** `control-runtime.test.ts`
  runs pause/resume/timeout/cancel against both the Claude adapter and the
  independently-shaped `EchoControlAdapter` fixture (which has its own barrier and
  its own expiry note), so the contract properties are not proven only against the
  one implementation.
- **The authorization blocker is executable, not just asserted.**
  `control-listener.test.ts` pins supported-verb + no-envelope → 403
  `not_authorized` with nothing journaled.
- **Coverage bar met on the new module.** `pause-gate.ts` 97.95% stmts /
  96.77% branch / 100% lines — clears the ≥85% line-and-branch bar.

## Non-blocking follow-ups (do not gate the merge)

- `finishPause`'s `requested` reason interpolates `this.inFlight.size` at return
  time; once B4 is fixed, make sure that string is not read as a live count.
- `applyControlCommand`'s `action !== 'pause'` branch settles `rejected` for
  `steer`/`abort`. Correct and well-commented, but S4/S6 will each need to
  remember to extend it — worth a `TODO` naming both stories.
- `control-state.ts` contains a stray NUL byte at offset 15928 which makes `grep`
  treat it as binary. **Pre-existing on `main`, not introduced here** — but it makes
  this file materially harder to review and is worth a one-line cleanup PR.
- Consider asserting in a test that the set of `setPhase` call sites covers every
  gate event that changes admission state; that is the invariant B5 violates, and a
  structural test would stop it regressing.
