## Findings (by confidence)

### HIGH — merge blockers

None.

### MEDIUM — discuss before merge

1. **Version-normalized fallback may over-match** (`neptune_client.py` lines 444-467): When exact symbol_id match returns nothing, the fallback uses `STARTS WITH $sid_prefix` where `sid_prefix` is just `"scip-python python <package>"`. This would match ALL symbols in that package across repos. Combined with the `:CALLS` edge requirement, false positives are unlikely (a structural call edge must exist), but if two repos call different functions from the same package, one repo's callers could theoretically appear for the other function. Risk is low because the `:CALLS` edge constraint is tight, and this path only fires when exact match fails (version mismatch scenario). Document as known limitation — acceptable for L2.

2. **Stale docstring** (`structural_backend.py` line 458): `cross_repo` parameter docstring still says "also search for cross-repo references via Zoekt" — but when Neptune is available, cross-repo now uses Neptune natively. Minor discrepancy; Zoekt is still used in the code-index fallback path so not entirely wrong, just imprecise.

### LOW — follow-up candidates

1. **No explicit `line` field in cross-repo results** — The issue's comment #2 mentions "readable `name`/`module`/`file`/`line`/`repo` per result." The cross-repo result dict includes `file` and `symbol` but not `line` (line 559-567 in structural_backend.py). Neptune may not always have line info from the cross-repo callee. Acceptable for L2; can enrich when indexer stores line data.

2. **No `distance` field in cross-repo results** — Same-repo results have `distance` (from Neptune's hop count), but cross-repo results don't. The openCypher query doesn't compute distance for cross-repo callers. Could be added via path length in future.

3. **ACL filtering note** — Cross-repo results pass through existing `_apply_acl()` (server.py line 501), which is correct per the pinned design ("cross-repo results filtered against caller's `allowed_repos`"). No new ACL code needed — existing infrastructure handles it.
