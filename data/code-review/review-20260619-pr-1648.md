## Critical accuracy issue

The `scip_neptune_loader.py` is **NOT fully label-agnostic** as the design claims. The loader:
- Hardcodes `:Symbol` label in `_load_vertices` (line 183: `MERGE (n:Symbol {~id: node.id})`)
- Hardcodes `CALLS` and `REFERENCES` edge labels in `_load_edges` (lines 216-219)
- Hardcodes specific property names (`symbol_id`, `name`, `module`, `file`, `line`, `kind`, `repo`)

The design (Section 4.6) claims: "No modification needed for the infra path because the loader uses generic MERGE from the CSV ~label column." This is **inaccurate** — the loader uses the `~label` column for filtering/grouping edges but hardcodes the Cypher MERGE labels and property extraction. Loading `:InfraResource` nodes with different properties (`address`, `resource_type`, `provider`, `module_path`) would require either:
1. Modifying the loader to be truly generic (read label + properties from CSV columns dynamically), OR
2. Writing a parallel loader function for infra (mirrors loader pattern but with infra labels/properties)

**Impact assessment**: This is a MEDIUM finding, not a merge blocker. The design is directionally correct (reuse the loader pattern), and the fix is straightforward. IAC-1 implementation will naturally need to address this — either by genericizing the loader or by adding infra-specific loading functions. The design's overall architecture (pipeline shape, graph model, Door surface) is sound regardless.

## Findings (by confidence)

### HIGH — merge blockers
None.

### MEDIUM — discuss before merge

1. **Loader reuse claim overstated** (Section 4.6): `scip_neptune_loader.py` hardcodes `:Symbol` label and code-specific properties. It cannot load `:InfraResource` nodes verbatim without modification. The design should note that IAC-1 will either genericize the loader or implement a parallel infra loader using the same `_neptune_query` / SigV4 pattern. This does not block the design document but should be corrected for accuracy before IAC-1 relies on it.

2. **`discover-infra.py` characterization inconsistent**: Comment 5 calls it a "placeholder" but the file has real AWS Resource Explorer functionality (~320 lines). The design document itself says "EXTEND" which is correct — but the earlier architect progress comments may confuse readers. Minor, document text is fine.

3. **Edge `~id` encoding: hash collision at 10 chars**: The edge `~id` uses only 10 chars of SHA-256 for from/to hashes. For a corpus of ~1200 edges this is fine, but for large-scale multi-repo infra graphs (tens of thousands of edges), 10-char hex (40 bits) gives ~1 trillion unique values — collision probability is negligible. Acceptable.

### LOW — follow-up candidates

1. **`symbol_exists` uses empty-list return on error** (neptune_client.py line 310 returns `False` when driver is None): The design's `infra_resource_exists` should follow the same fail-loud pattern it describes for `query_infra_impact`. The design already implies this but could be explicit about what to return when Neptune is unavailable (None vs raise).

2. **Cross-repo infra joins noted as "non-goal for Phase 1"** but the `repo` property is shared format — good future-proofing. No action needed.

3. **Appendix B mentions `hcl2.load(f, with_meta=True)` for line numbers**: Should verify python-hcl2 v8.x actually supports this before IAC-1 implementation. (Research-level concern, not a design blocker.)

## Recommendation
**APPROVE** — Design is comprehensive, well-grounded in the codebase, and correctly mirrors the proven SCIP pipeline pattern. The one medium finding (loader reuse claim) is directionally correct and will be addressed during implementation. No merge blockers.
