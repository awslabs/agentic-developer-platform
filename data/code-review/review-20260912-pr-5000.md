# Code Review — PR #5000 (issue #4999)

**Verdict: APPROVE.** Reviewed revision `c4417fe`. **Zero merge blockers.**

The change fixes a real and consequential gap: NetworkPolicy on this EKS Auto Mode
cluster was never enforced, so four policies — including the agent worker egress
restriction and the control-listener boundary — were decorative. This PR adds the
missing enforcement prerequisite and, critically, ships the one policy that must
exist *before* enforcement starts. Merging is safe because merging does not turn
enforcement on; that requires a separate manual dispatch.

The most important thing a reviewer can get wrong here is treating this as a flag
flip. It is not. I verified the ordering argument independently rather than
accepting the PR description, because the failure mode it guards against (total,
silent loss of agent telemetry) produces no error, no restart and no CrashLoop.

## The ordering safety argument — independently verified

The PR claims the two applies "cannot race". I checked the workflow triggers
directly rather than trusting the claim, and it holds by construction:

| Workflow | Trigger | Consequence |
|---|---|---|
| `webhook-ingress-deploy.yml` | `push` to `main` on `modules/agent-factory/webhook-ingress/**` | ADOT policy applies automatically on merge |
| `platform-infra-apply.yml` | `workflow_dispatch` **only** | Enforcement never activates on merge |

`platform-infra-apply.yml` has no `push` trigger (verified at lines 1–12; its
header comment states the rationale explicitly). So the safe order is structural,
not conventional. This also corrects the issue body, which asked for the two to be
"sequenced, not raced" — the developer's correction is accurate.

**The ordering risk is live, not hypothetical.** `enable_agent_otel = true` in
`modules/agent-factory/webhook-ingress/infra/terraform.tfvars:20`, so the ADOT
collector is actually deployed in dev. Had enforcement been enabled first, telemetry
would genuinely have stopped.

## Completeness of the deny-without-allow audit — extended beyond the PR

The whole safety case rests on "the ADOT collector was the *only* pod selected by
`default-deny-egress` with no matching allow." That policy uses `pod_selector {}`
(every pod in `adp-agents`), so an incomplete audit would mean an unannounced
outage. I checked every other pod-producing workload landing in that namespace:

| Workload | Source | Egress need | Verdict |
|---|---|---|---|
| `adot-collector` | `otel-collector.tf:119` | DNS + HTTPS (X-Ray/EMF/Logs/STS) | **Was the gap** — fixed by this PR |
| `agent-scaledjob` workers | `scaledjob.tf:204` | 53/443/22/4317/5100 | Covered by `agent-scaledjob-egress` |
| `agent-warm-pool` | `warm-pool.tf:154` | None — `sleep infinity` balloon | Deny is benign |
| `agent-image-prepull` | `warm-pool.tf:272` | None — `sleep 3600` loop; image pulls are kubelet-level, not pod egress | Deny is benign |
| Cyber-domain scaledjobs | `modules/domain-apps/cyber/k8s/` | n/a | Different namespace (`cyber-workers`) — unaffected |

The audit is complete. This is the finding I most wanted to disconfirm and could not.

**Selector correctness:** the ADOT policy selects
`app.kubernetes.io/name = adot-collector`, which matches the collector Deployment's
**pod template** labels at `otel-collector.tf:146` — not just the Deployment's own
metadata. A selector matching only the parent object would grant nothing and be
indistinguishable from a correct policy until enforcement began.

## Mutation testing of the assertions

A passing tftest proves nothing unless it can fail. I broke each guarded property
and confirmed the intended assertion fires:

| Mutation | Result |
|---|---|
| Drop ADOT 443 egress rule | ✅ fails — "must allow 443/TCP for STS, X-Ray and CloudWatch" |
| Narrow `default-deny-egress` `pod_selector` to workers only | ✅ fails — "must keep an EMPTY pod_selector" |
| Split control-listener `from` block in two (OR-widening) | ✅ fails — "must admit exactly one source" |
| Flip `enable_network_policy_controller` default to `true` | ✅ fails — "must default to false" |

The OR-widening mutation is the highest-value one: splitting `namespace_selector`
and `pod_selector` into separate `from` blocks changes AND to OR, which would admit
any pod labelled `bedrockgateway` in *any* namespace. That is invisible in a diff
and would make evaluation #3967's W1-04 pass for the wrong reason. It is guarded.

**The developer's self-disclosed gap is real but harmless.** Writing the ConfigMap
value as bare `true` instead of `"true"` still passes. I checked why: Terraform
coerces `true` → `"true"` in a `map(string)` (confirmed via `terraform console`),
so the mutation yields byte-identical applied config. The assertion guards a wrong
*value*, not a wrong *type*, and no wrong-type value can reach the cluster. No
action needed — and I credit the disclosure, which was accurate.

## Security review

No vulnerabilities found in the checks completed. This change **strengthens** the
security posture: it makes four previously inert boundaries effective. No secrets,
no IAM changes, no new permissions, no authz change.

Two notes, both **non-blocking**:

1. **ADOT 443/53 egress has no `to` destination restriction**, so it permits HTTPS
   to any reachable address, not only AWS endpoints. This matches the existing
   house pattern (`agent-scaledjob-egress` uses the same unscoped 53/443 shape),
   and tightening it to AWS prefix lists is out of scope here. Worth noting as a
   posture observation, not a defect in this PR.
2. **Any prior security review that concluded worker egress was restricted was
   reading inert configuration.** That conclusion should be treated as void until
   the live probes pass. This is the real security consequence of the PR and the
   reason the runbook's Step 4 matters.

## Validation gaps — what this approval does NOT establish

This approval covers the configuration as declared. It does **not** establish that
enforcement works. Specifically unproven:

- **The issue's central hypothesis is still unconfirmed:** that setting the
  ConfigMap key causes the controller to reconcile the four existing policies into
  `PolicyEndpoint` objects. Terraform declaring a key does not prove a controller
  acts on it. Both tftest files state this limitation honestly in their headers.
- Negative/positive probes, and post-enforcement telemetry, are live-only checks.
- Evaluation #3967's W1-04 is **not** unblocked by merging this PR.

The tests are plan-only with mocked providers. They prove what the configuration
declares, which is the right scope for pre-merge — but nobody should read this
approval as "isolation is now fixed."

One design note worth surfacing: `kubernetes_config_map` (create) rather than
`kubernetes_config_map_v1_data` (patch) means the apply will **fail loudly** if a
future environment already has that ConfigMap. The code documents this as
intentional, and I agree — a loud failure beats silent divergence. Operators
enabling in a new environment should expect it and import rather than force.
