## Findings (by confidence)

### HIGH — merge blockers

**1. `load_to_neptune()` will fail at runtime with `KeyError` — loader is NOT label-agnostic**

- **File**: `discover-infra.py:336`
- **What happens**: The code calls `load_to_neptune(csv_output=csv_output, ...)` from `scip_neptune_loader.py`. That function delegates to `_load_vertices()` (line 167-178 of scip_neptune_loader.py) which reads:
  ```python
  "symbol_id": v["symbol_id:String"],
  "name": v["name:String"],
  "module": v["module:String"],
  "kind": v["kind:String"],
  ```
  None of these columns exist in the IaC CSV (which has `address:String`, `resource_type:String`, `provider:String`, `module_path:String`). This will raise `KeyError: 'symbol_id:String'`.

- **Additionally**: `_load_edges()` (line 216-219) only groups by `CALLS` and `REFERENCES` labels:
  ```python
  calls_edges = [e for e in edges if e["~label"] == "CALLS"]
  ref_edges = [e for e in edges if e["~label"] == "REFERENCES"]
  ```
  IaC edges have labels `DEPENDS_ON`, `DECLARED_IN`, `USES_MODULE`, `USES_PROVIDER` — they'd be silently dropped (0 edges loaded).

- **Also**: The Cypher template hardcodes `:Symbol` label:
  ```python
  MERGE (n:Symbol {`~id`: node.id})
  ```
  Even if columns matched, all IaC nodes would be created as `:Symbol` instead of `:InfraResource`/`:InfraModule`/`:InfraProvider`.

- **Impact**: The entire IAC-1 pipeline fails silently or crashes at the Neptune load step — the core deliverable doesn't work.

- **Fix required**: Either:
  (a) Genericize `scip_neptune_loader.py` to read `~label` from CSV and dynamically build Cypher (the design doc's stated approach, §4.6), OR
  (b) Add a parallel `load_infra_to_neptune()` function in a new file or extend the existing loader, OR
  (c) Write IaC-specific loader functions inline in `discover-infra.py` using the `_neptune_query` helper (minimal approach — just the UNWIND batch logic with infra-specific columns)

  Option (c) is the smallest surgical change. Option (a) is architecturally cleanest but touches the proven SCIP path (regression risk).

### MEDIUM — discuss before merge

**2. Cypher injection risk in `get_infra_delete_queries`**

- **File**: `iac_neptune_csv.py:261-264`
- **Issue**: The `repo` parameter is directly interpolated into Cypher via f-string:
  ```python
  f"MATCH (n:InfraResource {{repo: '{repo}'}}) DETACH DELETE n RETURN count(n) AS deleted"
  ```
  Compare with `scip_neptune_loader.py:67-68` which uses parameterized queries:
  ```python
  cypher = "MATCH (n) WHERE n.repo = $repo DETACH DELETE n RETURN count(n) AS deleted"
  result = _neptune_query(neptune_url, region, cypher, {"repo": repo})
  ```
  Today `repo` comes from filesystem directory listing (safe), but if this function is ever called with user-supplied data, single quotes in the repo name enable Cypher injection.

- **Recommendation**: Use parameterized queries like the existing SCIP loader does. This is a security-hardening fix, not a functional bug today, so it's MEDIUM not HIGH.

**3. No post-load verification query**

- **File**: `discover-infra.py:343-360`
- **Issue**: The acceptance criteria say "Verify gate: assert `:InfraResource` count > 0 and `DEPENDS_ON` edges > 0 after ingestion." The parser has fail-loud (ValueError on 0 nodes), but there's no post-Neptune-load verification that the data actually made it into Neptune (i.e., a `MATCH (n:InfraResource {repo: $repo}) RETURN count(n) AS cnt` query after loading).
- **Recommendation**: Add a verification query after load_result returns (before the final return statement), log a warning if loaded count is 0 despite having CSV data. This catches silent Neptune failures where the loader reports success but MERGE didn't actually create nodes.
