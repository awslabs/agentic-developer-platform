## Findings (by confidence)

### MEDIUM — discuss before merge

- **M1: Sentinel data leaks `_neptune_no_callers` key to ACL filter** (server.py:500-508)
  The sentinel SearchHit passes through `_apply_acl()` before being stripped. In fail-closed mode (no caller principal), ALL hits are dropped — including the sentinel — so `has_neptune_sentinel` would be False, and the response would say `verdict: "symbol_not_found"` instead of `"no_callers"`. However, this is the correct behavior: if ACL denies access, reporting nothing is correct (fail-closed). The sentinel is stripped AFTER ACL, which is the right order. **No action needed** — confirmed as non-issue on deeper analysis.

- **M2: `resolve_symbol()` strategy 2 (CONTAINS) could be noisy** (neptune_client.py:171-187)
  A search for "main" would match any symbol whose name contains "main" (e.g., "maintain", "domain_name", "main_handler"). Results are sorted by `size(s.name) ASC` (shortest first) and capped at 10, so the shortest match (likely exact) is selected first by the caller (`resolved[0]`). This is acceptable given the early-exit on strategy 1 (exact match) — strategy 2 only fires if exact fails. **Low risk** — follow-up could add a `WHERE s.kind IN ['function', 'method', 'class']` filter to reduce noise.

- **M3: `_understand_via_neptune` "slash in target" block has duplicate result-building logic** (structural_backend.py:266-291, 329-352)
  Three places in `_understand_via_neptune` build the same `data` dict from Neptune records (lines 223-241, 272-291, 333-352). This is acceptable for a bug fix PR (surgical fix), but a follow-up refactoring to extract a helper (`_build_neptune_understand_hit(rec, repo_id, depth)`) would reduce the 80 lines of repetition.

### LOW — follow-up candidates

- **L1: No test for the server-level `symbol_not_found` verdict path** — the test file tests `_impact_via_neptune` returning a sentinel, but doesn't test the full `_handle_impact` → verdict="symbol_not_found" path when Neptune returns `None` AND the S3 fallback also returns empty. This is an edge case that's hard to unit test without mocking the full pipeline; acceptable for now.

- **L2: Performance consideration** — `resolve_symbol()` makes up to 3 separate Neptune queries. Combined with the existing `neptune_available()` round-trip per call, the worst case for a bare-symbol impact query is: 1 (availability) + 1 (query_impact empty) + 3 (resolve_symbol) + 1 (query_impact retry) + 1 (symbol_exists) = 7 Neptune round-trips. Follow-up: cache availability, combine resolve+query.

- **L3: The `LIMIT 1` in `symbol_exists` Cypher is redundant** — `count(s) > 0` already returns a single boolean row. Harmless but unnecessary.
