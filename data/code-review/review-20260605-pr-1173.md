## Findings (by confidence)

### HIGH — merge blockers

1. **`agent_learning/*.md` files committed** — AGENTS.md explicitly states: "Never commit `agent_learning/*.md` — that directory is gitignored; explicit `git add` bypasses the ignore and has caused drift five times already."
   - `agent_learning/2026-04-22-issue-93-learnings.md` (+1/-1)
   - `agent_learning/2026-04-22-issue-95-learnings.md` (+2/-2)
   
   These must be reverted from the PR.

2. **`.github/workflows/malware-analysis-agent.yml` — `${AWS_ACCOUNT_ID}` in GHA env literal won't resolve.** The fallback values in the `env:` block of a workflow `run` step are YAML string literals passed as environment variables to the container. The syntax `${AWS_ACCOUNT_ID}` only works if there's a shell expansion happening at evaluation time. But these values are within a `${{ vars.X || '...' }}` expression — GitHub Actions evaluates the `${{ }}` expression at workflow parse time, picks the fallback string literal (since the var likely isn't set), and passes it as-is to the container. The container would then need an env var `AWS_ACCOUNT_ID` to be set in its environment for the shell to expand it. This is a **runtime breakage** if `vars.CYBER_TRIAGE_QUEUE` is not set.
   - Lines 116-119: All 4 CYBER queue URLs use `${AWS_ACCOUNT_ID}` in fallback strings
   - The correct fix: use `${{ vars.AWS_ACCOUNT_ID }}` or fully remove the fallback and require `vars.CYBER_TRIAGE_QUEUE` to be set, OR construct the URL dynamically in a shell step.

3. **`modules/gateway/k8s/deployment.yaml` — `${AWS_ACCOUNT_ID}` not rendered before `kubectl apply`.** The `gateway-deploy.yml` workflow applies `deployment.yaml` directly with `kubectl apply -f modules/gateway/k8s/deployment.yaml` (no `envsubst`, no `sed`). The literal string `${AWS_ACCOUNT_ID}` will be stored as the image name, causing an image pull failure. The workflow then calls `kubectl set image` to override the image tag — but `kubectl apply` first validates/applies the manifest with the broken image reference.
   - **However**, on closer inspection, the `kubectl set image` immediately after overrides the image field. Kubernetes doesn't pull the image until the pod template is fully reconciled. Since `kubectl set image` fires right after `kubectl apply`, the effective image used will be the one from `set image`. But if there's ANY delay or if `kubectl apply` triggers an immediate rollout before `set image` completes, pods will fail to pull `${AWS_ACCOUNT_ID}.dkr.ecr...`.
   - Safer approach: use `sed` or `envsubst` to render the manifest before applying, or use a genuine placeholder that the deploy script replaces.

4. **`modules/domain-apps/cyber/k8s/*.yaml` — `${AWS_ACCOUNT_ID}` not rendered.** The `cyber-k8s-deploy.yml` workflow applies these manifests with a raw `kubectl apply -f "$f"` — no envsubst, no sed. The literal `${AWS_ACCOUNT_ID}` will be stored in the ScaledJob/container spec, causing:
   - Image pull failures (`${AWS_ACCOUNT_ID}.dkr.ecr...` is not a valid registry)
   - KEDA will never scale because the SQS queue URL is invalid
   - This is the same pattern as #3 but with NO subsequent override step. **This is a definite runtime breakage.**

### MEDIUM — discuss before merge

5. **`modules/agent-factory/actions/setup-beads/action.yml` — default changed to empty string `''`.** The original default was `'adp-beads-state-193832579677'`. Now it's `''`. The init logic checks `if [ -n "$S3_BUCKET" ]` before building the remote URL, so an empty default means NO remote will be configured unless `vars.BEADS_S3_BUCKET` is set in GitHub org variables. This is intentional per the PR description ("Relies on `vars.BEADS_S3_BUCKET`") but all 7 agent workflows pass `${{ vars.BEADS_S3_BUCKET || 'adp-beads-state' }}` — meaning if `vars.BEADS_S3_BUCKET` is NOT set, the bucket name `adp-beads-state` (without account suffix) will be used. This bucket likely doesn't exist. The original at least pointed to a real bucket. **Operational risk if `vars.BEADS_S3_BUCKET` is not configured.**

6. **`modules/agent-factory/tests/e2e/conftest.py` and `test_artifacts_e2e.py`** — changed from hardcoded `adp-dev-chat-artifacts-879318057152` to `os.environ.get("ARTIFACTS_BUCKET", "adp-dev-chat-artifacts")`. The default fallback changed (no account suffix) — if the bucket was actually named `adp-dev-chat-artifacts-879318057152`, tests will fail with the wrong bucket name unless `ARTIFACTS_BUCKET` env var is set. Minor since these are e2e tests that require AWS access anyway.
