## Findings (by confidence)

### HIGH — merge blockers

### MEDIUM — discuss before merge
- **`owner`/`repo` input validation**: `resolve_installation_for_repo` passes `owner` and `repo` directly into the URL path (`f"/repos/{owner}/{repo}/installation"`). While GitHub will return 404/422 for invalid inputs, untrusted caller input with path-traversal characters (e.g., `../`) or URL-encoded sequences could theoretically produce unexpected URLs. Since the design doc says these are "pure service functions" called by story #4's route layer (which should validate), this is acceptable — but worth noting that the caller MUST validate inputs before calling.

### LOW — follow-up candidates
- **No `LIMIT 1` on the ownership query**: The `channel_tenant_map` query doesn't use `LIMIT 1`. Given that `org_id` narrows to 1-5 rows and the unique constraint on `(provider, provider_scope_id)` further constrains it, this is fine per the design doc's explicit note ("No index needed: org_id narrows to 1-5 rows, then JSON extract is trivial."). No action needed.
- **Lazy import of `get_settings` in `_get_global_app_credentials`**: While this is consistent with the file's existing pattern (lazy imports inside functions to avoid circular deps), it means every call to `resolve_installation_for_repo` re-evaluates `get_settings()`. Since `get_settings()` is typically cached (via `@lru_cache`), this is fine.
