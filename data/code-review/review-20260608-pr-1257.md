## Findings (by confidence)

### HIGH — merge blockers

None found.

### MEDIUM — discuss before merge

1. **Step 5 migration privilege model gap** (deploy.sh lines 170–177): The script retrieves the DB master creds and uses them with `PGPASSWORD` in a `psql` command for CREATE EXTENSION, but then runs `gbrain apply-migrations --yes --non-interactive` in Step 5b without explicitly passing those master credentials to the migration command. The `apply-migrations` command will use whatever DB credentials are configured in the container's environment (which are the *app role* credentials, injected via ECS task definition secrets from `db_credentials_arn`). This is the same credential set (the secret `adp/research/gbrain/db-credentials` stores the sole user `gbrain`), so it should work — but the "run with master/superuser privilege" intent may not be fully realized since RDS only has one user (`gbrain`) defined in the terraform. The issue's concern about BYPASSRLS may not manifest because there's only one DB user. This is acceptable for the experimental module scope.

2. **`ecs execute-command` output capture** (deploy.sh lines 173–177, 183–188): The `aws ecs execute-command --interactive` command is designed for interactive terminal sessions and may not cleanly capture stdout into a variable. In practice, this can work with `2>&1` redirection but may include session manager noise (SSM session prompts, etc.) in the captured output. The error-checking `grep` patterns should still catch hard failures, but schema version parsing may be unreliable if SSM session boilerplate is mixed in. The fallback path ("Schema check command unavailable; trusting apply-migrations exit") handles this gracefully.

3. **`SMOKE_EXIT` variable capture after `if` block** (deploy.sh line 234): In bash, after an `if cmd; then ... else` block, `$?` reflects the exit status of the *last command before the else*, not the original command. When `"${SCRIPT_DIR}/smoke-test.sh"` fails and control enters the `else` branch, `SMOKE_EXIT=$?` would capture 0 (from the `if` test) rather than the actual smoke-test exit code. This is cosmetic — the message says "exit ${SMOKE_EXIT}" but the value may be wrong. The deploy logic is still correct (it's in the else branch, so it knows smoke failed).

### LOW — follow-up candidates

1. **No shellcheck validation** — The script uses patterns like `[ "${RUNNING_COUNT}" -lt 1 ] 2>/dev/null` (redirecting stderr from `[`) which works but is unconventional. Consider running `shellcheck` in CI for this module's scripts.
2. **Step 4 `--output text --query` suppresses useful info** — If `update-service` fails for a reason other than a non-zero exit (e.g., service not found returns an error response), the output is swallowed by `>/dev/null`. The `set -e` should still catch a non-zero exit though.
3. **EXPERIMENT.md not updated** — Issue mentions updating "README.md / EXPERIMENT.md" but only README.md was updated. Minor — EXPERIMENT.md likely just needs a pointer to the README.

## Recommendation

**APPROVE** — All acceptance criteria are satisfied. The MEDIUM findings are acceptable trade-offs for an experimental module: (1) the single-user DB means the privilege concern is moot, (2) the SSM output noise is handled by the fallback path, (3) the SMOKE_EXIT variable is cosmetic only. The script achieves its stated goal: `terraform destroy` → `deploy.sh` → fully working gbrain with zero manual steps.
