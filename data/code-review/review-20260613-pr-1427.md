## Findings (by confidence)

### MEDIUM — discuss before merge

1. **images/ingestion/ingest-repo.py:1307** — Wiki S3 key mismatch in deepwiki verification.
   - The `store_wiki()` function writes to `f"{wiki_s3_prefix}/{safe_name}-wiki.md"` where `safe_name = org_repo.replace("/", "-")` (e.g., `content/wikis/aws-e-adp-wiki.md`)
   - But the verification constructs: `f"{WIKI_S3_PREFIX}/{org_repo}/wiki.md"` (e.g., `content/wikis/aws-e/adp/wiki.md`)
   - These keys don't match. The verification will **always fail** because it's checking a key that doesn't exist.
   - Fix: use `wiki_result.s3_key` (which is the actual key written by `store_wiki`) instead of constructing it manually.
   - Impact: deepwiki stage will always be marked `failed` even on successful writes. Not a data-loss bug (the wiki IS written), but defeats the purpose of verify-after-write tracking for this stage. The reconciliation would also flag it as drift.

### LOW — follow-up candidates

1. **images/ingestion/ingest-repo.py:1388** — GraphRAG verification is not a true read-back.
   - `ctx.verify(lambda: entity_count > 0)` just checks the in-memory return value, not an actual Neptune read-back. This is the same class of issue the PR is designed to fix (trusting the producer's claim without verifying the durable store).
   - Understandable given Neptune's API doesn't have a simple `head_object` equivalent. Documented as a conscious tradeoff.

2. **images/ingestion/stage_tracker.py** — `StageContext` uses public dataclass fields prefixed with `_`. Using `_` prefix on dataclass fields is unconventional and creates fields like `ctx._stage_name` that look private but are actually dataclass-managed.
   - Not a bug, but slightly confusing API. The `set_artifact()` and `verify()` methods are the intended public interface.

3. **alembic migration** — No `IF NOT EXISTS` or `IF EXISTS` guards on the column ADD/DROP. If the migration is re-run or partially applied, it could fail. However, alembic tracks revision state so this is standard practice.

4. **stages not yet tracked** — `embed_vectors`, `zoekt_index`, `sbom_image` are in `VALID_STAGES` but have no tracking in the current pipeline. This is fine (forward-compatible schema) but worth noting.
