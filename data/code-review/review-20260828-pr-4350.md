### MEDIUM — worth noting before/at apply

1. **`scaledjob-iam.tf` — the `/internal/*` grant is broader than the three endpoints the worker calls, though not a net privilege increase.**
   The grant admits the worker to *every* `/internal/v1/*` route on the internal
   plane, including `admin_routes.py` (`/admin/tenant-config/{tenant}`,
   `/admin/audit-entries`), `provenance_routes.py`, and
   `status_callback_routes.py` — not just the gatekeeper + two credential paths.
   **Why this is not a blocker:** `/agent/{proxy+}` strips its prefix before
   forwarding, so `/agent/internal/v1/admin/...` under the *old* `/agent/*`
   grant already reached those same handlers. Effective app-layer reach is
   therefore unchanged by this PR — the change is transport, as advertised.
   Defence-in-depth also holds independently: `verify_internal_or_irsa` +
   `extract_iam_identity_from_headers` authenticate against the agent_registry,
   `X-Caller-Identity` is injected by API Gateway from
   `context.identity.userArn` (not caller-suppliable), `_check_agent_scope`
   gates the credential routes, and `/admin/audit-entries` requires `org_id`
   (post-#3985). Declining to widen to `.../*` was the right call.
   *Suggested follow-up, not a change request:* if per-path tightening is ever
   wanted, enumerate the three concrete endpoint ARNs instead of `/internal/*`.

2. **Deployment section names the wrong trigger path.** The PR says
   `webhook-ingress-deploy` fires on `modules/agent-factory/**`. It actually
   triggers on `modules/agent-factory/webhook-ingress/**`
   (`webhook-ingress-deploy.yml:5-7`). The outcome is still correct — the
   `scaledjob-iam.tf` change is under that path so the IAM applies, and the two
   source files are covered by `agent-worker-image.yml`
   (`modules/agent-factory/agent/**` + `agent-worker-image/**`) which rebuilds
   the runtime image. **Both halves do ship; the prose is just imprecise.**
   Worth correcting so a future reader doesn't assume a single workflow covers
   both.

### LOW — follow-up candidates

3. **Ordering hazard worth stating in the ops gate.** `local.internal_plane_alb_dns`
   falls back to the *edge* ALB when `internal_plane_alb_dns` is unset
   (`api-gateway/main.tf:167-168`). In that fallback state, `/internal/{proxy+}`
   points back at the edge ALB — where the deny lives — so this fix would 403
   again. The PR's ops gate should explicitly verify the live integration URI
   resolves to the internal-plane ALB (`…-d2e32d8c72-…`) before re-enabling the
   flag. `apply-internal-plane-deny.sh --verify` already checks this precondition.

4. **The acknowledged follow-up is real and confirmed.** `provenance_client.py:173`
   (`base_url = gateway_endpoint + "/agent"`) and `adp_cred/client.py:39`
   (`+ "/agent"`) do carry the identical defect and will 403 the same way once
   the deny is in force. Correctly scoped out of this PR; please file the
   follow-up issue as promised. Note `provenance_client` fails *soft*
   ("Failed to post provenance (non-fatal): HTTP 403") so it degrades silently
   rather than crashing — easy to miss in production.

5. **Nit — redundant `rstrip`.** `_base_url` calls `.rstrip("/")` on
   `self._gateway_endpoint`, which `__init__` already stripped
   (`gateway_credential_client.py:66`). Harmless and arguably defensive given
   the trailing-slash test; no change needed.

## 🔒 Security review (`/security-review`)

**Result: no vulnerabilities found. Change is security-neutral.**

Scope: the SigV4 URL retargeting and the `execute-api` grant widening from
`.../agent/*` to `[.../agent/*, .../internal/*]`. Test-only files excluded.

### Baseline finding that decides the IAM question

`/agent/{proxy+}` **strips** its prefix before forwarding
(`uri = http://<edge-alb>/{proxy}`), so under the *pre-existing* `.../agent/*`
grant a request to `/agent/internal/v1/<anything>` already arrived at the pod as
`/internal/v1/<anything>` and hit the same handlers. The old grant was therefore
already a **superset** of the new `/internal/*` ARN in terms of reachable
application paths. Adding the second ARN grants **no new application-layer
reach** — this is a transport correction, not privilege escalation.

### Controls confirmed intact
- Same `AWS_IAM` authorization type on both routes.
- `X-Caller-Identity` is injected by API Gateway from `context.identity.userArn`
  and is **not** caller-suppliable, so the worker cannot spoof its identity.
- Pod-side `verify_internal_or_irsa` + agent_registry lookup unchanged;
  `_check_agent_scope` still gates the credential routes.
- The #4010 edge deny is a control against CloudFront-originated traffic; SigV4
  API Gateway traffic was never in its threat model. This change moves traffic
  *onto* the plane #4010 intends, so no control is weakened or bypassed.
- Host is unchanged and env-var-sourced (trusted); only the path changed — no
  credential is redirected to an unintended host.
- No hardcoded secrets, keys, or tokens introduced.

### Explicitly considered and rejected
Privilege escalation via the IAM widening; auth bypass on the new route; loss of
the edge-deny control; credential exfiltration via host change. All rejected
with the reasoning above.

### Non-security note
`provenance_client.py:173`, `provenanceClient.ts:122`, `adp_cred/client.py:39`
still build `${gatewayEndpoint}/agent` for their own `/internal/v1/*` calls —
incomplete remediation of #4343 and an **availability** concern (they will 403),
not a security weakness: `/agent` is the *more*-restricted transport. Tracked as
LOW finding #4 above.
