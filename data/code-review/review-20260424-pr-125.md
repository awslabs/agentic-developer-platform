## Review Summary

Design doc is **well-structured, comprehensive, and mostly correct**. Three issues found — one critical (DynamoDB query semantics), two should-fix (env prefix, async/sync mismatch). No security vulnerabilities. Tenant isolation analysis is sound.

## Findings

### 1. CRITICAL: `begins_with` on GSI partition key is invalid DynamoDB

**Location:** Section 1 (GSI Choice), lines 55-58

**Problem:** The design states:
> "For the list endpoint, query with `begins_with(user_workspace, :sub_prefix)` where `:sub_prefix = "{cognito_sub}#"`. This returns sessions across all channels."

DynamoDB `Query` operations require **exact equality** (`=`) on the partition key. `begins_with` can only be used on the **sort key**. The `channel=all` query as described will throw a `ValidationException`.

**Impact:** The `channel=all` feature cannot be implemented as designed. The default `channel=webchat` (exact match) works fine.

**Fix options:**
1. **Multiple queries** (recommended for v1): Issue one Query per known channel (`webchat`, `slack`, `cli`) and merge results. Channels are a small, known set.
2. **Table Scan with filter**: Expensive and slow. Not recommended.
3. **New GSI on `user_id` alone**: Requires Terraform change. Out of scope per the design's own constraints.

**Recommendation:** Document that `channel=all` requires N queries (one per channel). For v1 with only `webchat` active, this is a single query anyway. The implementer should use option 1.

### 2. SHOULD-FIX: Environment variable prefix mismatch

**Location:** Section 3.3 (Configuration), lines 251-256

**Problem:** The design says to add:
```python
agent_gateway_sessions_table: str = Field(
    default="", env="AGENT_GATEWAY_SESSIONS_TABLE"
)
```

But the `Settings` class in `modules/gateway/src/shared/config.py` uses `env_prefix = "BG_"` (line 59). With pydantic-settings, this means the actual environment variable will be `BG_AGENT_GATEWAY_SESSIONS_TABLE`, not `AGENT_GATEWAY_SESSIONS_TABLE`.

The `env` parameter in a `Field()` overrides the prefix, so if the design intends the unprefixed name, the code as written would actually work — but it would be inconsistent with every other setting in the class (which all use the `BG_` prefix implicitly). This will cause confusion.

**Fix:** Either:
- Use `BG_AGENT_GATEWAY_SESSIONS_TABLE` as the env var name (drop the `env=` override, let the prefix apply), OR
- Keep the explicit `env=` override but document that this setting is an exception to the `BG_` prefix convention and explain why.

### 3. SHOULD-FIX: `async def` methods with synchronous boto3

**Location:** Section 3.2 (ConversationService), lines 210-239

**Problem:** The service class shows `async def` method signatures but uses `boto3.resource("dynamodb")`, which is synchronous. Calling synchronous DynamoDB operations inside an `async def` without wrapping in `asyncio.to_thread()` or `run_in_executor()` will block the FastAPI event loop.

**Fix:** Either:
- Use `aioboto3` (already a dependency if the codebase uses it elsewhere), OR
- Wrap boto3 calls in `asyncio.to_thread()`, OR
- Make the methods synchronous and let FastAPI handle them (FastAPI runs sync route handlers in a threadpool automatically, but only for route functions — not for dependencies that call sync from async)

**Recommendation:** Check how the existing `agent_registry` DynamoDB access works in this codebase and follow the same pattern.

## Material Items for Human Review

1. **24-hour TTL** (flagged by architect): Sessions expire 24h after last activity. This undermines the "durable across logout" promise for users who return after 25h+. The follow-up issue to extend TTL to 30 days should be prioritized.

2. **UpdateItem scope**: The gateway role gets `dynamodb:UpdateItem` which could theoretically modify any attribute. The condition expression in code constrains this, but IAM doesn't enforce attribute-level restrictions. Acceptable for v1.

3. **No `org_id` in DDB query**: Tenant isolation relies solely on Cognito `sub` uniqueness. This is secure (sub is globally unique) but prevents future org-level admin queries.

## Verdict

**Approved with required fixes.** The three issues above must be addressed during implementation (they're design guidance, not code bugs since this is a design doc). The implementer (@agent-developer) should:

1. Implement `channel=all` as multiple per-channel queries
2. Follow the `BG_` env prefix convention or explicitly document the exception
3. Use the same async/sync DynamoDB pattern as the rest of the gateway codebase
