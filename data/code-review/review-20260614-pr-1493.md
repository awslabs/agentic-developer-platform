## Findings (by confidence)

### HIGH — merge blockers
None found.

### MEDIUM — discuss before merge

1. **`service.py:50` — overly broad exception catch**: The `except (json.JSONDecodeError, UnicodeDecodeError, Exception)` clause catches `Exception`, making the other two redundant. This is defensive and the result is correct (raises `ValueError`), but the catch-all obscures what errors are actually possible. Since the behavior is correct (bad input → ValueError → 400), this is not blocking but worth noting.

2. **`routes.py` — `get_activity_service()` creates a new `ActivityService()` per request**: This instantiates a new boto3 DynamoDB resource on every request. The docstring says "boto3 handles connection pooling" — while boto3 does reuse HTTP connections within a session, creating a new `resource` each time adds overhead. For initial launch this is fine (low traffic from a single screen); if activity gets high load, consider injecting a shared instance. Not blocking.

### LOW — follow-up candidates

1. **No IRSA policy change in this PR** — The issue mentions adding `dynamodb:Query`/`GetItem` permissions to the gateway IRSA role. This is expected to be done separately via `gateway-infra-apply.yml` as stated in the Deployment section. The PR description correctly documents this. No action needed in this PR.

2. **`service.py:27` hardcoded default `adp-dev-webhook-events`** — Fine for dev; in production the `WEBHOOK_EVENTS_TABLE` env var should be set. This is already handled by SSM injection per the design.
