## Findings (by confidence)

### HIGH — merge blockers
None.

### MEDIUM — discuss before merge

1. **Design Coverage Audit gap (self-identified in doc):** Section 6 notes that Deployment and Validation were "Needs addition below" and then adds them. This is fine — the doc is self-contained. But the five-section structure per CLAUDE.md's issue-authoring convention applies to the *implementation issues* that get filed from this design, not to the design doc itself. The architect correctly flagged this and filled it. No action needed.

2. **Shared entry delete semantics could be more visible in UI:** The design (Section 3.4) says "v1: accept this. The owner owns the data." The delete confirmation modal (Section 2.6) does show a warning about shared status. This is adequate for v1 but worth noting that the implementation issue (Issue B) should make the warning prominent.

### LOW — follow-up candidates

1. **Rate limit enforcement mechanism not specified:** Section 1.4 mentions "10 searches/minute per user" for semantic search and "1 export/hour per user" but doesn't specify whether this uses the existing gateway rate-limit middleware or a new per-endpoint limiter. Implementation issue A should decide.

2. **Embedding re-generation cost on edit:** If a user edits multiple entries rapidly, each triggers an embedding call. No batch/debounce mechanism described. Acceptable for v1 given expected low volume, but worth noting for the implementation.

3. **`/api/personal-context/syntheses` endpoint vs filter:** The syntheses endpoint (Section 1.4) is described as "a convenience alias" that pre-filters `type=synthesis`. This could be a query on `/entries?type=synthesis` instead of a separate endpoint. Minor API design choice — both are valid.
