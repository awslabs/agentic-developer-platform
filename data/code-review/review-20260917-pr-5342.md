## What the PR does

The orchestration cost readback (`src/orchestration/cost.py`) groups `usage_logs`
by `graph_address` and shipped correct, but nothing ever wrote the column — so
every flow reported `{"status":"unknown","reason":"no_usage_rows"}`. This PR
supplies the writer: `validate_engine_authority` already loaded and proved the
flow and node rows and discarded them; it now returns them as a frozen
`GraphAttribution`, the model-identity middleware attaches it to the request's
`TokenContext` as a pydantic `PrivateAttr`, and the shared usage writer persists
it at final metering. It also adds tenant-scoped `(org_id, slug)` uniqueness on
flows (migration 052), because a flow's slug is the first segment of every
address.

## Reviewer-applied repair

### Finding 1 — `get_flow_by_slug` raised on the un-migrated schema (FIXED in `dc190f3a`)

- **File:** `modules/gateway/src/orchestration/repository.py` (`get_flow_by_slug`)
- **Impact severity:** high — unhandled HTTP 500 on plan submission for an
  affected tenant
- **Confidence:** high — reproduced, corroborated by an independent second pass,
  and the regression test fails against the pre-repair code with exactly the
  predicted exception
- **Approval impact:** was a blocker; now resolved
- **Author of the repair:** @agent-reviewer (this review task), commit `dc190f3a`

The new indexed lookup used `scalar_one_or_none()`, which raises
`sqlalchemy.exc.MultipleResultsFound` when a tenant holds duplicate
`(org_id, slug)` flows. The full scan it replaced tolerated that state:
`list_flows` orders `created_at DESC` and `compile._resolve_flow` took the first
match, so the newest flow won.

That duplicate state is reachable by design, not hypothetical, for two
independent reasons:

1. Migration 052 **deliberately refuses to apply** while duplicates exist, so an
   operator resolves them explicitly — the duplicates persist in the meantime.
2. `.github/workflows/gateway-deploy.yml` declares `run-migrations` with
   `needs: [changes, deploy-backend]`, so the new backend code is already live
   against the pre-052 schema.

**Failure scenario.** A tenant has two `orchestration_flows` rows with
`org_id='org1', slug='delivery-loop'` (possible today — no constraint exists on
`main`). The new backend deploys; migration 052 refuses on those duplicates, as
intended. Any plan submission or amendment for that tenant now calls
`_resolve_flow` → `get_flow_by_slug`, which raises `MultipleResultsFound`.
`MultipleResultsFound` subclasses neither `ProposalRejectedError` nor
`TenantMismatchError`, which are the only exceptions the route handles
(`src/orchestration/routes.py:386-399`), so it escapes as an **unhandled HTTP
500** rather than a diagnosable 422 — for precisely the tenants the refusing
migration exists to protect. Before this PR the same submission succeeded against
the newest flow.

Reproduced directly:

```
OLD scan -> newer
NEW RAISED: MultipleResultsFound
```

**Repair.** Restored the previous tolerance with
`ORDER BY created_at DESC LIMIT 1` + `.scalars().first()`. Results are identical
to the assertion form once uniqueness holds, and identical to the prior scan
before it does — so migration 052 remains a safety net rather than a
prerequisite for the attribution write. Tenant scoping (`org_id` filter) is
untouched, so no security property changed.

**Regression test.** Added
`TestFlowSlugUniqueness::test_lookup_still_resolves_on_a_database_that_predates_the_migration`
in `tests/orchestration/test_compile.py`. It drops the fixture's
`create_all`-built unique index to reach the un-migrated state — without the drop
the duplicate rows cannot be inserted and the assertion would be vacuous — then
asserts the lookup resolves newest-wins and that `compile_proposal` converges on
that flow rather than creating a third. Verified to fail with
`MultipleResultsFound` against the pre-repair implementation.

### Security review

`/security-review` was run against the diff at head. **No qualifying
vulnerabilities.** Specifically traced and found clean:

- **No caller-supplied path to the persisted address.** `PrivateAttr` behavior
  confirmed empirically on the repo's pydantic 2.12; every `TokenContext(...)`
  construction site passes explicit named fields from server-resolved state, never
  a caller dict. One writer, one reader.
- **No authorization check became a no-op.** Every refusal in
  `validate_engine_authority` is unchanged and identically ordered; both
  coordinator early-returns still return `None` after their checks.
- **No cross-tenant attribution.** The middleware requires
  `attribution.org_id == caller.tenant_id` and
  `attribution.run_id == caller.invocation_id`; the row's `org_id` is the same
  `caller.tenant_id`, so a persisted `(org_id, graph_address)` pair cannot
  straddle tenants. The readback filters `org_id` in SQL.
- **No per-request leakage.** `TokenContext` is built fresh per request; nothing
  caches it.
- **Migration SQL not injectable** — the f-string interpolates only module
  constants.
- **`flow.slug` cannot forge extra address segments** — `validate_proposal`
  enforces a four-segment address pattern, so a slug cannot contain `/`.

After my repair I reassessed the affected surface: the change is a query
`ORDER BY`/`LIMIT` with the `org_id` filter unchanged, so it alters no
authorization, tenant-scoping or attribution property.
