## The practical picture

The change is foundation, not feature. All four control verbs (pause / resume / steer /
abort) still answer 501, and I confirmed that is structurally true rather than merely
configured: `IMPLEMENTED_CONTROL_VERBS` is an empty set, the listener's `SUPPORTED_ACTIONS`
is now the *same object* rather than a second set that happens to agree, and the worker
derives the store's verb set from the adapter. So the surface an operator can reach is
unchanged, which is what makes the risk here low.

The one genuinely risky thing in this PR is that it touches `resilientQuery`, the retry
wrapper behind every ordinary agent run in the platform. I checked that claim hardest
(below). It holds.

### The post-deploy smoke divergence — resolved, not a blocker

Issue #3962 says the wave-2 smoke command "exits 0, with all required checks passed, none
skipped/not-run". This PR ships exit 4 with nine `not_run`. I treated that as a possible
unmet criterion and investigated. It is a legitimate staged hand-off:

- Nine of the ten wave-2 checks assert properties S3 does not build (proven pause AC-P1/P2,
  auto-resume, the whole abort vocabulary, preflight, cleanup recheck). Requiring exit 0
  from #3962 would require it to deliver S2, S4, S5 and S7's work.
- **Exit 0 here would be the actual defect.** Registering wave 2 with only its one delivered
  check would be a 1/1 wave exiting 0 — a green report for a wave with no pause proof. That
  design choice is pinned by a test, and the "collapse wave 2 to its delivered check" mutant
  fails 3 tests.
- Exit 4 is `EXIT_CHECKS_FAILED`, an honest failure, and `failed == 0` plus nine
  owner-naming `not_run` messages is what distinguishes "not yet" from "regressed".
- Evaluation **#3968 owns wave 2's live acceptance**, exactly as wave 1's #3967 did. This
  was never a PR gate.

I drove the real `main()` and observed: `passed=1 failed=0 skipped=0 not_run=9 required=10`,
exit 4, each `not_run` naming its owning story. The PR's claim that `--wave 2` previously
could not run at all is also true — on `main`, `SUPPORTED_WAVES = (1,)` and the wave guard
fires before `load_config`, so the issue's own published smoke command was a refusal that
wrote no evidence.

## The highest-risk claim, checked hardest

`resilientQuery` has ~18 call sites — every ordinary agent run. The claim is that all three
new hooks are absent in production so behaviour is byte-identical. **It holds.**

- **Mechanically proven identical.** I stripped exactly the #3962-added regions from the

- **No production caller passes any hook.** Grep for the three option names as arguments
  returns hits only in `resilientQuery.ts` itself, `claude-control.ts` (the getters), and
  the `agent-worker.ts:1446-1461` comment explaining the omission.
- **Prompt shape unchanged** without the factory (string, not iterable); `finally` /
  `session.close()` unchanged; backoff timing character-identical; `onSessionId` still fires
  once.
- **The double-close fix is sound.** Exactly one owner on all four paths (completion, retry,
  cancellation, throw): `resilientQuery.ts:315` creates and `:374` closes; the adapter's
  `dispose` closes only the channel it created. No path double-closes, and none leaks.

**Minor accuracy note (not a finding):** the PR and code comments say "17 callers"; I count
18 call sites. Likely "17 others + the worker". Cosmetic.

**One latent issue for whoever enables the hooks (explicitly NOT a defect in this PR):**
driving the real adapter through the hooks shows the task prompt is dropped — `:305`
replaces the prompt with the adapter's iterable, and the channel starts empty and never
enqueues `context.promptText`, so an agent would receive no task. The adapter's docstring
assumes `queryParams.prompt` still carries it, but it has been overwritten. Unreachable on
this branch (no caller passes the hooks), so it blocks nothing here — but S2/S4/S6 must
enqueue the initial prompt when they flip this on. Recommend a comment at
`claude-control.ts:379-397` recording that.
