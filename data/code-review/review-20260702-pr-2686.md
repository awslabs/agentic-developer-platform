## Findings (by confidence)

### HIGH -- merge blockers

None. The implementation is correct and complete per the spec.

### MEDIUM -- discuss before merge

1. **Expression injection in guard step (lines 84-85, 92):** `${{ inputs.customer_account_id }}` and `${{ inputs.account_id }}` are directly interpolated into `run:` blocks. While `workflow_dispatch` requires write access (so the attacker already has code execution), best practice is to route string inputs through `env:` context to prevent injection:
   ```yaml
   env:
     INPUT_ACCOUNT_ID: ${{ inputs.account_id }}
     CUSTOMER_ACCOUNT_ID: ${{ inputs.customer_account_id }}
   run: |
     if [ -n "$CUSTOMER_ACCOUNT_ID" ]; then
       EXPECTED_ACCOUNT="$CUSTOMER_ACCOUNT_ID"
   ```
   **Practical risk: LOW** (attacker needs repo write access + account_id must pass 12-digit comparison). This is consistent with existing destroy workflows (gateway-infra-destroy.yml uses the same pattern). **Suggestion, not a blocker.**

2. **Guard bypass if job is `skipped` vs. `failed`:** The `destroy` job uses `needs: guard` but GitHub treats `skipped` as passing for `needs:`. If the guard step's `if:` condition (hypothetically) causes it to skip, the destroy job still runs. Adding `if: ${{ needs.guard.result == 'success' }}` to the destroy job would be more defensive:
   ```yaml
   destroy:
     needs: guard
     if: ${{ needs.guard.result == 'success' }}
   ```
   **Currently safe** because the guard has no `if:` condition and always runs. But this would be defense-in-depth against future refactors. **Suggestion, not a blocker.**

3. **`skip_phases` input missing explicit `type: string`:** Line 21-24 defines `skip_phases` without a `type:` key. GitHub defaults to `string`, but all other string inputs in this workflow explicitly declare their type. Add `type: string` for consistency and explicitness.

### LOW -- follow-up candidates

1. **`skip_phases` not validated against allowlist:** The input accepts arbitrary CSV. While the comparison logic is safe (exact-match against known phase names), invalid values would be silently ignored. Consider adding a validation step that warns on unrecognized phase names:
   ```bash
   VALID_PHASES="agent-context webhook-ingress agent-factory gateway platform"
   for s in "${SKIPPED[@]}"; do
     s=$(echo "$s" | xargs)
     [ -z "$s" ] && continue
     if ! echo "$VALID_PHASES" | grep -qw "$s"; then
       echo "::warning::Unknown phase in skip_phases: '$s' (will be ignored)"
     fi
   done
   ```

2. **`fetch-depth: 0` on all three jobs:** Full git history is fetched but not used (no git log, git diff, or history-dependent operations). `fetch-depth: 1` (default) would reduce clone time. However, this is consistent with all existing destroy workflows and the `load-deploy-config` action might reference git history. **Not actionable.**

3. **Summary step uses `${{ needs.guard.outputs.account_id }}` in a `run:` block (line 271):** This is safe because it comes from our own step output (not external user input), but it's worth noting as a pattern to be aware of.

4. **Phase order vs. parent design:** The parent design issue #2651 specified "agent-context -> agent-factory -> webhook-ingress -> gateway -> platform" but the implementation issue #2663 (and this PR) uses "agent-context -> webhook-ingress -> agent-factory -> gateway -> platform". This is technically correct since webhook-ingress creates ScaledJobs in the `adp-gateway-agents` namespace which agent-factory later deletes. Destroying webhook-ingress first removes those resources cleanly before the namespace is killed. The shared library `undeploy-phases.sh` also declares functions in this order. **No action needed.**

## Security Review Summary

| Category | Finding | Severity |
|----------|---------|----------|
| Expression injection | `${{ inputs.* }}` in run blocks | MEDIUM (mitigated by write-access gate) |
| Permissions | `contents: read` only -- minimal and correct | GOOD |
| Secrets | No hardcoded secrets, uses ambient IAM | GOOD |
| Concurrency | `cancel-in-progress: false` prevents DoS | GOOD |
| Guard logic | Correctly fails (exit 1) on mismatch, not skip | GOOD |
| Bootstrap isolation | opt-in, requires `needs: destroy` success | GOOD |
| Input validation | account_id validated by comparison to AWS identity | GOOD |

## Recommendation

**APPROVE** -- The implementation is correct, complete, and secure for its deployment context (workflow_dispatch, requires repo write access). The findings are all MEDIUM or LOW and consistent with patterns already established in the existing destroy workflows. None are merge blockers.

The three MEDIUM suggestions (env-context for inputs, explicit guard-result check, skip_phases type declaration) are nice-to-have improvements that could be addressed in a follow-up if the team wants to harden all destroy workflows uniformly.
