## Findings (by confidence)

### HIGH — merge blockers
None.

### MEDIUM — discuss before merge
1. **recall-at-task-start.ts:247-250 — XML injection in `formatLearningEntry`**: `learning.id` and `learning.content` are interpolated directly into XML template strings without escaping. Since recalled content originates from the user's own prior saves (owner-scoped), the blast radius is self-inflicted today. However, if `visibility: 'shared'` learnings are ever surfaced cross-user, this becomes a stored prompt injection vector. Recommend adding `escapeXml()` for `<`, `>`, `&`, `"` in `id` and `content`. This is not a merge blocker because:
   - Owner-scoped isolation is enforced server-side
   - The XML is consumed by an LLM (no XML parser at risk)
   - Risk is self-inflicted under current design

### LOW — follow-up candidates
1. **No response body size limit in `callRecall`**: `response.json()` parses the full body. Server returns max 5 results, but if the server were compromised, an extremely large response could OOM the process. Mitigated by the 3s timeout (limits how much data can arrive). Non-actionable today.
2. **Module-level const `RECALL_ENABLED` means tests can't toggle it at runtime**: The tests acknowledge this limitation and test the lower-level functions (`callRecall`, `formatRecallSection`) directly. Acceptable tradeoff for a KEDA ScaledJob (one task per pod).
