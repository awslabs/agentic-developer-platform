## What the PR does, in one paragraph

Extends the #5225/#5226 quote contract to non-text input and chargeable server work. The
design turns on one property of the existing bound: the adapters **count nothing**. They
reserve the model's entire published context window at the dearest published input-side
rate. That ceiling is provider-enforced (a request whose assembled input exceeds the
window is rejected, not served expensively), so it is provably independent of media size
and content. Media is therefore admitted when its **bytes are inline in the request body**;
server-retained history and server-side tools/MCP stay refused with named prerequisites,
and those limitations are published on #5175.

The refusal rationale is also correct in a way that matters: because the bound counts
nothing, "we cannot count the bytes so the cost is unbounded" would be **false**. The real
reasons references are refused are **authorization** (the provider dereferences a
`file_id`/URL under the gateway pod's single shared IRSA principal, so one tenant could
name another tenant's file) and **no fetcher**. A cost ceiling is not an authorization
boundary. A test fails if the cost-based wording returns.

## Findings — both repaired on this branch (commit `b494758e`)

### 1. The matrix advertised a capability the adapter refused (spec-conformance defect)

`openai_responses_inline_media` listed `input_audio` as admitted, naming an **`audio_url`**
payload field. The OpenAI Responses API **defines no such field**: an audio part carries
`input_audio: {"data": "<base64>", "format": "wav"|"mp3"}` — a nested *object*. (Confirmed
against the `openai-python` SDK type definitions, as `platform.openai.com` returned 403.)
The adapter scanned only data-URI *strings*, so the **only spec-compliant way to send audio
was refused `malformed_request`** while the published matrix promised it worked. A caller
following the API got a 403 on a capability #5227 commits to delivering.

**Root cause of the drift, and why the prior review round missed it:** the matrix test
bound the *Anthropic* row's accepted source types to real adapter behaviour, but there was
**no equivalent binding for the Responses row** — its `content_part_types` and payload-field
claims were unasserted prose in a fixture whose whole purpose is to be auditable. Two tests
now close that structural gap: every advertised part type must produce a real quote, and the
row's per-part payload field must equal the adapter's own `MEDIA_PART_PAYLOADS` map.

### 2. Media part validation was a denylist, and it leaked (tenant-isolation defect)

The prior round's fix scanned a **fixed set** of payload field names and refused the
known-external ones. Because the body is forwarded **byte-for-byte**, any field *not* in
that set still reached the provider and would be dereferenced under the shared principal.
For this control, only an **allowlist** holds. Validation is now keyed to the part's
declared `type`: each part must carry its own type's payload field, and any other key is
refused rather than ignored.

The shared "did any payload field look inline?" tally went with it. It was never a proof
about the part in hand — a nested audio object sitting beside an `input_image` satisfied
that image's inline requirement, so the image's own `image_url` reference was never
scheme-checked.

I confirmed empirically that **9 crafted shapes which the reviewed head `cc22879e`
ADMITTED** are all refused `mutable_media_reference` at `b494758e`, including:

- nested `input_audio: {"data": "s3://victim/secret.wav"}` — a reference wearing the
  payload's name (nested `data` must now be drawn from the base64 alphabet);
- an `audio_url` reference riding inside a nested decoy — note this was a **regression the
  denylist introduced** versus the head before it;
- `{"type": "input_image", "image_url": {...reference...}, <other type's payload>}` — the
  cross-type satisfaction case.

Every optional field the API documents (`detail`, `filename`, `prompt_cache_breakpoint`,
`format`) still admits, so the fix is not a blunt tightening.

`MEDIA_RESPONSES_PARTS` is now **derived** from `MEDIA_PART_PAYLOADS` rather than written
out twice, so the set the adapter dispatches on and the map saying where each part's bytes
live cannot drift apart.

The money bound was never at risk in any of this — the whole context window is reserved
regardless of content — and the fix does not rest on cost. These were holes in an
**authorization** control.

### 3. The reference refusal was enforced only where media was priced (tenant isolation)

An independent adversarial re-attack at `b494758e` found the control **still bypassable**.
I reproduced **12 admitted bodies myself** before touching anything, and checked each
against the merge base `a1207e02` to separate what this PR introduces from what it inherits.

The root defect was **where** the checks ran, not what they checked. The reference scan and
the key allowlist lived inside the media branch, which is reached only when a part's
declared `type` is a media type. Everything else was walked for *type* but never for
*reference fields* — so declaring `"type": "input_text"` and hanging a `file_id` off it
bypassed the control entirely. Repaired, each with regression tests:

| # | Bypass | Status |
|---|---|---|
| a | `file_id`/`file_url` on any non-media part (`input_text`, `text`, `output_text`, `summary_text`, `refusal`) and in `instructions` | scan hoisted above the type dispatch |
| b | Anthropic block/source had **no key allowlist**: `url`, `file_id` and Bedrock-native `s3Location` admitted *beside* valid base64, quote labelled MEDIA | `ALLOWED_ANTHROPIC_SOURCE_KEYS` / `ALLOWED_ANTHROPIC_MEDIA_BLOCK_KEYS` |
| c | Anthropic `data` required only "non-empty str", so `data: "s3://victim/secret.png"` was admitted as inline bytes | strict base64 decode; the two routes no longer disagree about "inline" |
| d | `BASE64_ALPHABET` contains `+`, `/`, `=`, so `file/VICTIMTENANTB/secret==` passed it — only the `:` in `s3://` was doing any work | replaced by `is_inline_base64` (decode with `validate=True`) |
| e | `data:` was a scheme-only `startswith`, so `data://attacker/probe.png` and `data:,https://attacker/x` were admitted | `is_inline_data_uri` requires the full `data:<mediatype>;base64,<payload>` form |
| f | Allowlisted keys were **value**-unchecked: `format: "https://attacker/probe.wav"`, `filename: "s3://victim/secret.pdf"` | each key now has its documented closed set |

Also: an unhashable `type` raised a bare `TypeError` out of the adapter rather than a
`QuoteRefusedError`. It failed closed only because a caller catches `TypeError` broadly —
recording **no reason or capability**, so the refusal was invisible in the very evidence
this layer exists to produce. Both routes now refuse it properly.

**Generalisable lesson, and the reason two rounds were needed:** an allowlist is only as
good as its *coverage*. The allowlist logic itself was sound — it was simply not reached
for most of the document. When validating input that is forwarded verbatim, the question
"is this check correct?" is secondary to "does this check run on every node that can carry
the dangerous thing?"

Verified after repair: all 10 in-scope shapes refuse `mutable_media_reference` (or
`malformed_request` for the unhashable case), and **18 documented legitimate shapes still
admit** — data-URI image/file, nested wav/mp3 audio, `detail`, `filename`,
`prompt_cache_breakpoint`, a 40KB payload, Anthropic base64/text/content sources,
`cache_control`, `title`/`context`/`citations`, text blocks, nested `tool_result` — with
references keeping their specific refusal reasons.

## Out of scope, needs a follow-up issue (NOT a regression from this PR)

Reference-bearing **container fields are never walked at all**: top-level `attachments`,
top-level and per-item `file_ids`, and `tools[].file_id` are admitted on the Responses
route. I confirmed these are admitted **identically at the merge base `a1207e02`**, where
all media was refused `non_text_content` — so they pre-date this work and are not caused by
it. I deliberately did **not** fold a fix in: closing them means deciding a top-level body
allowlist, which is its own change with its own blast radius and deserves its own review.
**This should be filed and tracked** — it is a live tenant-isolation gap on the base
branch, independent of whether this PR merges.
