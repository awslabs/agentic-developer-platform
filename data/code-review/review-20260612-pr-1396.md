## Findings (by confidence)

### HIGH — merge blockers

None.

### MEDIUM — discuss before merge

1. **Section 4.1 `is_reachable()` signature mismatch with Section 5.3 `_triage()`**: The pseudocode in Section 4.1 accepts `vuln_symbols: list[str] | None` (per-function precision) but Section 5.3's `_triage()` only passes `vuln.package_name` (package-level check). This is a minor design-doc inconsistency — the implementation should support both per Section 4.1's strategy notes. Not a blocker since this is a design note, not shipped code, but worth noting for implementors.

2. **Triage gate order**: Section 5.3 checks idempotency → reachability → severity. This is the optimal order (cheapest checks first, avoid Neptune query for already-filed CVEs). Good design. No action needed — noting as positive.

### LOW — follow-up candidates

1. **Open Question §17.1 (Neptune fallback to S3)**: The design recommends S3 `code-index.json` as fallback when Neptune unavailable. This aligns with the fail-safe behavior (assume reachable) but should be explicitly linked. Minor doc polish for future iteration.

2. **Migration sequence assumption**: The design assumes `002_remediation_runs.py` is next after `001_knowledge_layer_schema.py`. Implementor should verify no other migration has claimed that slot by the time they implement.
