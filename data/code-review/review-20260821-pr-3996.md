## Security review

Ran a dedicated adversarial pass on the five questions that actually matter for this diff.
**The diff is clean on all five.**

- **Denylist completeness** — verified against every header the app trusts for
  identity/authz: `x-auth-source`, `x-caller-identity`, `x-amzn-iam-user-arn`,
  `x-amzn-requestcontext`, `x-internal-api-key`, and all 11 `x-agent-*` variants plus
  `x-agent-scopes` (`credential_routes.py:567,701` — self-grants credential scopes, so
  stripping it matters). The `x-agent-` prefix loop covers all of them. `authorization`
  and `x-api-key` correctly left intact (both cryptographically validated).
- **Bypassability** — CloudFront lowercases header names in the event object, so the
  lowercase literals are correct for any input casing. Duplicate headers collapse into
  one field with a `multiValue` array; `delete` removes the whole field. `for…in` with
  `delete` of the visited key cannot skip unvisited keys, and the loop runs after the
  explicit deletes. `/%61pi/…` and `/api%2F…` do not match `/api/*` and fall to S3.
  Critically, **header deletion is unconditional** — independent of whether the prefix
  strip fires — so no strip edge case can resurrect a forged header.
- **No remaining unstripped CloudFront behavior** — full enumeration: `/api/*` ✓ function,
  `/.well-known/*` ✓ function (added here), `/gitlab/*` different origin, `default` → S3.
- **No regression** — every legitimate sender of these headers bypasses CloudFront:
  agent-context posts to the `ClusterIP` (`bedrockgateway.adp-gateway.svc.cluster.local`),
  the agent worker and webhook lambdas use `ADP_GATEWAY_ENDPOINT` (API GW `execute-api`),
  and `sigv4-proxy.ts:81` injects `x-agent-orgid` toward API GW. The frontend sends none
  of them (zero hits in `frontend/src`).
- **`/.well-known/*` attachment is safe** — served by `gitlab_sso.py:291-299`, no auth
  dependency, reads no identity headers. Nothing fetches JWKS from the CloudFront domain
  (`cognito_jwt.py:111` and `frontend/src/config/cognito.ts:78` both point at Cognito).

### MEDIUM — worth acting on, but not blocking this PR

**M1 — The CRITICAL is not fully closed after this PR: API Gateway `/{proxy+}` is a second public, unstripped door to the same pod.**
`modules/gateway/infra/modules/api-gateway/main.tf:162-189`

This PR fully closes the CloudFront edge. But CloudFront is not the only public ingress
to that pod. `/{proxy+}` and `/` are declared `x-amazon-apigateway-auth = { type = "NONE" }`
with an `http_proxy` VPC-Link integration to **the same internal ALB**
(`uri = "http://${var.internal_alb_dns}/{proxy}"`). Unlike `/agent/{proxy+}` (`:236`) and
`/internal/{proxy+}` (`:271`), the `/{proxy+}` integration has **no**
`integration.request.header.X-Caller-Identity` mapping to overwrite a client-supplied
value, and `*_PROXY` integrations pass client headers through verbatim. There is no
`aws_api_gateway_rest_api_policy` on this API (the only one in the repo belongs to
webhook-ingress), and `enable_api_gateway = true` in dev. The invoke URL is not secret —
it is published to SSM and returned in the `/admin/agents/onboard` response.

Scenario (described rather than reproduced verbatim — this path is **not yet fixed**; the
exact request is in the #3996 review comment and #3985): an unauthenticated POST to the
API Gateway invoke URL for a proxied inference path, carrying the `X-Auth-Source` and
`X-Agent-OrgId` trust headers set to a victim org.
`/v1/messages` is in `ENFORCED_PATHS`, so `TokenContextMiddleware` runs; with
`BG_TRUST_APIGW_HEADERS=true` (set unconditionally at `gateway-deploy.yml:226`) it reads
`X-Auth-Source` and calls `extract_api_gateway_context` (`middleware.py:591-600`), which
builds a `TokenContext` purely from headers → inference billed and audit-logged to the
victim org.

Scope notes, in fairness to this PR:
- **This is pre-existing, not introduced here** — the diff touches 2 files and neither is
  the API Gateway module. It is not a regression and not a reason to hold this PR.
- The `/internal/v1/*` credential plane is **not** reachable this way: `/internal/{proxy+}`
  is a more-specific `AWS_IAM` route and wins over `/{proxy+}`. The forgery lands on the
  proxy/usage/budgets/admin plane, not the vault.
- PR 2 of A1 (deleting `extract_api_gateway_context` and the unregistered-ARN fallback per
  the developer's step 8) closes the app-side half of exactly this. So the right outcome is
  **traceability, not blocking**: this PR's body claims A1 "closes the internet-facing
  CRITICAL," which is true only once PR 2 lands. Recommend the PR body / #3985 say so
  explicitly so nobody reads a green #3996 as "CRITICAL resolved."

**M2 — Zero automated coverage for the CloudFront Function.**
`modules/gateway/infra/modules/cloudfront/main.tf:97-120`

The function is now a load-bearing security control on two behaviors, and its logic (the
anchored regex + the denylist) exists only as an inline heredoc string. There is no test

test over the handler asserting the rewrite table and that each denied header is absent.
Reasonable as a follow-up rather than a change request.
