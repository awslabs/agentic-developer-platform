## Findings (by confidence)

### HIGH -- merge blockers

### MEDIUM -- discuss before merge
1. **peering.tf:195 comment inaccuracy**: Comment says "The CAPE host SG has no egress rules targeting the ADP VPC" but cape-host.tf:28-36 shows egress `0.0.0.0/0` (broad egress, includes ADP VPC CIDR). This means during the bootstrap-to-hardening window, the CAPE host *can* initiate connections to ADP resources via the return route. Post-hardening (script 04), egress is tightened. Risk is low (no malware running during bootstrap), but the comment should be updated to say "post-hardening, the CAPE host SG egress is tightened to VPC endpoints only."
2. **Return route uses full ADP VPC CIDR** (peering.tf:203, `var.adp_vpc_cidr = 10.0.0.0/16`): Could be scoped to just the EKS pod subnet CIDRs for defense-in-depth. This was flagged in PR #226 review too. Low priority for dev.

1. **`ec2:CreateTags` not in CAPE host IAM role**: `03-hypervisor-smoke.sh:178` and other scripts call `aws ec2 create-tags` but the host role only has S3/DDB/SecretsManager/SSM. The `|| true` prevents failure but tags won't be set. Cosmetic only.
2. **Whitespace-only changes in runner-iam/main.tf**: Lines 131-135 and 149-153 are alignment-only changes (Sid/Effect/Action indentation). Harmless but noisy in the diff.
