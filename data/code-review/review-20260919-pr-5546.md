## Summary

The five blocking findings from the previous independent review (AF-001..AF-005, reviewed at
`e00be001`) are all genuinely fixed at `3afa59ff`. I verified each by direct probe rather than
by reading the developer's tests — the reproductions from the original review no longer
reproduce, and the positive controls still behave.

Probing the repair itself surfaced **three new defects**, all introduced by the repair commits
and all sharing one root cause: resources discovered on the cluster and passed as
`extra_actions` went through the new ownership guard but bypassed the mode and convergence
reasoning that governs generated actions. I fixed all three on this branch in `e70f19dd`, with
regression tests that fail against the pre-fix code.

Practical consequence of the three, had they merged: a workspace cleanup could (a) produce a
plan that kro reconciles back, (b) close an AWS account into an irreversible 90-day suspension
from an ordinary cleanup, and (c) delete a tenant's own cluster in `bring-existing-cluster`.
Each required only that cleanup be built from live cluster state, which is the documented
purpose of `extra_actions`.

## Findings I fixed (reviewer-authored, commit `e70f19dd`)

### RF-001 — Non-convergent cleanup plans reachable through discovery
**Impact:** high · **Confidence:** high (probe) · `cleanup.py`

`_check_convergence` ran over the generated `actions` list only, so the convergence property
AF-002 established was unenforced on the discovered half of the plan. A discovered
`IAMRoleSelector` with entirely valid ownership evidence was accepted into a new-account plan
while the `AccountOwnership` that declares it is retained — kro reconciles it straight back.

Probe before fix: plan accepted, `deleted-but-still-declared: ['IAMRoleSelector']`.
Fix: convergence is checked over `[*actions, *extra_actions]`.

### RF-002 — Account closure reachable from a workspace cleanup
**Impact:** high · **Confidence:** high (probe) · `cleanup.py`

A discovered `AccountOwnership` was accepted on ownership evidence in every mode. That object
declares the Organizations `Account`, so deleting it closes the account into an irreversible
90-day suspension — precisely what Design item 4 forbids and what `closure_request` (with its
provisioned-account record and acknowledgement) exists to gate. Ownership evidence cannot
refuse this case, because a genuinely owned account root has valid evidence; ownership is the
wrong question for this kind.

Probe before fix: accepted, with `closes_account=False` while the plan's own `retained` text
claimed the account was retained.
Fix: `_ACCOUNT_ROOT_KINDS` refused in all modes, checked before the ownership guard.

### RF-003 — ADP deleting infrastructure it never created
**Impact:** high · **Confidence:** high (probe) · `cleanup.py`

In `bring-existing-cluster`, discovered `WorkspaceInfrastructure`, `NetworkStack` and
`EKSClusterStack` were all accepted. ADP created none of them in that mode, so this is ADP
destroying a tenant's own cluster and network during a cleanup the mode documents as
namespace-only. The mode's central promise held for the generated plan and not the discovered
one.

Probe before fix: all four kinds accepted.
Fix: `_DELETABLE_BY_MODE` bounds deletable kinds per mode.

### Regression tests
Three tests, each verified to fail against the pre-fix code with `DID NOT RAISE CleanupError`,
plus two positive controls (an owned adoption-record ConfigMap in bring-existing-cluster; a
discovered `NetworkStack` in existing-account-managed, where ADP did create it and the plan
converges) so the guards are boundaries rather than a blanket refusal.

## Security review

- **Secrets:** no credential literal in the diff or the module; `_SECRET_PATTERNS` refuses
  secret-shaped values in rendered output, and the refusal message deliberately does not
  reproduce the matched value (refusals reach logs and CI artifacts).
