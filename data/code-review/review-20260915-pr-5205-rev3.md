## Part 1 — What the previous round asked for

### B8 (false `Paused` from cross-thread settling) — CONFIRMED FIXED

The admission ledger is now scoped per thread and a stop settles only its own scope
(`claude-control.ts:326-411`):

```ts
const outstanding = new Map<string, { ticket: AdmissionTicket; scope: string | null }>();
const scopeOf = (input: HookInput): string | null =>
  (input as unknown as { agent_id?: string }).agent_id ?? null;
// onStop:
for (const [id, entry] of [...outstanding.entries()]) {
  if (entry.scope !== scope) continue;
  outstanding.delete(id);
  gate.settle(entry.ticket);
}
```

Probed in all four directions:

| Scenario | Result |
|---|---|
| `SubagentStop` vs. a live main-thread admission | `activeToolCount` stays **1** (was 0 pre-fix, with `requestPause()` returning `confirmed`) |
| main `Stop` vs. a live subagent admission | stays **1** |
| subagent A's stop vs. subagent B's admission | stays **1** |
| a scope settling its *own* admission | **0** — still works |

The premise is independently supported by the installed SDK 0.3.220 type surface:
`BaseHookInput.agent_id?: string` is the documented subagent discriminator and is absent on
the main thread even in `--agent` sessions; `SubagentStopHookInput.agent_id` is **required**.
Retaining `SubagentStop: [{ hooks: [pause.onStop] }]` (`developer-checkpoints.ts:117`) is
correct — per-scope cleanup is needed; the unscoped ledger was the whole defect.

### B7 (pause withheld forever after an unobservable probe) — CONFIRMED FIXED

`pause-gate.ts:381-402` adds the missing edge:

```ts
noteBackgroundWorkChanged(): void {
  if (this.phase !== 'pause_requested') return;
  if (this.inFlight.size !== 0) return;
  void this.reconfirm();
}
```

`reconfirm()` re-checks the epoch and phase inside `serialize()`, then calls
`confirmIfClear()`, which independently re-reads the probe and withholds on both `null` and
`> 0`. Probed: a pause withheld for an unobservable probe is re-driven to phase `paused`
with events `[active_work, active_work, pause_requested, pause_confirmed]`. All inverse
directions are safe — it does not confirm while a main-thread tool is live
(`pause_requested`, count 1), does not resurrect after `resume()` (`running`), and does not
resurrect after `cancel()` (`cancelled`).

### B7's reason code — FIXED

`releasePause(expired)` now distinguishes the two expiry causes
(`pause-gate.ts:589`): `settle_timeout` when work is still admitted, `background_work`
otherwise. Correct.

## Part 2 — New findings

### FINDING 1 — BLOCKER: an absent optional `background_tasks` becomes an affirmative all-clear

- **Impact severity:** high — false `Paused` while a process is still writing to the repo
- **Confidence:** confirmed by execution
- **Approval impact:** blocks

`claude-control.ts:255-259`:

```ts
noteBackgroundReport(tasks: unknown): void {
  this.seq += 1;
  this.lastReportSeq = this.seq;
  this.lastReportedCount = Array.isArray(tasks) ? tasks.length : 0;
}
```

`background_tasks` is **optional** on both `StopHookInput` and `SubagentStopHookInput` in SDK
0.3.220. When the field is absent, `Array.isArray(undefined)` is false, the count becomes a
hard `0`, and — because `lastReportSeq` was advanced — `count()` returns `0` rather than
`null`. Measured end-to-end:

```
PROBE bg bash                                     = null
PROBE after Stop with NO background_tasks field   = 0
```

Then `requestPause()` returns `{"outcome":"confirmed"}` and the phase goes to `paused` while
the backgrounded process is still running. This is the identical operator-visible failure as
B8 — "Paused" read as "nothing is touching my repository" — and it is reachable through the
hook registration that ships in this PR (`developer-checkpoints.ts:116-117`).

It is also **asserted as intended** at `claude-control.test.ts:1022-1032`:

> *"A non-array is the SDK not reporting any, which is different from the unobservable case above: a report did arrive, it simply named nothing."*

That reasoning does not hold for an *optional* field. "The SDK omitted the field" and "the SDK
sent `[]`" are different facts: only the second is an all-clear. This contradicts the gate's
own documented rule that an unobservable answer must be `null`, never `0` — which is exactly
the rule `claude-control.ts:230-240` spends a paragraph establishing.

**Fix direction:** distinguish absent/non-array from an empty array. Return `null` for the
former (do not advance `lastReportSeq`), `0` only for a genuine `[]`. The test at 1022-1032
must invert with it.

### FINDING 2 — a background report is applied unscoped, so one thread's all-clear vouches for another's work

- **Impact severity:** high (same class as Finding 1) · **Confidence:** confirmed · **Approval impact:** blocks

`claude-control.ts:393` passes `stop.background_tasks` to the observer with **no scope
check**, while the admission ledger three lines above is now carefully scoped. So a subagent
finishing with an empty report advances the sequence past a main-thread `Task` spawn:

```
PROBE after Task spawn        = null
PROBE after sibling all-clear = 0
```

The `outstanding` ledger was fixed for precisely this shape of error; the observer beside it
was not. Fix direction: scope the probe per thread as well, or treat a report as covering
only the scope that emitted it.

### FINDING 3 — a merely *parked* tool poisons the probe

- **Impact severity:** medium (the B7 direction — pause withheld, not falsely granted) · **Confidence:** confirmed · **Approval impact:** should fix

`noteToolStart` is called at the **top** of `preToolUse`, before `await gate.admit(...)`. A
`Task` or backgrounded `Bash` that only parks at the barrier and never executes still
registers as a spawn, flipping the probe to `null` and withholding later confirmations —
verified: `PROBE held at barrier = 1, probe now = null`. Nothing is running behind a tool
that never ran. Move the spawn note to after admission succeeds.

### FINDING 4 — MINOR: expiry reason text contradicts its own failure code

`pause-gate.ts:592` always reads *"…background work behind completed tools stayed
unobservable"*, even when the probe returned an observable positive count (measured with a
count of 3). The `failure` code is right; the human-readable string an operator uses to
decide whether a retry is worthwhile is wrong for that state.
