## Blocking

### B1 — The F1 verification path is unreachable for an API-refused termination
`.github/workflows/eval-cli-uplift.yml:573-576`
**Impact: MEDIUM · Confidence: CONFIRMED · Approval: BLOCKING**

The terminate loop retains `check=True` from before this PR:

```python
for item in targets:
    subprocess.run(["aws", "ec2", "terminate-instances", "--instance-ids", item["id"]],
                   capture_output=True, check=True)
```

`check=True` raises `CalledProcessError` on a non-zero exit. The new `observed`
poll loop and `recovery_report` are both *after* this loop, so any AWS refusal
aborts the step before either runs.

This matters because of which half of the F1 scenario it covers. The PR's own
rationale names two failure modes:

| Failure mode | AWS behaviour | Covered by the fix? |
|---|---|---|
| Stuck lifecycle hook / `stopping` state | exits 0, instance survives | **Yes** — poll observes non-`terminated`, `clean: false` |
| `DisableApiTermination` set | returns `OperationNotPermitted`, **non-zero** | **No** — `check=True` aborts first |

So the headline example in the commit message and the log's F1 write-up — the
termination-protected instance — is the case that still does not reach the new
verification. Reproduced the control flow directly: substituting a failing
command for the terminate call raises `CalledProcessError` and neither the poll
loop nor `recovery_report` is reached.

The consequence is **not** a silent leak: the step still exits non-zero, so the
job fails loudly. That is why this is MEDIUM, not HIGH. But the operator gets a
raw `CalledProcessError` traceback instead of the structured `outstanding` /
`observed` report the fix exists to produce, and the run aborts on the *first*
refusal, leaving every subsequent target in `targets` neither terminated nor
reported. On a multi-instance sweep that is strictly worse than the report the
fix was written to deliver.

Compare the in-run path, which this PR explicitly cites as the correct model
(`live.py:488-504`): it issues the terminate call and then polls to `terminated`
regardless, raising `PortError` only after the observation. The sweep should
mirror that ordering, not just its polling.

**Fix:** drop `check=True` and record the failure, letting the existing
observation logic classify it — the poll already treats an unreachable state as
`unknown`, which lands in `outstanding` and raises `SystemExit`. Something like:

```python
for item in targets:
    request = subprocess.run(
        ["aws", "ec2", "terminate-instances", "--instance-ids", item["id"]],
        capture_output=True, text=True,
    )
    if request.returncode != 0:
        # OperationNotPermitted (DisableApiTermination) lands here. Do NOT abort:
        # the poll below must still observe and report this instance, and the
        # remaining targets must still be attempted.
        print(f"Terminate request for {item['id']} failed: {request.stderr.strip()}")
```

Then add a test asserting a refused terminate still yields
`clean: false` with the instance in `outstanding` — the current tests all enter
`recovery_report` with a pre-built `observed` map, so none of them exercise this
ordering.

## Non-blocking

### N1 — The new sweep wiring has no workflow-invariant test, which is how F2 survived
**[CLOSED by `298c575` from a concurrent review pass — see Reconciliation.]**
`tests/unit/test_cli_uplift.py:5290+`
**Impact: LOW · Confidence: CONFIRMED · Approval: NON-BLOCKING (recommend before merge)**

The PR correctly diagnoses why CI never caught F2: the conversion lived in inline
workflow YAML that unit tests cannot import, and every pre-existing sweep test
passed `LaunchTime` as a float. Moving the logic into `cleanup.launch_epoch` fixes
the *library* half. The *wiring* half is still unpinned.

The file has a dedicated workflow-invariant section (`WORKFLOW_PATH`, "a future
edit could quietly drop any of them and every test above will still pass") that
already asserts on the sweep's `run` body — `recoverable_instances` and
`terminate-instances` are both pinned there. I checked whether any invariant test
mentions the new wiring:

```
'launch_epoch'       asserted: False
'describe-instances' asserted: False
'observed'           asserted: False
'mktime'             asserted: False
'recovery_report'    asserted: False
```

So a future edit reverting the workflow to `time.mktime(...)`, or dropping the
poll loop and passing a list of IDs again, leaves all 315 tests green.
`recovery_report`'s signature change makes the second case fail at runtime rather
than silently, which helps — but only on a live dispatch, which is precisely the
expensive place to find out.

**Fix:** extend `test_recovery_job_runs_even_when_the_evaluation_was_cancelled`
(or add a sibling) with `assert "launch_epoch" in body`, `assert "describe-instances"
in body`, and `assert "mktime" not in body`. Three lines, and they close the
exact regression class this PR was filed to fix.

### N2 — Sequential poll is bounded but can consume the job timeout
`.github/workflows/eval-cli-uplift.yml:585-598`
**Impact: LOW · Confidence: CONFIRMED · Approval: OPTIONAL FOLLOW-UP**

The poll is per-instance and sequential: 24 probes with 23 × 5s sleeps ≈ 115s
worst case each. The `recover` job has `timeout-minutes: 20`, so ~10 stuck
instances exhaust it and the job is killed mid-sweep — losing the report for
everything not yet processed. Not reachable in normal operation (a sweep finds
one or two instances), and the 115s bound is a sensible match for
`cleanup_wait_seconds: 120`. Worth a comment noting the interaction, or issuing
all terminates first and then polling in a single pass over the set.

## Security review

Run against this diff. **No vulnerabilities introduced.** Zero candidates reached
the reporting threshold.

- The new poll uses list-argv `subprocess.run` with no `shell=True`; `item["id"]`
  originates from the EC2 API's own `InstanceId`, not from a tag value. Tag values
  — the only attacker-influenceable field — are used solely for string comparison
  (`cleanup.py:382`, `:426`) and never reach an argv.
- New code sits inside a quote-delimited heredoc (`python - <<'PY'`); the workflow
  diff adds no `${{ }}` expansion.
- The change is **narrowing**, not widening: selection logic
  (`recoverable_instances`, `owned_by_run`, the required `prefix`) is untouched, and
  the `launch_epoch` fix *reduces* the pre-existing over-termination risk on
  east-of-UTC runners.
- Every probe error path fails closed (state stays `unknown` → `outstanding` →
  `SystemExit`).
- The new `observed` field carries only instance IDs and EC2 state names, has one
  consumer (a `print`), never enters `report.build()` or `report.schema.json`, and
  the `recover` job has no `upload-artifact` step.
- No `permissions:`, `environment:`, `secrets.*`, `if:` or `runs-on:` line changed.
  The invariant tests at `:5290-5375` still bind to the modified step.

Pre-existing and explicitly **not** regressions from this PR: F3 (free-form
`environment` plus the repository-scoped `secrets.AWS_E2E_ROLE_ARN` fallback), F5
(redacted token forwarded into downstream journeys), F6 (`report.SECRET_KEYS`
omits `credential`). F3 remains the one to settle before the first live dispatch;
it is a secrets/environment ownership decision for the repo owner, not a code fix.
