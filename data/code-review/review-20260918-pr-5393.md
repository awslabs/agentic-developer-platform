### Round 4–5: the bypass class three hardening rounds could not see

The validator's patterns match **contiguous** text, so a single character placed *inside* a
real secret ARN left every one of them unmatched while a downstream normalisation restored the
address byte-for-byte:

```
'arn:aws:secretsmanager:us-east-1 :123456789012:secret:nebius-AbCdEf'   was ACCEPTED
re.sub(r"\s+", "", stored) == the real ARN                              -> True
```

Exhaustive single-character insertion at every position of a real ARN found **32 accepted,
byte-exactly recoverable values**. Not confined to ARNs (`'AKIA IOSFODNN7EXAMPLE'` was stored
and strips back to a live access key id) and not confined to whitespace (escaping the
structure walked past the ARN pattern the same way). Both reached the model `@validates` hook
and the `cloud_accounts` list column.

**I made the same class of mistake twice while fixing it, and both times measurement caught
me rather than reasoning:**

1. My first escape fix decoded only `%3A`. That is precisely the error the three prior rounds
   kept repeating — narrow the hole, leave the class open — and my own docstring overclaimed
   ("any consumer that URL-decodes"). Verified by execution at `caae955d`: `%61rn:aws:...`
   (an encoded `a`), `&#58;`, `:` and lowercase variants were all still accepted.
2. Generalising to full percent/entity/`\uXXXX` decoding then repeated it one level up:
   decoding a fixed *number* of layers left `%253A` accepted, because one `unquote` pass only
   turns it into `%3A`. Depth must not decide the outcome, so the value is now decoded until
   it stops changing.

**Rule ordering was kept deliberate.** The whitespace rule is *residual* — placed after the
ARN and secret rules — so an interior-spaced ARN is still reported as **an ARN** and a split
access key as **secret material**. My first attempt put it first and broke two existing tests
by relabelling every one of these as "whitespace". The accurate reason is what an operator
acts on.

**Dead code in my own fix, found by mutation, not by inspection.** I initially matched four
recoverable forms. Reverting two of them changed no test result — they were dead. Rather than
just deleting them I established *why*: `%`, `&`, `#`, `;` appear in none of the pattern
character classes, so decoding can only ever **create** a match, never destroy one, which
makes the fixed point strictly subsume every partial decode. A 200k-case adversarial search
over interleaved escapes and structure-breaking entities found **0** counterexamples. Each
surviving form is mutation-proven load-bearing (reverting any one fails 1–4 tests).

**I reverted one of my own changes for cost.** I had made the AWS key-id pattern
`re.IGNORECASE`. It guards nothing — `akiaiosfodnn7example` is not a usable key id, AWS key
ids being case-sensitive uppercase, and no decode step recovers the uppercase form — and it
was not free: over a 300k-handle corpus it refused the legitimate
`u3pXKcVTL63jCtJRfakIaTObUB2FgWClh5Vftqnizabt`, where `akIaTObUB2FgWClh5Vft` is an incidental
mixed-case run. The trade that justifies this rule's *uppercase* false refusals — refuse
loudly rather than silently store a live key — does not carry when there is no live key to
store. The uppercase form stays refused, and a test now pins that reasoning so the
case-insensitive version is not reintroduced.

**The human commit `f9f0e908`, reviewed not assumed.** It makes the migration refuse on
*every* `credential_registry` row rather than only rows with a non-empty `secret_arn`, and
drops the `UPDATE ... SET adp_credential_id = ''` backfill. It is correct, and it fixes a real
defect: a pre-012 row cannot already hold a verified ADP credential ID because the column does
not exist until this revision creates it, and the old backfill manufactured a value the
model's own validator rejects.

### On the third repair — stated precisely, because the distinction matters

`credential_registry.adp_credential_id` was guarded twice (model `@validates` + Pydantic
`field_validator`). `cloud_accounts.adp_credential_ids_json` — **the other table issue #5046
names by file** — was guarded at neither, and it is an unbounded `Text`. A caller could store
a copied secret ARN or a whole PEM block under the new compliant-looking column name.

**It is not a vulnerability, and I am not reporting it as one.** I verified each decisive
claim myself rather than accepting the scanner's or the filter's word:

- Nothing resolves that column: repo-wide grep finds exactly one writer and one reader, both inside this module.
- `POST /accounts` requires `(Scope.ORGANIZATION, Permission.PROVISION)` (`endpoint_inventory.py:224`).
- The data is org-scoped and self-owned — an operator writing a bad value to their own org's row.
- `git show origin/main:...` confirms the pre-PR `secret_arns` field had **no validator either**, so this is not a regression this PR introduced.

**It is a real incompleteness.** Issue #5046 names `cloud_account.py` explicitly, and this
PR's own commit message claims the check is "enforced on the model (every writer)". Before
`3aba347d` that claim was true only of the sibling table. One of the 6 new tests guards the
opposite error: that IAM **role** ARNs keep being accepted.

I also moved both `field_validator`s below their field declarations. The PR had placed them
mid-class, so `irsa_role_arn` / `irsa_role_arns` trailed *after* a validator and read as
though outside the model. Harmless as written — I verified both are still in `model_fields`
by execution — but it invites a real bug on the next edit.

## Security review

`/security-review` was run on the branch. It reported **no HIGH or MEDIUM newly-introduced
vulnerability**, which I did not take as the finding — I treated its one substantive
observation as a lead and checked it myself, because scanner output is not proof either way.
That observation (my escape decode handled only `%3A`) turned out to be **correct and
under-stated**: by execution, five distinct values were still accepted at `caae955d`, and the
generalised fix then revealed the multi-layer case as well. Both are closed in `854095df`.

Two things I checked and am deliberately **not** reporting as vulnerabilities, having verified
the decisive claim in each rather than inferring it:

- **Information disclosure through refusal messages.** These reach a 422 body and the logs.
  The ARN branch previously echoed `candidate[:32]`, which for a value with no distinctive
  prefix (a bare 40-char AWS secret access key, a JWT) reflected live secret material. It now
  echoes only the *structural* matched span, and `test_no_refusal_branch_echoes_submitted_secret_material`
  asserts this for every vector including the new interior and escaped ones — the new rules
  added fresh ways to reach that branch, so the property is re-checked rather than assumed to
  still hold.
- **The residual whitespace rule is not a substitute for the shape rules.** It fires only for
  material whose shape is unrecognised. That ordering is what keeps the operator-facing reason
  accurate, and it is pinned by tests rather than by comment.

No secrets, keys, tokens or credentials appear in any changed file, the commit messages, or
this review. The example values used throughout are AWS's published documentation
placeholders (`AKIAIOSFODNN7EXAMPLE`, `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY`), not live
material.
