## Findings (by confidence)

### HIGH — merge blockers
- **FIXED**: `otel-collector.tf:145-188` — Collector config was missing `extensions.health_check` declaration and `service.extensions: [health_check]`. Without this, port 13133 is not listening and liveness/readiness probes would fail → CrashLoopBackOff. **Fixed in commit 3c6ad209.**

### MEDIUM — discuss before merge (accepted as-is)
1. **`scaledjob-netpol.tf:98-112`** — The collector egress rule in the agent scaledjob NetworkPolicy is unconditional (not gated by `enable_agent_otel`). When the flag is off, this just adds a rule that never matches (no pod with label `adot-collector` exists). **Benign** — saves a dynamic block that would complicate the netpol and adds no security risk; noted for completeness.

2. **`OTEL_RESOURCE_ATTRIBUTES` is static** — The env var carries only `deployment.environment` and `service.namespace`. Per-task dimensions (tenant.id, enduser.id, persona) are NOT included. This is correct for v1 (these values are per-SQS-message and would require entrypoint.py changes + image rebuild to compose dynamically). The architect's review (Comment 11) acknowledges this and recommends a follow-up.

3. **Collector image pinned to `v0.40.0`** — Good practice for reproducibility. Should be bumped periodically via a Dependabot-like process or tfvar override.

### LOW — follow-up candidates
1. **ADOT collector single-replica** — No PodDisruptionBudget. If the collector pod is evicted during node replacement, there's a brief telemetry gap. Acceptable for dev (telemetry loss ≠ run failure), but prod should consider 2 replicas.
2. **Log stream naming**: `otel-{tag}` — the `{tag}` template may resolve to an empty string for some SDK log records. Consider `otel-${HOSTNAME}` or similar for better traceability in CloudWatch.
3. **No `resource` processor to inject cluster-level attributes** (cluster name, node) — the SDK resource attributes are sufficient for v1 but a `resourcedetection` processor could enrich spans with EKS metadata in the future.

## Security Review

### Secrets/Credentials
- No hardcoded secrets, tokens, or API keys in any file
- IRSA used for collector AWS access (no static credentials)
- No secrets mounted into the collector pod

### IAM Scope (IRSA)
- X-Ray: `PutTraceSegments`, `PutTelemetryRecords`, `GetSamplingRules`, `GetSamplingTargets` — minimal for trace export
- CloudWatch Logs: scoped to ARN pattern `adp-*-agent-otel-*` — cannot write to arbitrary log groups
- CloudWatch Metrics: `PutMetricData` with `cloudwatch:namespace = ADP/AgentTelemetry` condition — cannot pollute other metric namespaces
- OIDC trust condition locks to specific service account (`adp-agents:adot-collector`) — no cross-namespace escalation

### Network Policy
- Collector egress limited to DNS (53) + HTTPS (443) — correct minimum for AWS API calls
- Agent→collector scoped to pod selector + port 4317 only — cannot be abused for arbitrary intra-namespace communication

### Container Image
- `public.ecr.aws/aws-observability/aws-otel-collector:v0.40.0` — official AWS image, pinned tag, no `:latest`

### Data Exposure
- Content-unmasking flags (`OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT`) are explicitly NOT set — structural telemetry only (durations, token counts, tool names)
- No sensitive data (prompts, tool output, API keys) flows through the collector in v1

### Findings
- **No security issues found.** The implementation follows the principle of least privilege.

## Recommendation
**APPROVE** — after the health_check extension fix (committed), all acceptance criteria are met. The implementation is clean, well-gated, follows established patterns (IRSA, NetworkPolicy, conditional `count`), and introduces no security risk.
