## Findings (by confidence)

### HIGH — merge blockers

### MEDIUM — discuss before merge (non-blocking, fix recommended)

1. **`infra/main.tf:89` — S3 lifecycle rule missing `filter {}` block**:
   The lifecycle configuration omits the required `filter` attribute. Terraform AWS provider currently warns:
   > "No attribute specified when one (and only one) of [rule[0].filter, rule[0].prefix] is required. This will be an error in a future version of the provider."
   
   Fix: add `filter {}` (empty filter = apply to all objects) inside the `rule` block. Not a blocker because the current provider version accepts it, but will break on next provider major version.

2. **`boto_helpers.py:83-100` — `_build_platform_session` IRSA path creates STS client with `aws_access_key_id=None`**:
   When IRSA env vars are present, the code creates an STS client with explicit `None` credentials to avoid using the cross-account assumed-role creds from `AWS_ACCESS_KEY_ID` env. While `boto3.client(..., aws_access_key_id=None)` doesn't crash today, it bypasses normal credential resolution in a fragile way. If `AWS_WEB_IDENTITY_TOKEN_FILE` + `AWS_ROLE_ARN` are both set, the better approach is to let `boto3.Session()` handle IRSA natively (it has a built-in web identity token provider in its credential chain). However, the `AWS_ACCESS_KEY_ID` env var from the cross-account assume takes precedence in the default chain, which is why this explicit approach is used. The current implementation is defensible — just noting the fragility.

### LOW — follow-up candidates

1. **Duplicate `requirements.txt` files**: Both `modules/platform-deploy-mgmt/requirements.txt` and `modules/platform-deploy-mgmt/platform_deploy_mgmt/checks/requirements.txt` exist with identical contents (`boto3>=1.28.0`, `botocore>=1.31.0`). The workflow installs from the root one. The inner one is dead code — consider removing to avoid drift. Not a blocker.

2. **Phase 1 check 1.7 severity vs spec**: Check 1.7 (`backend.tfvars contains account ID`) and 1.8 (`State bucket contains state files`) are `Severity.SOFT`. This is correct per the issue spec (they're informational/predictive), but differs from 1.1-1.6 which are all `HARD`. The distinction is intentional and appropriate.

3. **Concurrency key in verify workflow**: Uses `verify-${{ inputs.customer_account_id }}-${{ inputs.phase }}` — prevents parallel verification runs against the same account+phase. This is correct but could be noted: running `phase=all` vs `phase=1` would NOT conflict due to different keys.

4. **`checks/__main__.py`**: imports from `.runner` but the workflow invokes `python -m platform_deploy_mgmt.checks.runner` directly. The `__main__.py` would only be used via `python -m platform_deploy_mgmt.checks` (without the `.runner` suffix). Both paths exist and work; minor inconsistency.
