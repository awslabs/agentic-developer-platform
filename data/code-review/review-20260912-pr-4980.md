## Must-fix (1 of 2): the harness's teardown check tests an attribute that is never written

**Impact severity:** Medium · **Confidence:** High (verified) · **Approval impact:** blocks approval

`platform/scripts/agent-control-eval.py:1058` checks that terminal teardown
cleared the private control fields from the invocation row:

```python
key for key in ("control_token", "control_address", "control_port", "control_expires_at")
if key in item
```

The writer never writes `control_expires_at`. It writes
`control_token_expires_at` — `modules/agent-factory/agent-worker-image/lib/invocation_status.py:204`
(in `_CONTROL_ATTRIBUTES`) and `:299` (in the `SET` expression). The gateway
reads the same longer name at `modules/gateway/src/activity/control_service.py:481`.

So the fourth conjunct of this check can never fail. If a future change to
`clear_control_endpoint` left the expiry behind, the harness would report clean.
The check's own error message states the stake — *"Pod IPs are reused, so a stale
address eventually names a different tenant's pod"* — and this is the check that
enforces it.

Why it matters more than a typo: this harness is a deliverable of this story and
the named post-deploy smoke for it, and evaluation #3967 owns live acceptance on
top of it. A check that passes vacuously produces a false acceptance signal at
exactly the moment someone is deciding the story is complete.

Mitigating: the other three names are correct, and they are the more sensitive
attributes (token, address, port). This is a partial blind spot, not a dead check.

**Fix:** `control_expires_at` → `control_token_expires_at`. Consider importing or
mirroring `_CONTROL_ATTRIBUTES` so the two lists cannot drift again — the same
tuple already exists precisely to stop this class of drift on the writer side.

## Security review

Per the mandatory `/security-review` step. One candidate was surfaced and did not
survive verification.

**Candidate (rejected):** the in-pod listener's generation check at
`modules/agent-factory/agent/src/control-listener.ts:285` is skipped when the
`x-adp-control-generation` header is absent or empty, which reads like a
replay-protection bypass.

**Why it is not a finding.** The generation is not a secret and adds no
authentication strength:

- A fresh token is minted per generation — `entrypoint.py:2125`
  (`secrets.token_urlsafe(32)`, 256-bit CSPRNG) — and token and generation are
  bumped in one atomic update (`invocation_status.py:297-317`,
  `SET control_token = :t ... ADD control_generation :one`). Generation N and N+1
  never share a token, so token-match with generation-mismatch has no live path.
- The generation is readable by anyone holding the token: the gateway reads both
  from the same row (`control_service.py:480`) and an authenticated `/agent/ping`
  echoes it (`control-listener.ts:234`). Mandating the header adds zero bits an
  attacker must guess.
- The listener is constructed per-process from env (`agent-worker.ts:1972-1979`);
  it dies with the pod, so no gen-1 process can hold gen-2's token.
- The "duplicate header yields `string[]`" mechanic is factually wrong — Node
  joins duplicate ordinary headers into one comma-separated string, and
  `parseInt` still compares the first value strictly.
- The absent-header behaviour is deliberate and tested:
  `control-listener.test.ts:896-901` ("Absent is not stale: the header is
  optional").

That makes it a mis-routing guard, not an authorization boundary — a hardening
preference, not a vulnerability. Not reported.

**Verified sound** (each traced against code, not assumed):

| Area | Result |
|---|---|
| Tenant + owner authz | `resolve_target` requires tenant match **and** (`user_id` or `root_human_id`) — a deliberate tightening of `service.py:get_invocation`'s either-or `if/elif`. Same-tenant non-owner cannot reach control. |
| Enumeration oracle | Unknown, cross-tenant, and same-tenant-not-owned all raise byte-identical `ControlError(404, "run not found")`. |
| Identity source | Both adapters use `current_user.org_id`, never the caller-influenceable `attributed_org_id`. |
| Status ordering | 404 → 503 → 410 → 501 → 409 on both adapters, authorization first. Body validation precedes authz on POST but its 400/413 is identical whether or not the run exists. |
| SSRF | `ipaddress.ip_address()` literal-only parse rejects hostnames/URLs, closing the DNS-rebinding window; then loopback/unspecified/multicast/reserved, then `169.254.0.0/16` + `fe80::/10` by name, then non-`is_global`, then a **pinned** port from gateway config (never from the row), then pod-CIDR membership. Empty CIDR list refuses everything (409), and the deploy default is empty — fail-closed. `follow_redirects=False`; production client `trust_env=False`. |
| Token exposure | Absent from all four public models; `ControlTarget` is a frozen dataclass, so FastAPI cannot serialize it. No log line emits it (port/generation/expiry only). Child-process env only; `os.environ` untouched. |
| AuthN ordering | `handle()` authenticates before URL parse, body read, and `JSON.parse`. `start()` refuses to listen with no bind address, no token, or invalid port; never falls back to `0.0.0.0`. |
| NetworkPolicy | Selectors validated against real objects: `app.kubernetes.io/name=agent-scaledjob` (`scaledjob.tf:205`) and `app=bedrockgateway` (`deployment.yaml:24`). Both in **one** `from` block, i.e. ANDed. `policy_types=["Ingress"]`, applied unconditionally. |
| Flag defaults | Fail-closed on all four surfaces; no default of `true` anywhere. |
| Harness | No `subprocess`/`shell=True` — emitted "commands" are evidence strings. Token never enters an `Observation`. `run_cleanup` deletes only explicitly-named `(event_id, arrived_at)` pairs; no scan/prefix/wildcard. |

## Reasoned deviation from the spec (accepted)

The issue says "fix the dead egress selector." The PR **removes** the rule
instead. I checked this rather than taking it on faith, and I think removal is
correct: the rule's `namespace_selector` matched a *pod* label that exists on no
Namespace, so it permitted zero traffic and nothing depends on it. Repairing it
would have opened agent pods → gateway `:8080`, and the gateway trusts
`X-Caller-Identity` unsigned under `BG_TRUST_APIGW_HEADERS=true` with no ingress
policy of its own. Agent pods process untrusted repository content by design, so
"repair" here would have created the escalation path the dead rule accidentally
never had. Removal satisfies the intent (no dead selector remains) and is
strictly safer. The PR documents this reasoning inline. I am accepting it — the
only residue is must-fix #2, the description that still claims a repair.

## Validation gaps — what CI does *not* prove

Stated plainly so nobody reads green checks as more than they are:

1. **No live acceptance.** Every test in `agent-control-ci.yml` is a unit or text
   assertion and the workflow deliberately requires no AWS credential. Nothing
   here proves the path works against a real cluster. Evaluation **#3967** owns
   that, and per the issue, CI-green and merged do not close it.
2. **Nothing is deployed.** The issue requires S1 infrastructure to be applied and
   evidenced via `gh workflow run webhook-ingress-deploy.yml -f account_id=879318057152`.
   That has not happened. Merging does not prove the intended account was
   deployed.
3. **The NetworkPolicy is asserted, not exercised.** The 29 manifest tests check
   the Terraform *text*. That a policy admits the gateway and denies everything
   else is only provable in a cluster — and it is what the removed-egress
   reasoning rests on.
4. **The generation header's optionality is untested for absent-vs-required
   semantics.** Sound today (see the security section), but the shape is
   inherited silently by later stories. Worth an explicit test when a verb lands.
5. **Zero verbs implemented.** `SUPPORTED_ACTIONS` is an empty `frozenset` on
   both sides; every verb returns 501 and every capability reports `false`. This
   is the story's design, not a shortfall — but it means the command path's
   *behaviour* is unexercised end-to-end by construction.

  the nightly `Update Baselines` job needs `git config user.email` set, and the

  rather than restating it, so must-fix #1 cannot recur.

  the generation check — sound today, but the reasoning is subtle enough to
