## Findings (by confidence)

### HIGH — merge blockers

- **`agent_learning/2026-07-02-issue-2651-learnings.md`**: This file is in the `agent_learning/` directory which is listed in `.gitignore` (line 63: `agent_learning/`). The gitignore comment says "Agent-generated per-issue learnings dumps — do not commit to repo." The file was force-added (bypassing gitignore) and committed. **This file should be removed from the PR.** While there ARE historical `agent_learning/` files on `main` (they were committed before the gitignore rule was added), the gitignore explicitly prohibits new commits to this directory.

### MEDIUM — discuss before merge

- **Branch naming mismatch**: The PR branch is `agent/issue-2651` but the issue being assigned is #2653 (which is also the PR itself, labeled as closing #2651). This is technically fine since the work product is for #2651, and the branch naming convention says `agent/issue-<N>` where N is the driving issue. Just noting this won't trigger the reviewer workflow for issue 2653 specifically (but that's the expected behavior — #2651 is the driving issue).

- **Design Section 7 workflow example uses `workflow_call` reusable workflow calls** (lines ~520-530) but the learnings file (line 43) correctly notes that existing destroy workflows only have `workflow_dispatch` triggers (confirmed by codebase grep). The design mentions this as an implementation requirement but could be clearer about the prerequisite: "Per-module destroy workflows need a `workflow_call` trigger added before the orchestrator workflow can use reusable workflow calls." This is a design completeness observation, not a correctness bug — the implementation child issues (B-D) would naturally surface this.

- **`gbrain-infra-destroy.yml` is not mentioned** in the design document. A 6th destroy workflow exists (`.github/workflows/gbrain-infra-destroy.yml`). The learnings file acknowledges this (line 42) and explains it's excluded because gbrain is not part of #2562's deploy inventory. This is acceptable but the design should briefly note its exclusion and rationale for completeness.

### LOW — follow-up candidates

- **Timing estimates in Appendix B** are "based on observed destroy times from prior teardowns" but no specific prior teardown is cited. These are reasonable estimates but may need calibration during implementation testing.

- **Error Scenarios (Appendix C)** don't cover a scenario where a phase succeeds but leaves resources in a "deleting" state (e.g., RDS instance in "deleting" status for 5+ minutes). Terraform would see it as still existing on a re-run. This is a minor edge case that implementation testing would reveal.

- **Section 7 shared functions architecture** — the diagram shows `undeploy-phases.sh` is sourced by both tracks, but the workflow track (`undeploy.yml`) can't directly source bash files if it's calling reusable workflows. The design acknowledges two options (reusable calls vs. inline phases) but doesn't commit to one. This is appropriate for a design doc (implementation decides), but worth tracking.
