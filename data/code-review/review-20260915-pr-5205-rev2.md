### B7 (new) — a pause that cannot observe background work never confirms, and expires silently

This is the same *class* of defect as the fixed B4, on the path B4's fix does not
cover. `settle()` re-drives confirmation when in-flight work reaches zero
(`pause-gate.ts:344`), which is what fixed the late-settling-tool case. Nothing
re-drives it when the *background-work probe* is what withheld confirmation.

The probe answers `null` — "cannot tell" — for the whole window between a
backgrounded tool starting and the next `Stop`/`SubagentStop` report
(`claude-control.ts:262–266`). A pause requested in that window is withheld
correctly. But when the report later arrives and the probe becomes `0`,
`noteBackgroundReport` only updates the observer; it calls nothing on the gate. The
pause sits in `pause_requested` until its budget expires.

Reproduced with a throwaway probe driving the real hooks and gate — a delegated
`Task` that completed normally, then a `SubagentStop` reporting zero background
tasks:

```
observer.count() after Task completed: null
pause outcome: requested  ("background work behind completed tools is not observable")
observer.count() after SubagentStop reports []: 0
phase after background observably clear: pause_requested      <-- never confirms
final events: pause_requested -> pause_unavailable(settle_timeout) -> pause_released(expired=true)
```

Identical result for a backgrounded `Bash` (`run_in_background: true`).

**Failure scenario:** an operator pauses a run whose last tool was a `Task` or a
backgrounded `Bash`. The subagent finishes seconds later and the run is genuinely
quiescent, but the dashboard shows "pausing…" for the full 30 minutes, then the run
resumes by itself. The `pause_unavailable(settle_timeout)` that precedes the release
is the B4 fix working — so the operator is at least told — but the reason it gives
("admitted work did not reach a safe boundary") is wrong: admitted work reached zero
long before. The delegated/background case is one the issue calls out by name as
required coverage.

**Impact:** high — this is the story's headline promise failing on a common tool
shape, and `Task` is used constantly by these agents. **Confidence:** high —
reproduced twice with the shipped code, no mocks. **Approval impact:** blocker.

**Suggested fix:** give the observer the same edge the in-flight counter has. Have
`ClaudeBackgroundWorkObserver.noteBackgroundReport` notify the gate (an injected
callback keeps the gate provider-neutral), and expose a gate method that re-runs the
existing `reconfirm()` path. `reconfirm()` already guards on epoch and phase, so the
new caller needs no new concurrency reasoning. The `settle()` re-drive and this one
should share it — the asymmetry between the two withholding reasons is exactly how
this hid.

### B8 (new) — a subagent finishing settles the main thread's tool admissions, and the gate then confirms a false `paused`

This is the failure the story exists to prevent, reachable through ordinary tool use
with no operator error and no adversary.

`createClaudePauseHooks` keeps one session-wide `outstanding` map of
`tool_use_id → AdmissionTicket` (`claude-control.ts:316`). `onStop` settles **every**
ticket in it unconditionally (`claude-control.ts:379–380`). The comment justifying that
is sound for what it describes — "the turn has ended, so nothing is still executing
*inside* it" — but `developer-checkpoints.ts:117` registers the same callback for
`SubagentStop` as well as `Stop`, and `SubagentStop` is not turn-end. The pinned SDK
types it with a **required** `agent_id` (`sdk.d.ts:6809–6812`; `BaseHookInput.agent_id`
at `:176` is documented "present only when the hook fires from within a subagent"), i.e.
it fires each time one delegated subagent finishes while the main turn is still live.

So one subagent completing settles the main thread's still-running admissions. The same
file already knows to make this distinction — `checkpointReminder`
(`developer-checkpoints.ts:51`) filters on `input.agent_id`. The pause hooks do not.

I checked whether the background-work probe saves it, since a `Task` sets
`lastSpawnSeq` and should make `count()` answer `null`. It does not: `onStop` calls
`observer.noteBackgroundReport(...)` **before** the mass-settle
(`claude-control.ts:372`), so the subagent's own `background_tasks: []` bumps
`lastReportSeq` past `lastSpawnSeq` and flips the probe from `null` to `0` in the same
callback that clears the tickets. Nothing is left to withhold on.

Reproduced against the shipped hooks and gate — a main-thread parallel batch of a
delegated `Task` plus a long foreground `Bash`, then `SubagentStop` for the subagent:

```
inFlight after batch admitted   : 2
inFlight after SubagentStop     : 0     <-- the Bash is still running
backgroundWorkProbe             : 0
pause outcome                   : {"outcome":"confirmed"}
gate phase                      : paused
events                          : [... pause_requested, pause_confirmed]
activeToolCount after real Bash finished: 0
```

The late real `PostToolUse` for that `Bash` is a no-op — `settle()` ignores an unknown
ticket (`pause-gate.ts:347`) — so the count never self-corrects.

**Failure scenario:** an agent delegates a `Task` and, in the same batch, starts a long
`Bash` (a build, a migration, `rm -rf` on a work tree). The subagent finishes first. An
operator pauses. `bindGateTransitionsToStore` mirrors `pause_confirmed` into
`store.setPhase('paused')` and settles the journal command `applied` with the reason
"no new tool action can start" (`control-command-apply.ts:69–72`), while the `Bash` is
mid-write. That is a genuine False-Paused with `active_tool_count: 0`.

**Reachable today, in one respect.** The pause half is latent: `IMPLEMENTED_CONTROL_VERBS`
is empty, so `requestPause` returns `unavailable` from the capability intersection
(`claude-control.ts:614`) and no operator can confirm a false pause on this branch. But
`bindGateTransitionsToStore` is wired unconditionally once the listener starts
(`agent-worker.ts:2181`), and the `active_work` mirror needs no verb — so
`GET /agent/state` (`control-listener.ts:329` → `control-state.ts:365`) already reports
`active_tool_count: 0` while a main-thread tool runs, any time a subagent stops. The
false-quiescence signal is live on the read path now.

**Not covered by any test.** `grep -rn SubagentStop src/*.test.ts src/harnesses/*.test.ts`
returns nothing — the branch registers the hook and asserts nothing about it.

**Impact:** high — false containment is the one outcome this story is defined against,
and `Task` plus parallel batching is everyday behaviour for these agents.
**Confidence:** high — reproduced directly against the shipped code, and the SDK types
confirm the event semantics. **Approval impact:** blocker.

**Suggested fix:** scope the mass-settle to main-thread `Stop` — an early
`if (input.agent_id) return {}` before the loop, mirroring the existing guard at
`developer-checkpoints.ts:51` — or key `outstanding` by `agent_id` and settle only that
subagent's slice. Related, in the same area: letting a `SubagentStop`'s
`background_tasks` advance `lastReportSeq` lets one subagent's all-clear vouch for a
still-running sibling `Task`, which is precisely what the sequence-number design at
`claude-control.ts:242–267` was built to prevent. Please add a test for each: a
`SubagentStop` arriving mid-batch must not reduce `activeToolCount`, and must not let a
pause confirm.

## Optional follow-ups (not blocking)

- `control-command-apply.ts` could depend on a neutral pause interface instead of
  `Pick<ClaudeControlAdapter, ...>`; it is type-only today, so nothing leaks, but the
  neutrality is a convention rather than a constraint.
- `requestPause({timeoutMs})` accepts a value above `defaultTimeoutMs`, so
  `safeBudget()` can exceed the `maxParkDurationMs()` the hook timeout is derived
  from. Unreachable today — nothing passes `timeoutMs` — but it is a latent
  barrier-breach source if a caller ever does. A clamp to `defaultTimeoutMs` would
  close it.
- The experiment's `fixture_service_calls: 0` is a fact about the fixture's design,
  not a measurement. The code comment says so; the artifact does not.
- `claude-control.ts:227–229` asserts *"Not an assumption: a tool that never requested
  backgrounding has nothing behind it."* That is false for shell-level detachment
  (`nohup … &`, `setsid`, `& disown`), which sets neither `Task` nor
  `run_in_background`. I do not think the classifier can or should try to parse shell —
  treating every `Bash` as unobservable would mean pause never confirms — so this is a
  comment fix, not a code fix: say that the probe observes only harness-declared
  backgrounding, so `paused` means "no new admission and no harness-tracked background
  work." Given the module's honest-reporting posture, the overclaim is worth correcting.
