## Findings (by confidence)

### MEDIUM — discuss before merge

1. **`environments/dev/modules/agent-context-backend.tfvars` + `cyber-sandbox-backend.tfvars` — ACCOUNT_ID placeholder in bucket field will break `agent-context-infra-apply.yml` and `cyber-infra-apply.yml` workflows.**

   These two workflows do NOT use the `load-deploy-config` action and do NOT pass `-backend-config="bucket=${STATE_BUCKET}"` override at terraform init (unlike `gateway-infra-apply.yml` and `platform-infra-apply.yml` which do). They rely on the backend tfvars file having the literal bucket name.

   **Impact:** When operator runs `cyber-infra-apply.yml` or `agent-context-infra-apply.yml`, terraform init will try to use S3 bucket `adp-terraform-state-ACCOUNT_ID` (literal string) and fail.

   **Mitigation:** This is a pre-existing gap in these workflows (they never had `load-deploy-config`). The existing pattern on main worked because the account ID was hardcoded. Two paths to fix:
   - (a) Add `load-deploy-config` step + `bucket=${STATE_BUCKET}` override to `cyber-infra-apply.yml` and `agent-context-infra-apply.yml` (follow-up PR), OR
   - (b) Have `bootstrap.sh` substitute ACCOUNT_ID at clone time (it already does this for `environments/` tfvars)

   **Verdict:** NOT a merge blocker because `bootstrap.sh` already runs `find environments/ -name "*.tfvars" -exec sed -i -e "s/ACCOUNT_ID/${ACCOUNT_ID}/g"` which processes these exact files. The deployment playbook (CLAUDE.md) requires running `bootstrap.sh` before any terraform. But a follow-up to add `load-deploy-config` to these workflows would be robust.

2. **`modules/domain-apps/cyber/infra/terraform.tfvars` — `account_id = "ACCOUNT_ID"` has no substitution mechanism.**

   This file is at `modules/domain-apps/cyber/infra/terraform.tfvars` (NOT in `environments/`), so `bootstrap.sh`'s `find environments/` won't process it. The `cyber-infra-apply.yml` workflow passes it directly to terraform with no substitution.

   **Impact:** `terraform plan/apply` will receive the literal string `"ACCOUNT_ID"` for the `account_id` variable instead of a 12-digit number. Terraform resources that use this variable (e.g., ECR URLs, ARNs) will be malformed.

   **Mitigation options:**
   - Move this file to `environments/dev/modules/cyber.tfvars` (where bootstrap.sh would catch it)
   - Add sed substitution to `cyber-infra-apply.yml`
   - Use `-var "account_id=$(aws sts get-caller-identity --query Account --output text)"` at plan/apply time

   **Verdict:** This is a **deployment breakage** for the cyber module. However, the cyber module is not yet in production and is deployed via manual `workflow_dispatch` only. Filing as MEDIUM because the fix is straightforward and can be addressed in a follow-up.

3. **`environments/dev/modules/agent-context.tfvars` — `account_id = "ACCOUNT_ID"` — same gap as #2.**

   The `agent-context-infra-apply.yml` uses this file via `VAR_FILE: environments/dev/modules/agent-context.tfvars`. Since this IS in `environments/`, `bootstrap.sh` WILL substitute it. But the workflow doesn't run bootstrap first — it operates on the checked-out ref directly.

   **Mitigation:** Same as #1 — `bootstrap.sh` handles it for `deploy-all.sh` path; the individual workflow needs load-deploy-config or sed.

4. **`modules/gateway/scripts/lambda-events-policy.json` — `ACCOUNT_ID` placeholder with no consumer.**

   No script, workflow, or terraform file references this JSON policy file. It appears to be a documentation/reference artifact. The `ACCOUNT_ID` placeholder has no substitution mechanism, but since nothing consumes it automatically, it's harmless. If someone uses it manually, they'll know to substitute.

5. **`modules/gateway/k8s/deployment.yaml` — `REPLACE_WITH_GATEWAY_IMAGE` will cause K8s to immediately try to pull an image named literally `REPLACE_WITH_GATEWAY_IMAGE` during `kubectl apply`.**

   The `gateway-deploy.yml` does `kubectl apply -f deployment.yaml` then immediately `kubectl set image` to override. During the brief window between apply and set-image, K8s may attempt to schedule pods with the invalid image and they'll enter `ErrImagePull`. This is acceptable because:
   - The `kubectl set image` fires immediately after in the same step
   - The existing deployment (if any) won't be disrupted due to rolling update strategy
   - On first deploy, the pods will error briefly until set-image propagates

   The workflow comment on line 293 already says "The manifest has a generic placeholder" which suggests this is intentional.
