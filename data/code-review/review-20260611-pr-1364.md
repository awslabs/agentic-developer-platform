## Findings (by confidence)

### HIGH — merge blockers

**None.** This is a documentation/design PR with no code changes. All acceptance criteria from the issue are satisfied.

### MEDIUM — discuss before merge

1. **`Closes #1348` may be premature** — The issue describes the full replacement of OpenViking (code + Terraform + manifests + re-indexing). The PR only delivers the design note. Merging with `Closes #1348` will auto-close the issue before implementation is done. **Recommendation:** Change to `Part of #1348` or remove the closing keyword and manually close after implementation PRs land. However, since the architect's task was specifically the design review and the issue comments show this was their assigned scope, this is acceptable if the team agrees the issue's "done" state is the design approval (with implementation tracked via follow-up PRs).

2. **WIP commit in history** — First commit is `WIP: agent/architect starting #1348` (empty/placeholder). When squash-merged this is fine (both commits collapse), but if regular-merged it leaves a noise commit. **Recommendation:** Squash merge.

3. **IAM policy resource ARN format** — §5.4 uses `arn:aws:s3vectors:${region}:${account}:vector-bucket/adp-*` but based on the AWS documentation the ARN format for S3 Vectors indexes is `arn:aws:s3vectors:${region}:${account}:bucket/${BucketName}/index/${IndexName}`. The design should use the correct ARN format. This is a design doc accuracy issue, not a code blocker — implementers should verify against current AWS IAM docs.

4. **Metadata key semantics** — §8.2 code sample puts all metadata keys in a single flat `metadata` dict, but S3 Vectors API separates `metadata` (filterable, up to 2KB, 50 keys) from `data` (the vector itself). The `file_path`, `symbol_name`, `line_start`, `line_end` should go in a separate non-filterable metadata section. The prose in §4.1 correctly distinguishes these, but the code sample in §8.2 doesn't separate them. Implementers should follow §4.1's guidance, not the code sample structure.

### LOW — follow-up candidates

1. **`browse` feature rebuild deferred** (§13.3) — correctly scoped out but should be tracked as a follow-up issue.
2. **Top-K=100 ceiling** (noted in §2.1) — fine for current use cases but should be documented as a known limitation.
3. **Index naming doesn't include model/dimension** — The architect review (Comment #13, §4.3) recommended names like `code-vectors-titan1024-shard0`. The design uses `code-shard-{N}`. The recommendation is valid for future model migration — should be adopted in implementation.
4. **Dependency on #1354 and #1355** — The architect review (Comment #13, §4.4) noted this issue can't ship standalone without the Mountpoint (#1354) and Postgres catalog (#1355) work. The design doc acknowledges the phased approach but doesn't explicitly declare blockers.
