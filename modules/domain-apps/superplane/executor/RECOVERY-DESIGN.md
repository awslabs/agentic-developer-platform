# #5928 — complete original AWS allocation recovery

Supervisor approval: this design is approved for app-only implementation after #6226 merges, with remote runtime validation only. Implement the connected cancellation-to-cleanup path, original Node inventory/removal, captured-workload recovery and separated cost evidence. Preserve uncertainty for lost responses without trustworthy provenance. No source call may be rewritten as successful or absent merely to complete cleanup. Shared runtime expansion and cloud deployment remain excluded. This approval is for source work under the user's existing instruction, not live operations.

## Outcome and existing foundations

Cancellation, interrupted observation and lost responses must preserve the original allocation's identities, stop further creating work and either complete authorized cleanup or retain explicit unresolved exposure. Recovery must not recreate machines, repeat node initialization, resubmit workloads or substitute a same-name object. Resource absence and incurred cost are separate facts.

The current implementation already supplies shared Harness admission, provider intents, execution/recovery fences, allocation inventory, scoped claim observations and atomic recovery settlement receipts. `executor/superplane_executor/recovery.py` delegates claim/retry decisions to Harness; `recovery_inventory.py` consumes protected observations. Native commands have durable intent/handle journals and no automatic resend after uncertain SendCommand acceptance (`node_command_journal.py`, `node_command_inventory.py`). Network journals and cleanup preserve retained/adopted dependencies (`network_runtime.py`, `network_inventory.py` and network ownership modules). These should be extended, not replaced by another workflow engine.

These are source-supported capabilities with existing fixture coverage, not proof of live cleanup or bills. This audit ran no runtime tests or live calls.

## Concrete gaps

1. **No durable Node cleanup obligation.** `workspace.py:verified_nodes` checks Node UID/providerID against original EC2 instances but returns an in-memory map. Some pod result evidence includes Node identity; that is not complete join-time allocation inventory. `inventory.py:discover` inventories EC2 instances/volumes/interfaces/addresses, workload roots, networks and commands, but no Node resource. A stopped allocation can therefore leave a Kubernetes Node registration outside the release assessment.
2. **Deletion requests are not draining or completed removal.** `workspace.py:delete` sends foreground, UID-preconditioned root-object DELETEs. `provider.py`'s `delete_cluster` branch immediately proceeds to SkyPilot `/down`; there is no bounded wait for owned Pods, cordon/eviction sequence or original-UID Node deletion. Finalizer dependent-Pod reads help retain exposure afterward but do not establish the requested cleanup ordering.
3. **Cancellation does not drive compensation.** `task_worker.py:controller_task` refuses cancelled work; protected `controller_recovery.py` observation endpoints are read-only. `controller_deployments.py` admits teardown only from a closed, settled provision source in succeeded/failed/cancelled state. An uncertain source cannot simply invoke cleanup through its revoked/expired execution grant. A connected authorized cleanup transition is required, while retaining the recovery observer's read-only authority.
4. **Lost workload replies remain deliberately unresolved.** `workspace.py:apply` captures UID only after a successful POST response. `inventory.py:discover` refuses to adopt a later name/label match for governed workloads. `controller_recovery.py:observe` requires a journalled request ID; `recovery_observation.py:observe_request` handles launch/removal/native commands, not deploy/status. Even persisted workload UIDs need a recovery adapter; a truly lost UID needs trustworthy provenance, not relaxed label checks.
5. **Lost SkyPilot handles cannot be observed through the current endpoint.** A missing `controller_provider_requests.request_id` is refused. Tag inventory can reveal retained compute, but does not prove the async launch request is terminal or that late machines cannot still appear. An empty listing must not authorize resubmission or release.
6. **An exact EC2 read currently equates an empty collection with absence.** `inventory.py:observe` returns ABSENT for `if not items` after successful Describe calls. The next implementation should distinguish an explicitly authoritative not-found/terminated observation from an empty or malformed response and retain UNKNOWN when completeness/identity is not established. Native command termination already uses a stricter exact-instance terminated check.
7. **Accounting has exposure but no separated cost evidence.** `inventory.py:accounting` reports resource/call dispositions, completeness and release eligibility. It does not record compute, storage, network and transfer observations separately, their time windows or billed-cost unknowns.

## Small connected implementation sequence

### 1. Persist original Node and workload-effect obligations

Reuse `harness_allocation_resource` for immutable Node bindings; **do not add a redundant Node journal/table**. Add only app-owned cleanup-binding/workload mutation intent evidence that existing durable records cannot represent. Bind obligations to original org/workspace, original cluster identity and approved ARN, registration/membership generation where applicable, allocation, source operation/plan digest, admitted creating step keys, and exact provider identity. Existing membership records the enumerating observer's operation/attempt/fence.

For Nodes, use `provider='aws'`, a distinct `kind='kubernetes_node'`, and a versioned unambiguous reference retaining the exact domain cluster UUID, Node name, server UID, native providerID and region (providerID also retains zone/instance ID). Resolve and compare the full cluster ARN/account and original EC2 reference through the immutable source plan and creating-resource membership before querying or mutating. `InventoryAuthority.enumerate_resources` (`inventory.py:915`) already provides additive membership, live-fence checks, immutable provider/reference/kind and merged step attribution. It therefore supplies the durable identity guarantee without duplicating it in a domain table.

The shared `provider_reference` bound is 255 characters (`inventory.py:240`). Use an explicit compact representation and reject unsupported lengths before dependent workload execution; never truncate Node names, drop region/cluster identity, or replace the provider query handle with a hash. `resource_id` may be a stable digest for indexing only if the complete bounded query identity remains in `provider_reference`. Prepared native AWS Node names normally fit; this is a supported-bound check, not a claim that arbitrary Kubernetes Node names fit. Add boundary and overlength tests and retain unresolved exposure when discovery finds an unsupported identity.

Capture verified join identities as soon as observed, before dependent workload execution. Refactor the existing `Workspace.verified_nodes` identity checks so a common dedicated-authority helper can return original identities without requiring Ready/GPU state; the workload readiness caller keeps those requirements. Recovery/finalizer discovery must include partial, NotReady and deleting original Nodes. A label is only a query hint. Bind new observations to original provider-observed EC2 membership, exact providerID/zone and trusted dedicated Node registration authority. Fresh bounded discovery must not certify no Nodes solely because a capacity-label selector returned none; query known exact names and account for original providerIDs in a complete bounded Node listing. Incomplete pagination, excess bounds, conflicting UIDs or untrusted registration provenance remains UNKNOWN.

Prefer first enumeration under the source execution or source recovery claim, with its original launch/native-bootstrap creating step keys. If the first trustworthy observation occurs under a separate cleanup claim, `harness_allocation_resource.operation_id` correctly records that **observer**, not the creator. Validate the original source admission, original creating call keys and original EC2 membership independently and attach only those verified creating keys. Do not overwrite the observer column to fabricate source provenance. Node provenance checks must explicitly support this case; do not weaken the existing workload rule that requires a captured original workload UID. Once recorded, a same-name replacement cannot overwrite the retained UID; observe the old identity and conservatively retain any newly discovered original-instance obligation.

A crash after registration but before shared membership is written remains a discovery boundary. Under a fresh recovery claim, query original EC2 instances and the dedicated cluster, require the same original providerID and independently trusted Node-registration authority, then enumerate the server UID through the existing inventory authority. Do not authorize destructive adoption from labels or providerID writable by an untrusted cluster principal. A replaced Node UID is a new identity and remains unresolved unless separately established under that authority.

Split-pool discipline: read canonical cluster/source bindings through their supported domain/shared connections, then record Node membership only through the shared inventory authority. Do not join unavailable domain tables from the Harness connection or hold domain locks while awaiting a reverse-order shared lock. For cleanup/workload effects that require new domain intent, persist immutable intent first and enumerate the corresponding shared obligation under the current fence before dispatch. Domain writes are evidence, never proof of a live shared lease. A crash between stores is conservatively discoverable. Retain late accepted handles without using them to confer mutation authority. Follow existing native-command/network journal patterns and test the two-pool failure windows.

### 2. Connect cancellation to bounded, admitted cleanup

Keep cancelled/expired execution credentials unusable and protected recovery observers read-only. Use the existing Jobs/admission interfaces to produce one durable cleanup intent tied to the original allocation and an immutable cleanup-only plan. Deduplicate by source allocation/operation and consume a current separately authorized cleanup grant. No new allocator or generic retry loop.

The shared-interface audit confirms this is implementable with existing admission and execution interfaces; no new shared engine or cleanup grant type is required for **mutation progress**. Replace the current app-only settled-source guard with a distinct reviewed cancelled-source path, not an unrestricted teardown exception. The exact composition and its mandatory limits are below.

#### Confirmed shared composition and app preconditions

1. Record authenticated source cancellation through `harness_jobs.recovery.request_cancellation` (`modules/harness/jobs/harness_jobs/recovery.py:125`). Re-read source tenant/operation/cancellation state; a false return alone does not distinguish already-cancelled from missing/terminal. The source stays cancelled-requested and unresolved. Do not set it succeeded, close its lease, overwrite provider outcomes or release its reservation to make admission pass.
2. Establish a fenced, no-active-dispatch source through the existing recovery claim path. Require original cancellation and expiry of its original execution lease; a successful `harness_jobs.leases.fence_expired_lease` (`leases.py:803`) takeover increments its fence and refuses while its original `harness-provider-dispatch:<operation_id>` lock is held. Persist immutable takeover/source-fence/cancellation evidence at cleanup admission. Source cancellation blocks ordinary reacquisition (`leases.py:474`) and new provider intents (`execution.py:1051`). Keep that source recovery grant observation-only. Its subsequent expiry or legitimate replacement by another observation claim does not revoke independently approved cleanup and must not re-enable the cancelled source. The cleanup binding records evidence of fencing, not a borrowed recovery credential whose lifetime authorizes mutation. Do not force-close or steal a still-running provider hook. A fenced source may still have an already-accepted asynchronous cloud action; retain that uncertainty independently of local dispatch quiescence.
3. Under an app-owned deduplicated cleanup binding, derive the cleanup request from the exact persisted source using `deployment_plan.teardown_request` (`executor/superplane_executor/deployment_plan.py:402`). Preserve org/workspace, allocation, original deployment and plan, cluster/registration generation, eligible regions, account, credentials and exact original resource identities. Use one durable cleanup action for that source/allocation across repeated API requests/approval deliveries; verify concurrent requests cannot admit different cleanup owners. Revalidate these bindings on execution, not just preview.
4. Require a **current separate approval** for the exact cleanup request and use the existing app `facade.open_operation` path (`app/services/controller_deployments.py`, following its current source guard) to `harness_jobs.admission.admit_operation` (`admission.py:565`). Approval, idempotent identity, reservation and dispatch remain ordinary Harness behavior. `admit_operation` has no requirement that a different source operation be settled. `allocation.py:26` explicitly allows separately approved operations on one allocation.
5. Ordinary `harness_jobs.leases.acquire` (`leases.py:300`) grants the new cleanup operation its own attempt/fence. Its state/cancellation/history checks concern that new operation, not the source. Production `task_worker.controller_task` constructs `TaskRegistry`; provider execution still flows through `ControllerRPCServer.execute_step` and `OperationExecutor`. Keep the existing reviewed `('aws', 'delete_cluster')` descriptor: `effects.py` classifies it REMOVES, and `_refuse_creation_into_a_sealed_allocation` (`execution.py:293`, removal branch at 330) allows it without requiring an allocation seal. New unrecognized verbs are conservatively creating; do not bypass effect classification for a cosmetic cleanup descriptor.

The app precondition is consequently: authenticated cancellation + fenced source with no active local dispatch + current separate cleanup approval + exact original allocation/cluster/plan bindings + deduplicated cleanup ownership. None is satisfied by simply deleting `controller_deployments.py:404-417`'s settled-source predicate. Record the source fence/claim provenance and revalidate cancellation, non-resumption and original identity at the provider boundary; require monotonic preserved fencing rather than making a later read-only recovery claim invalidate cleanup. Allocation locks serialize membership/seal transitions, not an entire multi-call cleanup; use the app's durable original-action ownership to prevent duplicate cleanup dispatch and respect the documented allocation-before-lease lock order. Validate source facts in short database transactions, perform external ledger/admission awaits without unnecessarily retaining shared/domain locks, then recheck facts before binding/dispatch. Test interruption and competing cleanup between these phases; a durable pending app intent is not itself provider permission.

**Mutation progress is not final cleanup settlement.** `creating_calls_unaccounted_for` (`allocation.py:239`, uncertainty predicate at 301) checks creating intents from every operation on the allocation, including the original source. `InventoryAuthority.seal_allocation` (`inventory.py:1399`, outstanding-call refusal near 1488) refuses while any such intent is intended, unresolved or unknown. The app finalizer propagates that refusal, so RPC cannot settle the cleanup as succeeded merely because a removal provider call succeeded. The source sweep likewise defers intended calls (`recovery.py:870`). Preserve removed-resource/accepted-handle evidence and report cleanup progress with unresolved accounting; do not suppress the finalizer failure or certify absence to finish the task. Final reservation release remains unavailable until original creating claims are authoritatively reconciled and complete inventory is established. There is no shared-interface blocker to safe removal progress; an API promising final complete cleanup despite still-unknown creating claims would require different semantics and is explicitly outside this design.

**Unadmitted cleanup approval expiry remains a recovery limitation.** The durable app binding commits before paid admission and pins one request and approval. A crash or admission failure followed by that approval's expiry can leave this binding without a paid operation; current approval proposal deduplication returns the same expired ticket, and the app does not replace the owner. An interrupted Harness admission with a durable intent can be reconciled by `reconcile_interrupted_admissions`: its per-approval lock excludes the original writer, its deterministic ledger key recovers an uncertain reserve, and a resolved intent prevents later admission. However, the public interface only enumerates existing intents and cannot retire an approval when the app binding exists but no Harness intent was written. Checking for no operation/intent and revoking the ticket is insufficient: approval evaluation precedes the admission lock, so a previously validated waiter could still admit. No app-only owner replacement is implemented or approved. Acceptance must retain this explicit stuck-but-safe case until a reviewed retirement/renewal transition proves permanent exclusion of late admission and settlement of all ledger obligations, preserves the old binding evidence, and requires fresh approval without duplicate cleanup. Same-owner replay after paid admission and recovery of a lost domain registration commit remain supported; they do not establish recovery of an expired, unadmitted owner.

Within that grant: revalidate original cluster/generation and resource identities; cordon owned Nodes with UID/resourceVersion guards; delete the original workload roots with UID preconditions; wait for the exact owned dependent Pods to terminate. Use bounded eviction where required and respect disruption constraints. Do not evict arbitrary tenant or system Pods merely because they are on a selected Node. An unexpected workload, failed eviction, denied read or finalizer timeout retains exposure. Dedicated GPU-plugin/essential DaemonSet handling must be explicit and must not delete shared DaemonSet objects.

After owned workload drain, invoke SkyPilot down for the original capacity only. Do not delete the Node registration while its original compute can reconnect and re-register. Once provider termination is proven, delete the exact original Node UID and verify removal in the original cluster. Recheck no replacement original-instance registration escaped discovery. Then remove exclusively owned network dependencies in their existing reverse dependency order and reobserve all retained handles. Preserve platform EKS, adopted network assets, and dependencies still referenced by another allocation/member.

The native path has no hybrid activation to revoke. Preserve its command journal/latch evidence; treat unresolved commands as tied to original compute until termination is established. Observe native SSM registration state as a separate obligation where the API provides it; do not invent a hybrid deregistration mutation for an EC2 managed node or infer registration absence from an empty inventory page.

### 3. Reconcile lost replies without inventing identity

Add claim-bound read-only workload/status observation for UIDs already captured from the original creation response. Verify the original plan, cluster/namespace generation, UID and expected immutable workload specification; preserve workload results/absence without another POST.

Before dispatch, persist an immutable mutation intent with expected kind/name/namespace/spec digest and unique request correlation. This improves evidence but is **not sufficient to recover a lost server UID**: an ordinary namespace writer can copy annotations, a nonce or a signed marker onto a replacement. Matching user-writable metadata must remain UNKNOWN.

Recover a missing UID only from mutation-protected provenance tied to the original API request and authenticated creator: for example, an existing trusted API audit/response journal that records the original server-assigned UID and cannot be written by tenants, or an explicitly reviewed admission/provenance service with equivalent guarantees. Verify that such a service exists and that its correlation survives the real failure point before relying on it. Introducing new cluster authority solely to avoid uncertainty is not the default. If trustworthy provenance is unavailable, preserve unresolved intent and never resubmit/adopt a namesake. Authorized cleanup can remove independently proven original compute/Nodes, but cannot declare complete workload absence while original workload ownership is unknown.

For lost launch/down acknowledgements, retain original request/resource evidence. Prefer exact saved request observation; do not replay SkyPilot POSTs to obtain a handle. If a request handle was lost, inventory is exposure evidence, not request terminality. Require provider-backed proof that no original creation can still complete before release; otherwise remain unresolved. This limitation should be explicit in acceptance rather than hidden by empty-list assumptions.

### 4. Add resource and cost evidence to existing accounting

Extend app accounting projections/receipts with separate compute, storage, network and transfer categories. Each category records original provider/account/region/allocation references, observation source, observed interval, unit/quantity when available, currency and billed amount only when supported by authoritative billing data, and explicit unknown/reason fields otherwise. Distinguish resource-usage measurements, price estimates and observed billed costs; do not fabricate an allocation attribution from account-level totals.

Deletion can establish no continuing resource exposure while every billed category remains unknown. Preserve pre-deletion usage/handle evidence and accept late billing observations through the existing deduplicated receipt/reporting path. Do not change budget-release semantics into a zero-charge assertion. A billing adapter is optional only if the result explicitly records unavailable categories as unknown; four unlabeled nulls are insufficient evidence.
