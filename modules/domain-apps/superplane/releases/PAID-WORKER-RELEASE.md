# Separate paid-worker release

This implements the release-source portion of [native paid-worker preparation](../installation/PAID-WORKER-PREPARATION.md). [DESIGN.md](../DESIGN.md) remains authoritative; no story completion or live worker acceptance follows from building an image.

`superplane-paid-worker` has its own pending lock entry, ECR repository and project manifest. The existing platform CodeBuild module consumes `modules/domain-apps/*/codebuild/projects.json`, so the app-owned entry selects the fixed paid-worker buildspec and grants its generated project role only the declared ECR repository plus existing bounded build permissions. This does not modify or relabel the executor project. The app ECR Terraform inventory takes the union of pending and promoted entries, preserving the paid repository during promotion.

**Source enrollment is implemented; infrastructure provisioning and a live build have not been performed.** An operator must separately review/apply the existing platform project enrollment, app ECR plan, and exact project/repository additions to the existing dispatcher authorization. Adding the manifest does not grant the current operator permission or prove the project exists. No hand-created project or broad dispatcher grant is a substitute. The `superplane-executor-build.yml` workflow remains executor-only; this app-owned CLI uses the existing `platform/scripts/codebuild-run.sh` release archive seam, with no shared workflow change.

After that infrastructure is approved and observed, use an exact clean checkout of a commit already merged to maintained `aws-e/adp:main`. The CLI checks its GitHub merge ancestry before cloud calls, confirms the selected AWS account, exact project ARN/role/source/buildspec/environment and separately provisioned immutable ECR repository, and uses only the lock-derived paid source and repository. These pre/post observations detect project drift but are not an atomic fence on concurrent CodeBuild project updates; the provisioning owner must preserve the reviewed project during the authorized build. It passes `ADP_RELEASE_BUILD=true` and the exact SHA to the existing dispatcher, which archives committed source rather than the working directory. Supply the separately reviewed Python 3.12 base by digest.

```sh
python3 modules/domain-apps/superplane/releases/build_paid_worker.py \
  --account "$APP_ACCOUNT" --region "$APP_REGION" --environment "$APP_ENVIRONMENT" \
  --source-sha "$REVIEWED_MERGED_SHA" --python-image "$REVIEWED_PYTHON_IMAGE" \
  --receipt "$PRIVATE_RELEASE_DIRECTORY/paid-worker-build.json"
```

Before source upload or dispatch, the CLI conditionally claims a stable project/source identity in `adp-terraform-state-<account>/superplane/releases/paid-worker/dispatch/<dispatch-id>/claim.json`. This app prefix is outside the shared `codebuild/src/` lifecycle. The bucket must be owned by the selected account with versioning enabled and readable lifecycle metadata that cannot expire or archive current/noncurrent claim evidence. The immutable claim binds a canonical config digest including the reviewed base. A new local receipt path, lost local directory or changed base cannot repeat dispatch for the same project/source. There is no claim reset/delete/expiry path.

Conditional versioned `child.json` evidence records the build ID immediately when the existing shared CLI emits it, before polling completes. The private local receipt is a recovery aid, not the dispatch authority. If the dispatcher loses contact, fails or is interrupted, its state remains `dispatch-outcome-unknown`; reconcile the original build with the platform owner. A lost claim-write response also prohibits start. Live dispatcher authorization must explicitly cover only this app claim/evidence prefix as well as its existing source prefix; this source change does not grant that permission. The shared dispatch subprocess uses one AWS attempt per call so the SDK cannot silently retry an ambiguous `StartBuild`; existing explicit read-only polling retries remain. This wrapper does not repeat starts or cancel cloud builds.

The maintained project contract pins a **60-minute build timeout** and the existing shared renderer/service's **480-minute queue timeout**. Both are checked before dispatch and against the actual completed build. The manifest sets the supported `build_timeout` field; it does not invent a queue field the shared renderer ignores. Live authorization must cover the full possible queue/build window or require separately supported tighter queue configuration. The local polling deadline includes a five-minute grace; bounded pipe reads and process-group cleanup stop only local polling, including a descendant holding stdout open; they do not cancel a cloud build.

After a successful dispatcher response, the CLI checks the actual CodeBuild record against the project, exact archived source, buildspec, service role, build environment and every effective source/base/ECR override. It then reads the immutable commit tag's ECR digest and records `built-awaiting-image-review`. It does not modify the lock or deploy anything. That state proves a bounded build result, not image safety, entrypoint/runtime compatibility, effective IAM authority, worker readiness or workload success.

Review the actual produced image and required native runtime contract before promotion. In a reviewed lock update, move the pending metadata to `image_sources`, retain `source_path`, `ecr_repository`, `build_entrypoint`, `buildspec`, `project_manifest` and origin metadata, remove `blocked_by`, and add the actual registry/repository/tag, exact source revision, build ID/evidence and digest under `images`. Do not fabricate a digest or reinterpret the controller-service digest. The existing resolver and ECR inventory preserve the build inputs/repository across that transition. Native installer activation still awaits its separate authenticated shared-binding and live identity/schema/network gates.

Merging release/build-script changes can trigger existing API/controller/monitor publishing workflows. Those are separate live build actions requiring their existing account, environment and budget authorization; do not approve their build environment as a consequence of source review. The paid CLI itself is explicit and does not trigger on merge.
