# Separate Superplane domain runtime preparation

This is an app-owned source candidate for #7058. It prepares **only** a dedicated standard SQS queue and two limited IAM roles in a separate Terraform state. It does not deploy a worker, register a Gateway principal, modify the Gateway binding, create a database, install a Kubernetes Secret, turn on API admission, or prove native lifecycle execution. The source owner must review it independently before the foreground installer connects it to `deploy.sh`; the foreground owns `runner.py`, `config.py`, `__main__.py` and control-plane Terraform. No live target has been exercised by this PR.

## Inputs and output

`installation.runtime_preparation.review(request, inspector)` accepts **exactly** `account_id`, `region`, `environment`, `cluster`, `namespace` and `operator_role_arn`. These are private selected-installation values, not sample defaults. The inspector implements the existing installer adapter's `aws(service, *args)` and `json(response)` operations. Review reads STS, EKS/OIDC, SQS names and IAM roles; it refuses another account, assumed role, cluster or an unowned name. It returns the installation ID, request digest, selected cluster/OIDC, exact queue URL/ARN and two distinct role ARNs with `worker_ready: false`. It reserves no names. Identity checks are repeated before apply.

`compose(request, reviewed, env, lock, operator)` uses that review and the existing installer environment/release lock. The environment must include the installer's closed `deployment_identity` metadata: `service`, `connection_label`, `expected_role_arn` and independently resolved immutable `expected_role_id`. The request's operator ARN must match that selected connection; IAM role paths are supported. The proposal includes this metadata so a saved receipt cannot resume under another connection or recreated role. The private `operator` mapping must contain exactly:

- `review_id`: a reference for an independently authenticated operator review, **not approval proof**.
- `keda_operator_role_arn`: the selected existing same-account KEDA operator role; its owner must grant assumption of the new observer role by maintained policy.
- `producer_registry_id`, `worker_registry_id`: distinct identities assigned through the protected Gateway owner route, not created by this mapping.
- `database_secret_id`, `observation_credential_secret_id`: distinct selected Secrets Manager **references**, never SecretString or credentials.
- `observation_url`, `repo`: the protected Gateway observation endpoint and repository binding.
- `policy_configmap: superplane-lifecycle-policy`, `state_claim: superplane-lifecycle-state`: fixed reviewed inputs; existence, immutability and durability are not attested here.
- `worker`: exactly `database_secret`, `workspace_credentials_secret`, `provider_secret`, `operation_schema`, `skypilot_url`, `management_api_server`, `node_selector`, `egress`, `max_replica_count`, `active_deadline_seconds`. The first three are Kubernetes Secret **names**, not values. The existing paid-worker validator enforces the dedicated schema, bounded execution, distinct secrets and fixed egress names. The immutable paid-worker image comes from the selected release lock; a pending image is refused.

The composer outputs `terraform_variables`, a paid-worker configuration accepted by the existing validator, a **proposed** exact Gateway `DomainBinding`, protected registry registration proposals, Secret projection names and the current Harness Jobs schema owner. It always sets `worker_ready`, `binding_attested`, `authority_verified`, `shared_services_verified`, `domain_schema_installed`, `secret_projections_verified`, `policy_immutable_verified` and `state_durable_verified` to false. Do not feed those proposals into a shared service as an administrator bypass. The proposal does not manufacture workspace registration before first create.

## Plan, apply and recovery

The Python entry point for the foreground owner is `installation.runtime_preparation.prepare(request, env, lock, operator, inspector, commands, directory, *, approved_plan_digest=None, approval_check=None)`. The caller supplies the selected installer identity and release lock, its existing authenticated AWS inspector and checked command adapter, and an absolute private directory. `prepare` copies this root's pinned Terraform sources into that directory; uses the selected account's existing `adp-terraform-state-<account>` bucket, **separate** `<environment>/modules/superplane-domain-runtime/terraform.tfstate` key and existing `adp-terraform-locks` table; and saves a mode-0600 receipt and Terraform plan. A first call without approval returns `status: planned` with `plan_sha256`, a source digest and the exact named resources; it creates nothing. The receipt contains references and digests, not secret values. Preserve the receipt, plan and access-controlled working directory until completion/reconciliation.

To apply, the selected operator must obtain independent review of **that saved plan** and pass its exact `approved_plan_digest`. The foreground must provide an authenticated, separately trusted `approval_check.verify_plan(plan_sha256=..., installation_id=..., review_id=...)` adapter returning exactly `approved: true`, the matching digest/installation/review identifiers and a distinct nonempty `approver` identity. The `review_id` in configuration, a locally written approval dict or possession of the plan file is not this authority. Without that adapter, apply refuses. **This PR does not supply an approver or authorize one**. The foreground must choose and review its maintained approver mechanism before connecting this branch.

The foreground must bind both command adapters to the selected authorized connection. Before any Terraform command (including backend initialization and reconciliation), preparation uses the Terraform command adapter to verify STS account, role session and immutable RoleId against IAM `GetRole`. It repeats verification after approval, before recording an apply attempt. A read-only inspector's successful check alone does not authorize the Terraform adapter. Terraform also checks the selected role's exact ARN and unique ID. This requires narrowly scoped `iam:GetRole` on the selected operator role, not broader installer privileges. Existing saved receipts from before this identity binding must not be reused; an operator must reconcile any prior attempt and obtain a fresh reviewed plan.

The saved-plan inspector allows only the dedicated queue, worker/observer roles and their two inline policies, with exact names, owner tags, role trusts, resource-scoped actions, fixed bounds and no destructive, unknown or additional resources. Terraform itself verifies the selected account **and operator role**, active EKS/OIDC identity and existing KEDA role. On apply, the attempt is persisted before the command. If the response is lost, a same-input retry does **not** repeat apply: it compares this state with the live queue, owner tags, exact role unique IDs, trusts, policies and disabled output, or refuses when the result remains ambiguous. A different source, review, identity, resource, tag or policy needs a new independent decision; it cannot silently adopt an unowned role or queue. Neither a Terraform apply nor an `applied` infrastructure receipt means Gateway or worker readiness.

## Maintained owner handoff

The existing domain installer already owns isolated schema/runtime-role SQL and credential preparation through `database_preparation` and `config.prepare_database_sql`. Harness Jobs owns the versioned operation schema and upgrade contract under `modules/harness/jobs/harness_jobs/schema.py`; use its reviewed migration path for the selected domain schema, then verify grants and actual Secret projections with the database and Kubernetes owners. This PR does not run migrations or put DSNs into Terraform or source files. For the Gateway owner, install a distinct JSON DSN reference, the observation-credential reference and narrow Gateway IAM for `sqs:SendMessage`, `sqs:GetQueueAttributes`, `sqs:ReceiveMessage`, `sqs:DeleteMessage` and `sqs:ChangeMessageVisibility` on this exact queue, plus only the selected secret reads. The app roles do **not** acquire those Gateway operations: the worker invokes only the named controller-execution routes, and the KEDA observer reads only this queue's attributes. An owner-approved existing KEDA trust/policy route must permit assuming the observer role.

**Blocked shared-owner contract:** The current maintained `/admin/registry/agents` route cannot assign the `internal` registry scope or protected `credential_scopes` required by Gateway's producer/executor/recovery checks. Gateway currently loads `ADP_DOMAIN_OPERATION_BINDINGS` from deployment configuration and offers no maintained protected binding write or authenticated non-consuming exact-binding read. `producer-readiness` does not return binding identity or revision. Shared owners must review an audited, narrowly authorized registration and binding configuration/read mechanism; do not patch DynamoDB rows, bypass admin permissions, hardcode credentials or substitute a readiness response for #5535's real binding proof. Supply exact actual worker image digests and verify KEDA, OIDC, current identity, Secret metadata, database grants, policy/state resources and network enforcement before the foreground activates an installed worker. Keep the worker paused and API lifecycle admission closed until that proof and the final runtime readiness gate succeed. Optional workload serving, GPUs and new account creation are outside this source path.
