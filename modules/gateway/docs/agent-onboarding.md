# Agent Onboarding Guide

This guide explains how to onboard a new AI agent to the Bedrock Gateway platform. Once onboarded, your agent can be triggered by labeling GitHub issues and will make LLM calls through the gateway with budget enforcement and IAM-based authentication.

## Overview

The onboarding process does the following automatically:

1. Validates your inputs and IAM role ARN
2. Creates a Kubernetes namespace and ServiceAccount (with IRSA annotation) for your agent
3. Registers the agent in the agent registry (DynamoDB) with budget and model allowances
4. Creates a GitHub label that triggers your agent
5. Generates a per-agent GitHub Actions workflow file and opens a PR for you to merge

## Prerequisites

Before running the onboarding workflow you need:

- An AWS IAM role your agent will assume (one role per agent — roles cannot be shared)
- The role must exist in the same AWS account as the gateway (`605440105851`)
- Your GitHub username
- An org ID and optionally a team ID (ask your platform admin if unsure)

The onboarding workflow automatically attaches the `bedrockgw-agent-gateway-invoke` managed policy to your role, which grants `execute-api:Invoke` on the gateway's `/agent/*` path. You do not need to add this yourself.

After onboarding, you will need to update your role's trust policy to allow IRSA (the workflow summary shows the exact snippet).

### Creating an IAM Role

Create a role with the permissions your agent needs for its own work (e.g., deploying infra, reading S3). Gateway access is handled automatically. Example:

```bash
aws iam create-role \
  --role-name my-agent-role \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {"Service": "ec2.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }]
  }'
```

After onboarding, replace the trust policy with the IRSA snippet shown in the workflow summary.

## Running the Onboarding Workflow

Go to **Actions → Onboard Agent → Run workflow** in this repository.

### Required Inputs

| Input | Description | Example |
|-------|-------------|---------|
| `agent_name` | Unique name for your agent. Lowercase, alphanumeric, hyphens only. | `my-deployer` |
| `role_arn` | ARN of the IAM role your agent will use. One role per agent. | `arn:aws:iam::123456789012:role/my-agent-role` |
| `org_id` | Your organisation ID on the platform. | `acme` |
| `owner` | Your GitHub username. | `jsmith` |
| `level` | Scope level of the agent: `team`, `org`, or `personal`. | `team` |
| `agent_type` | Type of work the agent does: `general`, `infra`, `app-dev`, `monitoring`, `security`. | `general` |

### Optional Inputs

| Input | Description | Default |
|-------|-------------|---------|
| `team_id` | Team ID within your org. | — |
| `app_name` | App name (relevant for app-level agents). | — |
| `scope` | `shared` (visible to team) or `personal`. | `shared` |
| `allowed_models` | Comma-separated list of models the agent may use. | `claude-sonnet,claude-haiku` |
| `budget_monthly_usd` | Monthly spend cap in USD. Set to `0` for unlimited. | `50` |
| `description` | Short description of what the agent does. | — |
| `github_scope` | `repo` (this repo only) or `org` (all repos in the org). | `repo` |
| `github_repo` | Target repo name when `github_scope=repo`. | current repo |

## After the Workflow Runs

### 1. Update your IAM role trust policy

The workflow summary (visible in the Actions run) shows the exact trust policy statement to add to your IAM role. It looks like:

```json
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/oidc.eks.REGION.amazonaws.com/id/CLUSTER_ID"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "oidc.eks.REGION.amazonaws.com/id/CLUSTER_ID:sub": "system:serviceaccount:arc-runners-TEAM_ID:agent-AGENT_NAME-sa"
    }
  }
}
```

Add this to your role's trust policy:

```bash
aws iam update-assume-role-policy \
  --role-name my-agent-role \
  --policy-document file://trust-policy.json
```

### 2. Merge the generated PR

The workflow opens a PR titled **"Onboard agent: `<agent-name>`"** that adds `.github/workflows/<agent-name>.yml` to the repo. Review and merge it.

This workflow file is a thin wrapper that triggers the shared `agent-runner.yml` when an issue is labeled with your agent's name.

### 3. Trigger your agent

Label any GitHub issue with your agent's name (e.g., `my-deployer`) and the agent will pick it up and start working.

## How It Works

```
Developer labels issue
        │
        ▼
.github/workflows/<agent-name>.yml  (generated by onboarding)
        │  triggers agent-runner.yml
        ▼
agent-runner.yml
        │  runs on arc-runner-<agent-name> pod
        │  pod uses ServiceAccount → IRSA → IAM role
        ▼
Claude Code (skill-agent.ts)
        │  CLAUDE_CODE_USE_BEDROCK=1
        │  ANTHROPIC_BEDROCK_BASE_URL → API Gateway /agent path
        ▼
API Gateway (AWS_IAM auth)
        │  validates SigV4 signature
        │  checks agent registry + budget
        ▼
Bedrock Gateway (FastAPI)
        │  enforces budget / rate limits
        ▼
Amazon Bedrock
```

## Agent Levels

| Level | Who creates it | Scope |
|-------|---------------|-------|
| `personal` | Any developer | Only you can trigger it |
| `team` | Any developer | Shared within your team |
| `org` | Org admin | Shared across the organisation |

## Budget and Model Limits

- Default budget: **$50/month** (configurable via `budget_monthly_usd`)
- When the budget is exhausted the gateway returns HTTP 429 and the agent stops
- Allowed models default to `claude-sonnet` and `claude-haiku`
- Platform admins can adjust limits after onboarding via the admin API

## Troubleshooting

**Workflow fails at "Call Onboarding API" with HTTP 409**
The agent name or role ARN is already registered. If you're re-running onboarding for an existing agent this is expected and the workflow continues normally.

**Workflow fails at "Call Onboarding API" with HTTP 403**
The runner's IAM role doesn't have permission to call the gateway's `/agent` path. Contact your platform admin.

**Workflow fails at "Attach Gateway Invoke Policy" with an error**
This usually means the role is in a different AWS account. Cross-account roles are supported but the policy attachment must be done manually — ask your platform admin to attach `arn:aws:iam::605440105851:policy/bedrockgw-agent-gateway-invoke` to your role, or add an equivalent inline policy.

**Agent doesn't pick up issues after merging the PR**
- Check the label name matches exactly (case-sensitive)
- Confirm the ARC runner scale set is installed (`arc-runner-<agent-name>`)
- Check the workflow is enabled in the Actions tab

**IAM role trust policy error when agent runs**
The IRSA trust policy wasn't updated after onboarding. Add the trust policy snippet from the workflow summary to your IAM role.

## Example: Onboarding a Deployment Agent

```
agent_name:         my-deployer
role_arn:           arn:aws:iam::605440105851:role/my-deployer-role
org_id:             acme
team_id:            platform
owner:              jsmith
level:              team
agent_type:         infra
budget_monthly_usd: 200
description:        Deploys services to EKS on demand
github_scope:       repo
```

After merging the PR, label an issue with `my-deployer` and the agent will start working on it.
